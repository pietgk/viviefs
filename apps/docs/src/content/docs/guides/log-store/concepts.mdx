## Datom

A datom is one fact: entity `e`, attribute `a`, value `v`, the transaction id
`tx` that minted it, `op` (`assert` or `retract`), and `cs`, the changeset it
belongs to. Each datom is its own transaction, and the log only grows: a fact
is never updated in place; a later datom asserts or retracts. The why is
[ADR-0006 One datom log as the substrate][ADR-0006].

<Sample path="libs/datom/src/schema.ts" region="datom" />

`tx` is the datom's identity. The `datoms` table has a unique `tx` and an
append ignores a datom whose `tx` it already holds, so sending the same datom
twice is safe. Every datom also gets `seq`, its position in this replica's
log: positions differ between replicas, `tx` does not.

<Sample path="libs/datom/src/migrate.ts" region="datoms-table" />

Two indexes serve the two ways the log is read: EAVT (everything about an
entity) and AEVT (every entity with an attribute). `cs` names the changeset;
when `cs` equals `tx` the datom is a changeset of one, which is what most
writes are (the changesets guide explains the rest, [ADR-0008 Single-datom transactions with changesets][ADR-0008]).

## Envelope and acceptance time

Each changeset has exactly one envelope, found by its `cs`: who
(`actor`, `device`), under which lease, with which trace context and command.
The log store stores it next to the datoms, in the `changesets` table, not as
datoms. Acceptance time is the server's clock when it accepted the changeset;
it is set once and never replaced.

## The three kinds of tables

Domain truth lives only in the log ([ADR-0006 One datom log as the substrate][ADR-0006]). Every other SQL table
is one of three kinds:

| Kind | Examples | Rebuilt from the log? |
| --- | --- | --- |
| The log itself | `datoms`, `changesets` (envelopes) | It is the source |
| Read models | `projected_facts`, `changeset_status`, one `rm_<entity type>` table per entity type | Yes: disposable, never migrated |
| Operational state of one replica | `hlc_state`, `device_cursors` | No, and it holds no domain facts |

A fact that fits none of them goes into the log. Read models are the log
store's promise to everything built on it: any read model may be dropped and
rebuilt ([ADR-0011 Log store pattern, read models, compaction and analytics][ADR-0011]). How they are built is the changesets guide's.

## Prefix scans

Entity ids encode their parent for strict composition (`O{org}/L{list}/I{item}`,
[ADR-0010 Entity ids, defining attributes and strict-composition prefixes][ADR-0010]). `scanPrefix(prefix)` returns every datom of every entity
under a prefix, which is how a list and everything in it are read at once.
The id convention itself belongs to the changesets guide.
