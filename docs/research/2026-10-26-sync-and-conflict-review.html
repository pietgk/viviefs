Sync and conflict

I53 Sync and conflict asks whether sync in the foundation is a deliberate difference from vivief, which defers sync until one user works well, and whether the foundation's story should say why; whether an attribute needs a cardinality, with many-valued attributes resolved as a set; whether text ever needs a CRDT; and whether server validation is the stack's one trust strategy. It settles 5 rows of the vivief inventory and reviews I11 Quarantine of user content after a lost lease and I12 Partial sync, history consolidation and client data access. Effect's eventlog is read first: a concept Effect already names takes Effect's name (D135 Effect's names first).

The page in five lines

  1. vivief designed sync early (Hypercore from phase 1 "so the P2P path is never blocked by a storage migration") and deferred building it. ViViEfs built it and qualified it (P09 Sync), because its first app is a phone that goes offline and a person who switches devices. The difference is the build order, not the design, and the foundation story can say so in one paragraph.
  2. Sync itself, outbox up and one cursor stream down, holds up. Effect's EventLog has the same shape (server sequence, dedup by entry id) and still lacks a typed rejection: a handler that fails turns the whole batch into an InternalServerError the client retries forever.
  3. Found: human conflict is not built as decided. The basis is a sequence number in whichever log projects it, and every changeset outside P05 Changesets and projections sends basis 0. A conflict is a row each projector derives, never a fact. The server checks write-once only. And a human-conflict attribute never drops a value: a retract is ignored, so no command can resolve a conflict (run below).
  4. The proposal: authority decides a human conflict at accept, against the server cursor the writer had pulled, and writes it into the log as a viviefs/conflict fact; a command resolves it. Effect's own EventLog detects conflicts at the server on ingest, too.
  5. No cardinality: a set is an entity per member, as membership already is, so a member can gain data later with nothing to migrate. No text CRDT until two people type in one text at once. One checkpoint stays the one place trust is enforced (D124 One checkpoint). Under the journal fence, a refused history holds no user content; quarantine is the device's rejected changesets that carry some.

Ideas worth keeping

  • A relationship is never silently re-assigned ("a session silently pointing to a different client ... too high for a healthcare context"). We have it: references are human conflict. Section 5 shows it is not yet built as decided.
  • Design for sync before you need it. vivief's own reason for Hypercore in phase 1 is ours for building sync in the foundation: retrofitting replication onto a store designed for one writer is a migration.
  • A set is not a scalar. vivief resolves a many-valued attribute differently from a one-valued one. We get the same by making each member its own entity (example c).
  • One CRDT document per text instance bounds its history and makes archiving clean. Worth keeping for the day a CRDT comes (example d).
  • The read filter is the download hint: already the direction (D114).

What it does that we do

Append-only, server-sequenced catch-up, dedup by id, SQL on both sides, Reactivity. A React Native path is now plausible through SqlEventJournal over @effect/sql-sqlite-react-native, though session auth still needs WebCrypto Ed25519 on Hermes. And one thing worth copying: conflicts are found where entries are accepted, the server on ingest, and handed to code that decides.

What it still lacks

A typed rejection of one entry: a rule that fails on the server is still a poison batch. Order by a corrected clock: a skewed phone's entries sort by its own clock. Changesets: an entry is one event, with no atomic group and no draft. One journal for the engine: Effect's durable workflow persists in Cluster's MessageStorage, not in an EventJournal. ADR-0017's reasons stand on 4.0.5; nothing to adopt, and the word "conflict" agrees with Effect's.

4. Worked examples on real code

(a) Two phones retitle a list offline (LWW)

  1. Phone A, offline at 10:00, runs renameList to "Groceries" (command.ts). Phone B, offline at 11:00, renames the same list to "Shopping".
  2. A comes online at 12:00 and pushes; the server accepts (no check for LWW). B pushes at 13:00; accepted.
  3. Every projector reduces list/title by the highest commit tx: "Shopping", on A, on B, on the server's read of the log, whichever arrived first. Shown by P05 "basis lww".

Reading. This is right and needs nothing. The HLC makes "later" mean later in time, corrected against the server, so a phone with a wrong clock cannot win by it (ADR-0007 Hybrid logical clock for tx). The cost is the usual one: A's person sees their title replaced on the next pull, with no notice. For a title that is the right trade; for a person's work it is not, which is why user content is not LWW.

(b) Two phones attach a file to one evidence item (human conflict)

Concurrent: works by accident.

  1. A attaches blob:a to evidence E1, B attaches blob:b; neither has seen the other. Both send basis 0, as every changeset outside P05 does (p09-checks.ts, p11-runtime.ts:362).
  2. The server accepts both.
  3. On each phone the projector applies one first; the second finds the first's fact above basis 0 and writes a concurrent row. A and B may disagree on which changeset the row names until a rebuild.
  4. Both files stay visible. P05 "basis human conflict" shows exactly this, on one store.

Sequential, and the resolution: broken.

  1. B has pulled blob:a and deliberately replaces it with blob:b. Basis 0 says "I saw nothing", so a conflict is raised that is not one.
  2. Both values stay visible anyway: reduceAttribute returns every assert for a human-conflict attribute and drops retracts (visibility.ts:34-36).
  3. A person "resolves" by retracting blob:a. Nothing changes: the retract is ignored.
  4. The conflict is a row in projection_conflicts, deleted and derived again on every rebuild (projector.ts:376). It has no id a command could close.
// A throwaway run of libs/datom/src/visibility.ts reduceAttribute (2026-10-26):
sequential re-attach:      [ 'blob:a', 'blob:b' ]   // a replace keeps both
retract after keep-both:   [ 'blob:a', 'blob:b' ]   // a retract removes nothing
lww:                       [ 'Shopping' ]

Reading. No command writes evidence/file outside the P05 suite, and P09 never put two devices on a human-conflict attribute, so no gate saw this. What the policy needs: a basis that means the same on every node, someone who can see every accepted fact to decide, a conflict that is a fact so every node shows the same one and a command can close it, and a reduce in which a retract removes a value. (c) A set of tags: a many-valued attribute, or an entity per member

vivief: :many with an OR-Set.

[I1  item/tag  "urgent"  tx1  assert]
[I1  item/tag  "fragile" tx2  assert]
[I1  item/tag  "urgent"  tx3  retract]
-> item I1 tags: { "fragile" }

A new dimension on every attribute (one or many), a new reduce, and a typed read model that cannot hold it in a column: a set needs its own table (D121 Attribute value types, I66 Attribute value types and the typed reference read model). If a tag later needs data of its own (a colour, a note), the attribute must become entities: a migration, which D44' Never rename, never migrate, the RPC too forbids.

Ours today: an entity per member.

[O1/L1/I1/T{urgent}
   item-tag/added "1" tx1 assert]
[O1/L1/I1/T{fragile}
   item-tag/added "1" tx2 assert]
[O1/L1/I1/T{urgent}
   item-tag/added "1" tx3 retract]
-> tags under I1: { fragile }

A tag is an entity under its item by strict composition, its id derived from the tag (D120 Minted and derived id segments), its defining attribute LWW. Two phones adding "urgent" write the same entity; adding and removing it concurrently resolves by time. This is how membership already works (O{org}/M{person}, viviefs/membership/granted). A member gains attributes later with nothing to migrate, and the typed read model has one table per type as it does today.

Reading. Both converge. The OR-Set's one advantage is add-wins: an add concurrent with a remove of the same tag survives, where the entity's LWW picks the later. For tags and members that is rarely what matters, and an entity per member never needs a migration. Q4.

(d) A note edited on two phones: LWW, human conflict, or a CRDT

An inspector writes a paragraph about item I1 on phone A, offline; a colleague edits the same note on phone B. Hypothetical: no attribute holds long text today.

PolicyWhat the people seeWhat it costs
LWWThe later edit wins whole; the other's paragraph is gone with no notice.Nothing. Wrong for a person's work: "user work is never silently lost" (D15 Server authority after a lost lease).
Human conflictBoth versions shown, a person merges them by hand and saves one.Nothing new once Q2-Q3 are built. Fine when concurrent edits are rare, as offline edits of one note are.
CRDT (Loro)Both edits merged character by character, no prompt.A text value that is not a value: either the CRDT's updates are stored in the log as opaque facts and every reader runs Loro to read the text, or the text lives beside the log on its own channel (vivief's ContainerRef), a second sync protocol. Reading. A CRDT pays off when two people type in one text at the same time, live. Edits made apart, offline, are what a human conflict is for. Q5.

(e) An offline phone overtaken under the journal fence (I11)

An inspection run W1; its head is h3, the start of activity "photo". Phone A goes offline. A person asks phone B to continue W1: B writes h4b (photo exit) and h5b (seal start) and seals item I1 "gold". Meanwhile A, offline, does its own steps. A's outbox, in order:

Reading. The journal fence refuses engine facts only. User content travels in domain changesets, which pass or fail on their own, so a refused history strands no user content as long as an activity never keeps user content only in its journal value (an activity that captures a photo writes it as a domain changeset and returns its id). What is stranded is user content inside a changeset authority rejected for another reason, here a write-once collision. The device already keeps it: the rejected outbox row holds the whole changeset, and the blob is local. Quarantine is showing those rows to a person, who resubmits the content through a command (here, E10 as a new evidence item on I1) or discards it, and keeping their blobs until then. It is device-local: the changeset never reached the log, so there is nothing for a conflict fact in the log to point at. Q7 and I11's comment.

8. Q4 explained: one value or many

Cardinality is how many values one attribute of one entity holds at the same time. A list has one title. An item can have several tags; a team has several members; a photo can show several people. Q4 asks how ViViEfs writes "several", and whether the catalog needs a field that says "this attribute holds many values".

Three ways to write "item I1 is tagged urgent and fragile"

1. One value that is a list

[I1 item/tags
  '["urgent","fragile"]'
  tx1 assert]

One LWW attribute whose value Schema is an array (D121 Attribute value types allows it). Every change writes the whole list again.

2. A many-valued attribute

[I1 item/tag
  "urgent" tx1 assert]
[I1 item/tag
  "fragile" tx2 assert]

vivief's :many, as in Datomic. The catalog says cardinality: 'many'; each value is added or removed on its own, the later of its assert and retract winning (Q3's reduce, with no conflict).

3. An entity per member

[O1/L1/I1/T{urgent}

Each tag is an entity under its item (strict composition, D38 Entity ids and strict composition), its id segment derived from the tag (D120 Minted and derived id segments), its defining attribute LWW. No new catalog field. A SQL database does the same with a join table.

What the table shows

  • Shape 1 is out for anything two people may change: it loses a concurrent add (s1). A list value is still right where a value is always replaced whole by one writer, such as the corners of a drawn area.
  • Shapes 2 and 3 sync the same way (s1, s2, s3, s6): a value's later assert or retract wins in 2, the member's defining attribute's later fact wins in 3. They differ only in where a member lives, a value on its owner or an entity of its own.
  • That difference decides s4, s5, s7 and s8. Shape 2 is less to declare for a plain set of labels. Shape 3 grows without a migration, needs no second reduce or side table, and is what membership already is.

A rule of thumb, like D38's

D38 says "can it ever move? then it is a reference". The same kind of rule here: "is it a set? then it is entities", because whether a member will ever carry data of its own (s4) is rarely known on the day the set is designed, and the wrong guess cannot be migrated away.

Effect has no concept to name here (D135 Effect's names first): Schema.Array is shape 1, one value.

9. Q7 explained: what quarantine keeps

The promise. D15 Server authority after a lost lease: "User content (photos, recordings, drafts) is never dropped; it is quarantined for human resolution." I11 Quarantine of user content after a lost lease says there is no mechanism yet, and P14 Quarantine after a lost lease will show one. D15 was written for the lease: a phone that lost its lease drops its journal entries and replays the server's. Under the journal fence (D14' The journal is the fence) the same event is a refused history. Q7 asks what, then, is at risk and what quarantine holds.

Why not I11's first direction

I11 said "a human-conflict entry resolved by a command". After Q2, a conflict is a fact in the log that names values in the log. The rejected photo is not in the log, so a conflict fact would point at something no other device holds.

Revoked access is a special case

When the rejection is MembershipMissing, "keep as new evidence" cannot go back to that organization. What a phone keeps after its membership is revoked is I17 Local deletion after a revoked membership's to decide; quarantine follows it.

Glossary (Data section)

**Basis**:
The point a change was made from: how far its writer had caught up with the
server. The server cursor the writer had pulled; authority uses it at accept to
notice that someone else changed the same thing since ([D34']).

**Conflict policy**:
The rule for what happens when two people change the same thing at once. Per
attribute: last writer wins (LWW), write-once fenced, or human conflict, decided
by authority when the change is accepted. An attribute holds one value; a set
is entities, one per member ([D144]).

**Conflict datom**:
A note that two people changed the same thing and a person must choose. Written
by authority under the human-conflict policy, in the same step as the change it
found; a resolving command closes it.

**Quarantine**:   (new, after Conflict datom)
A person's work in a change the server refused, such as a photo sent with a seal
someone else set first, kept on their phone until they keep it as new or throw
it away. The user content of a rejected changeset, kept on the device with its
blobs until a person resolves it ([D148]).
_Avoid_: lost lease

No new word clashes: "conflict" agrees with Effect's EventLog (D135). Cardinality is not adopted, so it gets no entry.
