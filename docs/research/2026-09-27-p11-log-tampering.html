Who can tamper with the datom log, and what stops them

The datom log is our one audit trail (ADR-0006). This page maps every place it could be changed by someone who shouldn't, what defends it today, what P11 adds, and what we deliberately leave for later. It also covers the two small things we fix now so that "later" stays possible.

The whole answer in four sentences
  1. Devices are untrusted by design. The server re-validates everything a device sends, so tampering on a device only fools that device.
  2. P11 closes "who". After P11 every accepted changeset has a server-checked author and a server-stamped acceptance time (Q14).
  3. The server's stored history is trusted but not provable. A database admin could edit it, and nobody would notice. That is fine for the lab, but not for an app that makes audit claims.
  4. Tamper-evidence is deferred (Q15) until the first consumer app makes audit claims. Two rules keep it possible: never compact the server log, and keep P13's crypto-shredding compatible with a hash chain.

1. The map: where the log lives and where it can be touched

There is one log, with copies in several places. Devices hold a replica of their organization. The server holds the authoritative copy. Data moves up through Append and down through Pull. Each red marker T1-T5 is a place someone could tamper, and the next section's table explains each one.

Above the validation box: already safe by design

Anything a device or the network does must pass the server's checks before it becomes part of the authoritative log. That is D18 and server authority (ADR-0016): the server accepts or rejects a whole changeset, and never "fixes it up".

Below the validation box: trusted, not provable

Once a changeset is in Postgres, nothing checks it again. Devices believe what Pull returns. Someone with database access (T4) could rewrite history, and every device would faithfully replicate the rewrite.

2. The threat table

#Who, and an exampleDefence todayAfter P11Still open
T1 A user on their own device. Roots the phone and edits the local SQLite: inserts datoms, rewrites history, changes a title. safe The server never reads the device's log. It only sees changesets the device pushes, and re-validates each one. Same, plus: anything pushed is attributed to the signed-in person (Q7, Q8). The tampered device misleads only its own user. Nothing re-checks a local copy against the server.
T2 A client sending crafted changesets. Claims to be another user, writes into another org, or adds itself (or an outsider) as a member. partial Only the org prefix is checked, against a client-supplied org. closed Token, membership and actor checks. Plus a new rule: membership and person attributes are server-only, and a client changeset that touches them is rejected (see section 5). -
T3 The network. Someone between device and server changes a payload or steals a token. partial The manifest hash detects altered or missing changeset members. Bearer tokens are short-lived (about 5 minutes). The lab runs plain HTTP. TLS belongs to production hosting, which is already a deferred decision.
T4 The server operator, a DB admin, or a restored backup. Edits or deletes rows directly in Postgres. none Devices trust whatever the server sends. Unchanged. Tamper-evidence of stored history (Q15: deferred, with two constraints).
T5 The clock. A device claims a tx time in the past: "I recorded this evidence yesterday". partial The HLC rejects times more than 5 s in the future. The past is unbounded, as it must be for offline work. closed for audit The server stamps its own acceptance time on every changeset (Q14). The device's time stays a claim, which is still useful as "when the user did it offline".
Lesson from complyj (its ADR-0005): "Local application immutability is not tamper-proof storage against a privileged host or database administrator. Record that limitation without claiming commercial compliance guarantees." T4 is that limitation. We record it the same way, and don't pretend otherwise.

3. Walkthrough: a tampered device tries four things

Mallory is a real member of org acme and has rooted her phone. After P11, here is what each attempt achieves.

sequenceDiagram
  autonumber
  participant M as Mallory's device (tampered)
  participant S as Server validation
  participant L as Server log
  M->>M: edit local SQLite: rename list to "approved"
  Note over M: only her own screen shows it, nothing is sent
  M->>S: Append, envelope.actor = "alice"
  S-->>M: ActorMismatch (actor must be Mallory's person entity)
  M->>S: Append adds membership for outsider "eve"
  S-->>M: rejected: membership attributes are server-only
  M->>S: Append, actor = Mallory, tx time = last week
  S->>L: accept, stamped acceptedAt = now
  S-->>M: AppendAck
  Note over L: history shows: Mallory, claims last week, server received today

The last case is not an attack the server can refuse. Offline devices really do write in the past. What matters is that the log keeps both facts, so an auditor can see the gap between "claimed" and "received".

4. Three properties people call "tamper-proof"

"Tamper-proof" usually hides three different guarantees. They have very different costs, and we treat them separately.

1. Server authority

P11

Guarantee: nothing enters the log unless the server checked who sent it and that it is allowed.

Stops: T1, T2, most of T5.

Cost: already paid (P09 plus P11).

2. Tamper-evidence

deferred

Guarantee: if accepted history is changed afterwards, someone can detect it. It doesn't prevent the change; it makes it visible.

Stops: silent T4.

Cost: moderate. A hash chain on the server, plus checkpoints that devices keep and compare.

3. Proof of authorship

only if needed

Guarantee: even the server operator cannot forge a user's action. Each device signs its changesets with its own key.

Stops: a hostile operator inventing "Alice approved this".

Cost: high. Per-device keys, rotation, lost phones, key attestation.

Order of need: most business apps need only 1. Audit and compliance apps (GRC) need 1 and 2. Only apps that must hold up against their own operator (for example, legal evidence where the operator is a party) need 3.

6. How a hash chain would work (future direction)

This section only teaches the idea so the constraints in section 7 make sense. It is not designed yet. The design happens in its own grilling before the first audit app (Q15).

Every accepted changeset gets a link: link n = H(link n-1 + manifest n + envelope n + acceptedAt n), a hash of the previous link plus this changeset's content. We already compute a manifest hash per changeset (libs/datom/src/manifest.ts, hashMembers), so that is the natural input. Because each link includes the previous one, changing any old changeset changes every link after it.

flowchart LR
  G["genesis<br/>link 0"]
  C1["cs 1<br/>link 1 = H(link 0, cs 1)"]
  C2["cs 2<br/>link 2 = H(link 1, cs 2)"]
  C3["cs 3<br/>link 3 = H(link 2, cs 3)"]
  CP(["Device keeps checkpoint:<br/>at cs 3 the link was abc123"])
  G --> C1 --> C2 --> C3
  C3 -.-> CP

Now an admin edits changeset 2 directly in Postgres:

sequenceDiagram
  autonumber
  participant A as DB admin
  participant P as Postgres
  participant D as Device with checkpoint
  A->>P: UPDATE cs 2 (change a value)
  Note over P: link 2 no longer matches, so link 3 no longer matches
  D->>P: Pull, recompute links up to cs 3
  P-->>D: data + links
  D->>D: recomputed link 3 != checkpoint abc123
  Note over D: tampering detected: report it, do not trust this history

The admin could also recompute every later link, but then the links no longer match the checkpoints devices already hold. That is why checkpoints must live outside the server's control: on devices, or later in an external timestamping service.

7. Two rules we fix now, so "later" stays possible

Rule 1: never compact the server log

LogStore.compact() deletes datoms up to the horizon (DELETE FROM datoms WHERE seq <= horizon). On a device that is fine, because the server keeps everything. On the server it would delete the history a future chain has to cover, and the audit trail ADR-0006 promises.

Nothing compacts the server today. This makes it a stated rule instead of an accident. It holds until tamper-evidence is decided; the decision may later allow compaction that keeps the manifests and links.

Rule 2: P13 stays chain-compatible

Crypto-shredding (D51, P13) erases a person by destroying their key. The ciphertext stays, and "the log stays intact". A chain that hashes plaintext would have to be broken or rewritten to erase someone. A chain that hashes the stored ciphertext stays valid after erasure.

So P13 hashes exactly what is stored. This becomes a design input for P13's grilling.

9. Check yourself

Mallory edits her local SQLite so a list shows "approved". Does anyone else see it?

No. Only what she pushes reaches the server, and a direct SQLite edit isn't in her outbox. If she crafts a push instead, it is validated and attributed to her, like any other change she makes.

Would a hash chain have stopped the DB admin from editing a row?

No, it only makes the edit detectable. Tamper-evidence is not tamper-prevention. Prevention against someone with database access is not possible in software alone; detection is what an auditor needs.

Why add the server acceptance time now if the hash chain waits?

A chain can be computed later over existing history, as long as that history still exists (Rule 1). An acceptance time cannot be recovered later: nobody can know afterwards when old changesets arrived. So the part that can't be added later goes in now.

Why must checkpoints live on devices and not only on the server?

Someone who can edit the server's rows can also recompute the server's links. A checkpoint is only useful if the tamperer can't change it, so it has to live outside their control.

A member adds an outsider to their org by pushing a membership datom. What stops it?

The server-only attribute rule (section 5). Membership changes come only from server-authored commands, and who may call those is decided in round 3.
