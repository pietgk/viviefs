Attribute value types and the typed reference read model

I66 Attribute value types and the typed reference read model builds D121 Attribute value types: every attribute gets a value Schema in the catalog, and the reference read model gets typed columns. Before the build started test first, this page put four things to the human: the layout, what a typed row shows while an attribute is in conflict, whether "required" is declared now, and what declares a value. Your challenge from this morning (the log keeps one table and a text v; the Schema carries the type, a description, a range and what is required) holds throughout.

Answered

Round 3 (2026-10-30): Q1-Q4, all A, as recommended. Recorded as D209 The value is an Effect Schema, D210 The row store and the columnar copy differ, D211 A typed row while an attribute is in conflict and D212 Required comes with its check. The DuckDB and TanStack DB findings are comments on I63 The columnar copy as a Presenter implementation.

The page in six lines

  • The log does not change: one datoms table, v as text, no column or table per value type.
  • Each attribute's value is an Effect Schema: its type, range and description. The text in v and each column type are derived from it with Effect's own tools (section 1, round 2; round 1's nine value types are withdrawn).
  • Measured in SQLite at the planning volume of 10M datoms: one wide table is 3.4x bigger and 3x slower than one table per entity type at 400 attributes, and 20x the size and 20x slower to read by id at 1500 (section 3).
  • So the row store reference and the columnar copy should not make the same choice. A wide row costs SQLite a byte for every empty column; Parquet stores the same empty columns almost for free (Q1).
  • One column holds one value, but under D34' Per-attribute conflict policies, decided at accept an attribute in conflict holds two (Q2).
  • The range is part of the value Schema, so it is checked when the attribute's value is checked. "Required" is an acceptance rule with nothing to check it before I69 Accept checks every change (Q3).

1. What an attribute declares (round 2: Effect's Schema, nothing of our own)

Your challenge (round 2)

Effect's Schema already does what round 1's nine value types did, so inventing a second way to declare a type is wrong. Round 1's closed set (Value.text, Value.integer and the rest) is withdrawn. Everything below was checked against effect 4.0.5 in this repo.

The columnar side targets Arrow types instead of one engine's names: Parquet, DuckDB and Polars all read and write Arrow, so one mapping serves whichever I63 The columnar copy as a Presenter implementation picks. Two things Effect does not keep: a brand is gone from the representation (a reference is a String, which is TEXT anyway), and Effect has no calendar-date Schema (a date is a String with a pattern check, TEXT). Effect's effect/schema/Model was looked at too: it builds select, insert and update variants for tables an app writes, is marked unstable, and creates no tables, so it does not fit a derived read model.

A value that does not decode

The projector rejects the changeset, the way it already rejects an unknown attribute or a second write to a write-once attribute. It is deterministic, so every sync node rejects the same changeset. This is the value Schema's positive control in the changesets suite. Checking on accept, so that the writer hears of it, is I69 Accept checks every change's, as already decided (D125 Acceptance rules).

2. From the log to a typed row

A worked example with the evidence catalog. The log and projected_facts keep the text; the typed table holds the decoded value, one row per visible entity.

datoms (the log, unchanged)
 e              a                 v                     op      cs
 O1/L1/I3       evidence/item         1                 assert  …
 O1/L1/I3       evidence/item/title   Photo of the meter assert …
 O1/L1/I3       evidence/item/seal    s-81              assert  …

projected_facts (unchanged: every fact version with its commit order; the projector reduces it)

rm_item (new, one table per entity type, columns from the catalog)
 e         "evidence/item"  "evidence/item/title"  "evidence/item/seal"
 O1/L1/I3  1                Photo of the meter     s-81
  • Column names are the attribute names, quoted ("evidence/item/title"), so no second name is invented. SQLite, Postgres and DuckDB all accept a quoted name with /. The table is rm_ plus the entity type's name.
  • Visibility as today (ADR-0010 Entity ids, defining attributes and strict-composition prefixes): a row exists only while its entity is visible. Retracting a list's defining attribute removes the rows of its items and of the evidence they own, in the same transaction.
  • Updated incrementally in the projector's transaction (D37 Log store tables). The rows of every entity a changeset touches are rewritten, plus every entity whose visibility depends on a touched one.
  • Rebuilt, never migrated (D44 Never rename, never migrate): the read model stores a fingerprint of the catalog's tables. When an attribute is added, the fingerprint differs on start, so the typed tables are dropped, created again and rebuilt from the log.
  • The conformance claim the changesets suite gains: the typed rows after any sequence of incremental projections equal the rows a full rebuild gives, and equal the rows derived in memory from the visible facts (D110 The reference implementation). P05 Changesets and projections and P08 UI three-way prototype are run again on it.
  • Reading: the projector gets rows(type, query), returning decoded typed rows for the committed or the draft view, filtered by prefix. That is the reference read model a Presenter will read once one is built (D107 The Presenter pattern, not built yet). facts(query) stays for the sync probes and the suite.

3. The measurement

A throwaway benchmark (Node 22's built-in SQLite 3.51.3, WAL, one transaction per build) with 20 entity types and 8 values set per entity. Layout A is one table per entity type; layout B is one table for all types with an entity_type column and a partial index per type. A Presenter selects only its type's columns in both. Layout C, one table per organization, has B's row layout, so in SQLite it costs what B costs, per organization.

Why: a SQLite record has a header byte for every column, empty or not, so at 400 attributes each row of B carries about 380 bytes of empty columns (500 MB over 1.25M entities, which is the measured gap). A range filter on B scans those wide rows. Postgres keeps a null bitmap, one bit per column, so its cost for B is smaller, but A is no worse there. Parquet stores an empty column chunk almost for free and reads only the columns a query names, which is why I63 The columnar copy as a Presenter implementation's one wide table per organization is right for the columnar copy and wrong for the row store.

Round 2: would Polars DataFrames be the better option?

Agreed first: a column per attribute across all types pays off only in a columnar engine (Parquet, DuckDB and DuckLake, Polars). That is the columnar copy, not the row store reference. Where Polars could sit:

  • Not as the reference. The reference must run on every sync node (D110 The reference implementation), phones on Hermes included. nodejs-polars (0.26.1, Polars 0.55.2) is a Rust N-API addon; its README says it is "intended to work only with server-side JS/TS (Node, Bun, Deno)" and sends the browser to js-polars. There is no official iOS or Android build, and Polars' own WebAssembly builds have open issues (for example pola-rs/polars#25857). A DataFrame is also held in memory and rebuilt, not updated in the projector's transaction the way D37 Log store tables asks.
  • Yes as a candidate for the columnar copy, on the server: I63 The columnar copy as a Presenter implementation already lists DuckDB, Polars and Arrow as its engines (merged from I31 Ideas batch: DataFrames as a universal data format). Polars has a point in its favour there: its lazy expressions are a typed query in code, which is what D108 The query is data translates, without going through a SQL string. DuckDB has wider reach (a WebAssembly build, and a community React Native package) and DuckLake's catalog. I63 measures them; I66 only has to give both their column types, which the Arrow column above does.

Read on 2026-10-29: github.com/pola-rs/nodejs-polars (README, releases, Cargo.toml) and the pola-rs/polars WebAssembly issues. npm refused the request.

Round 3: DuckDB on the device, and TanStack DB

You tested react-native-duckdb in your fork: the suite is green on the iOS simulator (155) and the Android emulator (164, release build), not yet on a physical device, on DuckDB 1.4.5 and React Native 0.82.1. DuckDB 2.0 and Expo SDK 58 are work in progress. Unlike Polars, DuckDB is a database with transactions and a durable file, so a column store per organization could live on the phone. The same data and queries in DuckDB, one wide table with an entity_type column and a unique index on the id:

Your idea holds on storage: the file does not grow with the catalog (162 MB at 1500 attributes, against SQLite's 5,881 MB for one wide table). What a screen and the projector do most is 40 to 50x slower than the SQLite tables: reading by id or by parent, and updating a row. The analytical query is already ahead, on only 62,500 rows; a query over a whole organization should widen the gap, but that was not measured. Measured on this Mac with @duckdb/node-api 2.0.0-r.1, not on a phone. A throwaway script, not qualification evidence.

A single transaction cannot span a SQLite log and a DuckDB file, so D37 Log store tables's "same transaction" cannot hold for DuckDB. As a copy derived from a cursor, which is what I63 The columnar copy as a Presenter implementation already says, it needs no such transaction.

TanStack DB (1.0 RC1 announced 2026-10-29; its README and docs badge still say beta; MIT) is a reactive client store: typed collections in memory, live queries kept up to date incrementally by d2ts, and optimistic writes. It maps onto what is decided here:

  • Live queries are a named candidate already. D110 The reference implementation and I63 both name D2TS for keeping answers up to date. TanStack DB is that candidate, packaged.
  • A custom collection per entity type fits this layout: its sync function gets begin, write, commit and markReady, so the projector's changed rows flow in. The source behind a collection can be the SQLite read model, DuckDB on the device, or another sync node. A frame from another sync node has the status remote (D109 Frame and frame subscription); data kept for offline use still lands in the local log (D114 Partial sync on demand).
  • Reads only. Its optimistic writes would be a second write path beside commands and the log, and a second draft view beside "committed plus my open changesets". A collection would have no onInsert: writes stay commands, changesets and the log, and open changesets reach the collection as rows.
  • Memory. Collections live in the JavaScript heap, so a phone can hold what screens use (on-demand mode), not an organization's whole log.
  • Beside query atoms, not instead of them. D42 Live reads with query atoms is qualified; TanStack DB would be a declared Presenter implementation (D113 Who chooses the implementation), adopted when a frame subscription's rerun misses its budget. Hermes is not mentioned in its docs, so a run on Hermes comes first.
  • One idea to take now. Its "test oracles", an independent small model recomputing each answer, are what section 2's conformance claim does. The changesets suite can check the typed rows that way.

4. Questions

Q1. The reference read model's layout

I66 asked the reference and the columnar copy to make the same choice. The measurement says the engines want different layouts, and both still return the same frames: the columnar copy gives a view per entity type, so D110 The reference implementation's check holds.

Q2. A typed row while an attribute is in conflict

Two devices replace evidence/file on the same evidence concurrently; under D34' Per-attribute conflict policies, decided at accept both values stay until a command resolves it. projected_facts keeps both either way, and the conflict is in projection_conflicts.

Q3. "Required" on the attribute

You listed what is required as part of an attribute's Schema. Required is an acceptance rule (D125 Acceptance rules), and D125 fails verify on a rule without a positive control. Nothing can be a positive control for required before I69 Accept checks every change's rule runner exists. The range is different: it is in the value Schema, so the projector checks it from the start.
