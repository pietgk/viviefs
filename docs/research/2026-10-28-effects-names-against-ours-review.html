The entries, recommended

**Workflow engine**:
The part that runs workflows and keeps their journals, the same on every device and on the server.
Our datom-backed implementation of Effect's `WorkflowEngine`
([ADR-0012]).
_Not_: a JavaScript engine such as Hermes, or a database engine.
_Avoid_: engine (alone, our word until D18x)

**Workflow runner**:
A program on a device or on the server that runs the workflow engine.
The process that hosts a workflow engine and runs workflow executions;
today the app on each device and one on the server. Server scale-out
is more workflow runners writing on each run's journal head ([I8]).
_Like_: Temporal's worker or an Effect Cluster runner, except that a
device runs one too and the journal, not a shard, fences it
([ADR-0036]).
_Not_: Effect's `workers/Worker`, a worker thread such as the OPFS
worker the web log store runs SQLite in.
_Avoid_: worker (our word until D18x), runner (alone)

**Durable deferred**:
A point where a workflow waits for something from outside, such as a person's approval.
A durable wait completed from outside (a person, the server, a
notification action): Effect's `DurableDeferred`; its completion is
journaled under `viviefs/deferred/exit`.
_Not_: Effect's `Deferred`, an in-memory cell completed once and
gone after a restart.
_Avoid_: deferred (alone, our word until D18x)

**Journal**:
The record of what a workflow run has done so far, so it can carry on after a restart.
(precise part as today)
_Like_: Temporal's event history, except that it is facts in the same
log as the data, and it fences the run ([ADR-0036]).
_Not_: Effect's `EventJournal`, which stores a whole event log; the
log is never called a journal.
_Avoid_: history, event history

Why not the alternatives

  • Engine with a _Not_ line: 323 bare uses would stay short, but "the engine" in a React Native repo also reads as Hermes, and Effect already has the compound we mean (D135 Effect's names first). The lib is already libs/workflow-engine and the gates say "Workflow engine crash matrix".
  • Worker kept as Temporal's word: our own code already uses worker for the OPFS web worker, and Effect's Worker is a thread. Temporal's worker is the only one that means ours, and it appears in three lists.
  • Workflow engine only, no runner term: possible; prose would say "a server running the workflow engine". But I8, ADR-0036 and the vision page speak of several runners on one journal head, and need a noun.
  • Deferred with a _Not_ line: Effect names ours DurableDeferred and its own Deferred is used in our code's upstream issue; Durable clock already follows DurableClock. The pinned viviefs/deferred/exit stays (D44).
  • Journal as a compound ("run journal"): Effect's workflow module never says journal, and ADR-0036's title, D14' and D39' all use it; the risk runs the other way (calling the log a journal), which the _Not_ line names.

4. Origin, Intent, actor, Envelope: the bare word stays

Three platform words share their core with ours, so D170 keeps the bare word and asks only for a _Like_ line. Envelope does not share its core, but its name is in the sync RPC, which never renames.

Origin: the web's origin is the same idea, narrower

A browser decides what a script may do by where it came from: its origin, scheme, host and port. We decide how far to trust a change's content by where it came from: its origin (D115 Origin trust). Provenance as the basis for trust is the shared core.

_Like_: the web's origin, except that ours names any source
of content (a person, a mail account, a website, a model), is
recorded on each changeset, and how far it is trusted can change.

A website as an origin is then the web's origin in our sense too, which is the example that helps most.

Intent: Android's Intent is the same idea

Android: an Intent is "an abstract description of an operation to be performed", which another component carries out. Ours: what someone asks to happen, which a command checks (D167).

_Like_: Android's `Intent`, except that ours comes from a person,
an agent or an outside source, and a command checks it before
anything is written.

actor: an audit log's actor, not the actor model's

GitHub's actor and audit logs generally mean who did it: our sense. The actor model's actor (Akka, Erlang, vivief) is a process with a mailbox, which D136 mapped to a workflow run. No library our code uses names an actor (effect-machine has none; Effect's source mentions the word three times in prose).

_Like_: an audit log's actor, such as GitHub's `actor`, except
that authority checked it before accepting the change.
_Not_: the actor model's actor (vivief's, Akka's), which here is
a workflow run ([D136]).
_Avoid_: Actor as an entity or type name, author

Envelope: a different core, a pinned name

Effect uses envelope for a transport wrapper in three places; it carries the message and lives for one delivery. Ours carries no datoms, is stored per changeset for good, and is named in the sync RPC (D44'), so a compound would split prose from code for good. Both carry the same trace fields, which is why the mark matters.

_Not_: Effect's `Envelope` (Cluster) and RPC message envelopes,
which wrap one message in transit.

5. Manifest and Cursor: compounds

Changeset manifest

Ours is only ever a changeset's. The app shell (P12 UI on every platform) is next in the Schedule, and it will need the web app manifest and Expo's manifests in their own sense. Expo's update manifest shares our core (a list of the parts and their hashes, applied only when all are there); the web app manifest does not (an app's name and icons).

**Changeset manifest**:
The packing list of a changeset: how many facts and files it has, so nothing is applied half.
The count and hash of its members (and file references) that must
be satisfied before it is applied.
_Like_: Expo's update manifest, except that it lists one changeset's
facts and files, not an app update's assets.
_Not_: the web app manifest, which names an installable web app.
_Avoid_: manifest (alone, our word until D18x)

ADR-0008: "commit datom arrives, carrying a manifest its changeset manifest (count + hash of members ..."

Sync cursor

The bare word means two of ours today (the entry says "Not the trace cursor"), and the docs site links "Cursor" the editor to our entry (I26's observed case). A compound joins the family that already exists: sync cursor, trace cursor, and acknowledged cursor for what both are.

**Sync cursor**:
A bookmark: how far a device has caught up with the server's list of changes.
The server sequence position a replica has confirmed; first sync
keeps one sync cursor per organization. It is an acknowledged
cursor, as the trace cursor is.
_Like_: a database or paging cursor, except that it is stored and
moves only when the device confirms what it received.
_Avoid_: cursor (alone, our word until D18x)

Start here, Sync: "[Outbox], [Cursor Sync cursor], [Conflict datom]"

The bare word with marks instead

Manifest: 38 uses, all changeset ones; a _Like_ and a _Not_ line would do today, until the app shell's pages say "manifest" in Expo's sense next to ours. Cursor: a _Like_ line and the heading in lower case ("cursor", as "actor" and "effect" are) would stop the editor's link, but would leave our two cursors on one bare word.

6. Tool and prompt

Tool: D102's app keeps the word

Plain English "tool" (something you use to do work) is D102's sense; Effect's Tool is a narrow technical one, and the code imports nothing from effect/ai. tools/ is a project kind (D52), and verify and qualify are called tools throughout. Effect's sense is written as a compound: "a model's tool".

**Tool**:
An app for the people and agents who build apps, such as the checks run before every merge.
An app whose users are the people and agents building apps, often
run from the command line or in CI: `verify`, `qualify`, the
generators, `exercise` ([D102]). It lives in `tools/`, a project
kind no product app depends on ([D52]); it is an app but not a
`node` ([D103]).
_Not_: Effect's `Tool`, an operation a model may call, written "a
model's tool"; `verify` offered to an agent over MCP is both.

D134's "an agent reads a frame through a tool" is a decision row and stays as written; no living document repeats it.

Prompt: not a term

Effect itself has three prompts: ai/Prompt (every message a model receives: system, history, tool results), an MCP prompt (a named template a server offers) and cli/Prompt (a terminal question). D132's "a prompt" is a person's request to an agent, one user message inside Effect's Prompt. Every living use is plain English (a hook "on every prompt", OIDC's prompt=login).

Recommended: bare "prompt" never becomes a term; I92 Map 2's new words, which names the kinds of intent, names this one with that constraint (for example "a request to an agent").

Tool the other way round

Give Effect's sense the bare word and D102's a compound ("builder tool"). Agents and their docs say tool for a model's tool all day, and map 6 brings tool calls into the journal. Cost: tools/ and the project kind keep the old word in every path, and plain English already says tool for verify.

Effect has no word for an entity type that acts, since every Cluster Entity acts; ours has one kind that acts, the workflow run (an execution). Recommended: no word until a second kind acts; "a workflow run" says it.
