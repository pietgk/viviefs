1. Definitions (revised)

Each term answers one question. A file treatment is about a file; a suite is about a pattern's contract.

What changed since round 1
  • Treatment becomes file treatment. Agreed: the name then says what it is attached to, so nobody speaks of a project's or a suite's treatment. In code the type is FileTreatment; inside a registry entry the field is treatment.
  • Suite names were implicit, and mixed three schemes: by gate ("P09 host checks"), by port ("token verifier conformance"), by technique ("crash matrix"). Now one scheme: <pattern>/<aspect>, declared once in code.
  • Suites and patterns: checked below against every suite in the repo. They do not overlap; they nest. Each suite checks one aspect of exactly one pattern's contract. The glossary already says so in other words ("an implementation is qualified by running the pattern's conformance probe").
  • "Engine suites" is a grouping, not a term. The three suites libs/workflow-engine runs belong to three patterns (durable workflow, device durability, tracing); what they share is the implementation under test.

File treatment

Answers: for this file, which verify step produces its evidence, and which verdict judges it?

How one production file's behaviour is shown in verify: the verify step that produces the evidence and the verdict applied to it. Every production file has exactly one, with a written rationale, in the registry. Replaces the per-project evidence owner.

Example: libs/datom/src/hlc.ts has file treatment node-unit: the unit step, judged by an exact coverage tuple.

Avoid: treatment (alone), evidence owner, coverage owner.

Suite

Answers: which aspect of which pattern's contract was checked, against which implementations?

The executable form of one aspect of a pattern's contract: a named set of checks, written once, run against each implementation of that contract, with a positive control that must fail it. A pattern has one or more suites; a suite belongs to exactly one pattern. The same suite function runs in a verify step as a check and in a gate's probe as the claim (D70).

Named <pattern>/<aspect>, for example log-store/conformance, durable-workflow/crash-matrix. The pattern slug is the one its guide's pattern frontmatter uses (D63).

Avoid: conformance probe (a probe is what a gate runs; it calls suites), test suite (a Vitest file), host checks.

Verify step, producer

A verify step is one named unit of a verify stage (typecheck, unit, docs...), from the stage table in tools/verify/src/stages.ts. "Step" alone stays reserved for gate steps (P11.6). A producer is a verify step that executes code and emits a coverage map and a test report: today unit, integration, storybook.

Verdict

The rule a file treatment applies to what its step produced. Five kinds: exact coverage (the file's tuple equals the lockfile), stories ran (every story passed with axe), reached (at least one statement ran), statically checked (the file's shape, for example only re-exports), gate named (the named gate is in the gate table; verify does not read the ledger, D63).

Exact coverage tuple, owning producer

For one file and one producer: covered and total statements, branches, functions and lines. The owning producer is the one its file treatment names; only its tuple is judged. Another producer reaching the file is informational: it can neither fail nor rescue the verdict (web-interview ADR 010).

Registry, evidence lockfile

The registry is the one list of file, file treatment, rationale, suites, reviewed by a human; filesystem rules only discover files. The evidence lockfile is machine-written by pnpm verify baseline: owned tuples per producer, provider name and version, the registry digest, and the bundle-size references.

Two things this surfaces. (1) Two suites (sync/protocol, identity/membership) have one implementation today. They are still suites: they check a pattern's contract, and a second implementation would run the same checks. Their functions are named after the gate (runP09, runP11Node) and live in tools/qualification, not libs/testing; renaming them is part of this step, moving them is a question for the sync and identity guides. (2) A gate can call several suites (P10 calls three), and a suite's gate is where its claim is recorded, not its name.

How a suite is named and checked

  • Each suite is declared once in code: { id, pattern, aspect, gate } next to its function. The id is <pattern>/<aspect>; the pattern slug is from a fixed list (D65's patterns), later checked against the guides' pattern frontmatter.
  • A test that runs a suite tags itself with the suite id; a registry entry names suite ids. verify fails on an unknown id, on an entry naming a suite that has no passing tagged test in the owning producer, and on a declared suite no test runs (except a lab-only one such as tracing/sink, which names its gate instead).

Why a suite is not a file treatment: they are two axes

A suite is checked against files whose file treatment is a coverage treatment; the suite's own files are test-support. One file can be checked by several suites, and one suite checks files in several projects.

2. Producers, projects and Nx today

Each producer step asks Nx to run one target over the projects that declare it. Each target is vitest run in the project's own directory, cached by Nx on default and ^production inputs, with no declared outputs. Locally the scope is nx affected; in CI it is nx run-many --all.

3. How unit and integration produce evidence

The registry, verdicts and lockfile are the same in all three. What differs is how each step's one coverage map comes about, and what counts as evidence. B is the only option that changes what counts.

Recommended now

A: one root run per step

A root Vitest config lists the projects whose project.json declares test (or test-integration), each with its own environment. One process, one map.

Pros

  • Fewest moving parts: no merge, no cached coverage whose correctness depends on Nx inputs.
  • Cross-project evidence counts.
  • Measured the same time as a full run today (about 30 s both steps).

Cons

  • No Nx cache or affected for these two steps: every local verify runs all of them.
  • Two ways to run a project's tests: the root run (verify) and nx run datom:test (by hand). Same tests and configs, so they cannot disagree on results, only on scope.
  • Cost grows with every tested project (exercise tracks will add several).
Changes what counts

B: per project, own files only

Today's Nx targets, each also measuring coverage of its own project's files. A file is proven only by tests in its own project.

Pros

  • Nx affected and cache unchanged; no merge.
  • Evidence sits next to the code it proves.

Cons

  • 14 files, about 2,500 lines, lose their evidence today. Getting it back means new tests in those projects that repeat what the P09 and P11 host checks and the token contract already prove: layers that permanently overlap (D48', web-interview ADR 005).
  • A conformance suite run from a store project would not count for the engine, and so on: suites stop working as shared evidence.
Upgrade path from A

C: per project, workspace coverage, merged

Today's Nx targets with Vitest's root at the workspace. Each writes its coverage as a declared Nx output; the step runs run-many --all so unchanged projects replay from cache, then merges.

Pros

  • Cross-project evidence counts.
  • Nx stays the one way to run tests; a change reruns only what it affects.
  • Scales with the number of projects.

Cons

  • Evidence is only as right as each target's Nx inputs. Example today: p09.test.ts reads committed evidence notes that are not in its inputs, so a stale cached pass is possible.
  • A merge step (union of hits, drop unreached entries), and affected becomes run-many --all for these steps.
  • More code in tools/verify to maintain.

Recommendation: A now. It is the simplest thing that is right, costs no measurable time today, and does not rest evidence on cache correctness. Move to C when the two steps pass a stated threshold (proposal: one minute on a full run, in line with D70's "a host-only check over a minute needs a reason"); only the step's assembly changes. B is not recommended because it discards cross-project evidence and pushes toward duplicate tests.
