Effect and the effect handler

I88 Effect and the effect handler is the first ticket of map 3. It tests the charting's draft of effect and effect handler on a command, a workflow step, an activity that calls a model, and Vision - View - Effects, the way D137 One meaning of entity settled entity. Round 1 decides what effect means, the shape of the Vision - View - Effects entry, and the verb decide. Later rounds take effect handler, intent and the formula's names, which depend on round 1.

Answered

Q1-Q3 as recommended (2026-10-28): effect has one meaning, named by phase; Vision - View - Effects is one entry for the phrase; a command decides, marked against DecisionModel.decide. Already in GLOSSARY.md: the Vision - View - Effects entry and the marks on Command and Decision. Round 2 (Q4-Q6) as recommended too: effect handler is a term, the compound; an intent is what someone asks to happen; Effect and effect are two entries, told apart by case (the docs linker now matches case). Round 3 (Q7-Q8) as recommended: no formula with names of its own; I30 narrowed to its fourth form. Recorded as D163-D169; see I88's Answer.

The page in six lines

  1. Your framing holds, with one addition. Effect the library does not use the word in a second meaning: its own docs say "creating an effect does not perform the work", so for Effect, too, an effect is the work that makes a difference; an Effect value is that effect not yet run, and an Exit is how it ended (section 1).
  2. The addition is phase. The draft already uses the word in two phases: the handler's input and outputs are effects asked for, and Vision - View - Effects' Effects is what happened. vivief said the same of the datom: "the distinction is PHASE, not TYPE" (section 2).
  3. Our words already name the phases: asked for (an intent), proposed (a changeset), happened (a fact in the log, an activity's journaled Exit, a span). They line up with D132 Four states at every level: hot, the frontier, warm (section 3).
  4. The four worked examples all fit the reading "one meaning, named by phase", and each strains the draft as written in one place (section 4).
  5. "View" cannot be a term alone: React Native's View is its basic component, and the glossary's Read model already avoids "view". One entry for the whole name is proposed (section 5).
  6. "Effect handler" is a known compound elsewhere: OCaml 5 and Koka call an interpreter that catches a performed effect and resumes the computation an effect handler. That is round 2's question, after round 1 settles effect (section 6).

3. The draft, read as one meaning in phases

The charting's draft (to test, not to adopt)

Effect: Something that happens and makes a difference: a fact written, a message sent, a screen redrawn, a model asked. Effect, the TypeScript library, writes an effect down as a value of its type Effect and runs it later; that describing and running are two steps is how the library works, not another meaning.

Effect handler: A step that takes what is known and an effect that comes in, and decides which effects follow.

The handler line uses "effect" for things that have not happened: the effect that comes in has been asked for, the effects that follow are proposed and can be rejected. The plain sentence uses it for what happens. Both hold if the entry says an effect passes through phases, and names each phase with the word we already have:

The rule this gives a writer: write "effect" alone only where the phase does not matter ("a command has no effect until authority accepts it"); where it matters, write the phase's word.

What is knownThe read model (read.title)
The effect that comes inThe intent: rename this list to this title. Asked for.
What it returnsAn Effect value: described, not yet run. Run, it ends in an Exit: a changeset or a DomainError.
The effects that followThe changeset: two datoms and a commit. Proposed: authority may still reject it (ADR-0035 Accepting a change).
What happenedAfter accept: the facts in the log; the projector evolves the read model; the screen shows the new title.

Where the draft strains: "decides which effects follow" is right if the changeset is an effect proposed. Read with the plain sentence alone ("something that happens"), the changeset has not happened, and the rejected blank-title changeset of I69 Accept checks every change never does. The phase line fixes it.

I78's finding, checked against the reading

"In Effect's own vocabulary an Effect is closer to an intent (what may happen when run) and an Exit is what happened. D98's Effects is the plain English word."

Correct, and it is the phase line: Effect writes the early phase as Effect and the last as Exit. It argues against two meanings, not for them: neither the library nor D98 uses "effect" for something other than a change something causes.

Sketch of the one entry (wording settled after round 1)

Vision - View - Effects: The loop this project runs at every level: what we intend, what we show, and what actually happens. Vision is what we intend and decide (decisions, ADRs, claims); Effects is what actually happened (the log, evidence, traces), the last phase of an effect; View is what a person or agent sees and learns from (guides, diagrams, the app's screens). A gate is one turn, a guide another, a grilling a third (D98, D98'). The three words are not terms alone: View is not React Native's View, and Effects is not the library.

8c. Sketches of the entries (if Q4-Q6 go as recommended)

effect: Something that happens and makes a difference: a fact written, a message sent, a screen redrawn, a model asked. An effect passes through phases, and the stack names each: asked for (an intent), proposed (a changeset), happened (a fact in the log, an activity's journaled exit). Effect, the library, writes an effect down as a value of its type Effect before it runs and calls how it ended an Exit; that is how the library carries one effect through its phases, not another meaning. Write effect alone only where the phase does not matter. A read makes no difference, so it is not an effect.

Effect handler: A step that takes what is known and an effect asked for, and decides which effects follow, without making them happen. A command is one (a read model and an intent in, a changeset or a DomainError out), authority's accept another, and a workflow body a third, over its journal. Reads and pure helpers are not. Like Elm's update, except what it returns is proposed and counts only once accepted. vivief's effectHandler, in this form (D130, D136). Not an effect handler of algebraic effects (OCaml 5, Koka), which resumes a paused computation; Effect has no effect handler, and a handler alone is Effect's: the code behind a declared operation.

Intent: What someone asks to happen, before it is checked: a person, an agent or an outside source. An effect in its first phase; the input to a command; not a datom. A clock firing, a sync arriving or an activity's exit is not an intent.

Effect (the library): The TypeScript library this whole stack is written with ... (as today), plus: An Effect value is an effect described, not yet run; see effect.
