The page in six lines

  1. All five of vivief's concepts have already landed, each in a ViViEfs form, by I49-I56: Datom stands, Projection's read side is the Presenter, Surface is "a surface of any modality", Contract is accepting a change, effectHandler is the shape at the data level and the durable workflow (section 1).
  2. What has not landed is the closed set. vivief says five concepts model everything and the rest are patterns that compose them. ViViEfs has it the other way round: an open set of patterns, each with a contract, a suite and a gate, and a concept lives inside one pattern's guide (D82). D125 already refused vivief's closed set of six contract sub-types for the same reason (section 2).
  3. Proposal: ADR-0032 gains one table, its foundation concepts: twelve rows, each with a plain sentence, what it came from in vivief, the decisions, the pattern that owns it and the gate that shows it or the issue that will (section 3).
  4. Libs stay one per pattern and implementation; the table's pattern column, with each lib's metadata.guides, is how code maps to the concepts (section 4).
  5. Portability: the lock-in half is ours already (one contract, several implementations, one suite). The newcomer half, "you may know it as", goes to map 3 as a glossary line, tested by I21 in map 4 (section 5).
  6. 98 of the 101 rows have a disposition; the three missing are this ticket's own. ADR-0032 is intent with no gate, so "accepted" needs a ruling: D65 already accepts 0001 and 0002 directly (section 6). Questions in section 7.

Ideas worth keeping, checked

  • One small set a newcomer can hold in their head. vivief's strongest teaching move. Kept by the proposal in section 3: one table, read top to bottom as one loop.
  • "Spec, test and runtime guard at once." Kept: an acceptance rule is declared once, has a positive control in a suite, and runs on the device and with authority (D125).
  • The composition table (§10): "Datom + Schema Contract = validated facts", "Projection + Surface = rendered output". Kept in spirit by D82's "builds on": a pattern relies on another's promises. Not kept as a closed algebra.
  • "Concept vs. pattern" (domain, bridge, artifact, slice, profile, skill are patterns). The word clash is vivief:concept-vs-pattern's, on map 3. Its content is settled: a domain is a consumer app (D106), a bridge is a boundary with an origin (D129), a skill is an implementation strategy (D132).
  • "The system gets more deterministic over time." vivief:deterministic-first, map 6. Not touched here.

A candidate with a contract code depends on, a suite and a gate is a pattern; otherwise it is a concept, taught in one pattern's guide.

So "foundation concept" on this map means an idea the P01-P10 stage built on, not D82's narrower "concept" (an idea with no contract of its own). Most foundation concepts are owned by a pattern; some are patterns themselves. D125 already refused vivief's closed set of six contract sub-types because "D82 keeps that set open". The same argument applies to the five: closing the set would make a new pattern (access, the Presenter, both added by map 2) a breach of the model rather than the normal way the stack grows.

What is worth taking from the closed set is its size: a newcomer reads one short list, in one order, and knows the whole loop. Section 3 keeps that without closing anything.

Read as one turn

A command (3) decides a changeset of datoms (2), named by its origin (7); authority accepts it (4), having asked access (10), and chains it (12); sync (9) carries it to every device; the projector builds read models (5); a Presenter answers a screen with a frame (6). Long work runs as a workflow (8) whose journal is in the same log. Each of these is a pattern (1), so each can be done another way that passes the same suite.

One lib per pattern's core, one per implementation (each store), tagged by layer and platform (D52-D54). A guide adds its pattern id to metadata.guides in the commit that creates it (D84), so only the log store's libs carry one yet.

The difference that matters: vivief puts each concept in one package; here a pattern's implementations are separate libs because each runs on a different platform (the four stores) and the boundary lint decides what may import what. Grouping by concept would put op-sqlite and Postgres in one package. vivief's goal, that the code says the concepts, is met by the pattern id (guide folder, suite prefix, metadata.guides, D82) and by the table's "owning pattern" column. The four patterns map 2 added (Presenter, origin trust, access, the hash chain) get their libs when phase 3 builds them.

5. Portability: two halves

vivief v6 §6: "Every vivief concept maps to a conventional equivalent. Bidirectional. Read-only snapshots proving portability. A Projection maps to a SQL view, an effectHandler to an Express route, a Contract to a JSON Schema + integration test. The proof that every concept has a conventional equivalent reduces perceived lock-in."

Lock-in: ours already, stronger

Here the claim is not "it maps to something conventional" but "it runs on something conventional, under the same suite": the log store on SQLite (three drivers) and Postgres, proven by P04; the Presenter's reference implementation is plain SQLite read models every other must agree with (D110). The final choice is the pattern, implementations stay free (D123). Disposition proposed: keep ours.

Newcomers: not done anywhere yet

The glossary's Avoid lines say which word not to use, not what a newcomer may already know. A "like X, except Y" line would let a developer from elsewhere place a term in one read. It is a glossary line, so it belongs to map 3, and whether it helps is map 4's question (I21, a reader outside software). Disposition proposed: hand to map 3.

Worked example: what such lines would say

The "except" column is the point: a bare "Read model = materialized view" would teach the wrong thing (a view is not rebuilt from a log). That risk is why a reader test (I21) should judge it, not this ticket.

6. The 101 rows, and what "accepted" means for ADR-0032

Row check (a script over the inventory's "Map 2: Foundation (101)" and every issue's Answer)

  • 98 of 101 rows appear in an Answer of I47-I59. The three that do not are I55's own: vivief:five-concepts, vivief:concept-aligned-packages, vivief:portability.
  • Six inventory lines carry two ids (a vivief row and a ViViEfs row of the same comparison); each is disposed under its first id, the second named in the same line where it matters (vivief:peer-validation-as-contract handed from I53 to I54, settled there).
  • Two rows were disposed twice, on purpose: I47 deferred viviefs:changeset and vivief:fractal-factory to I56, and I56 settled them. The later Answer is the disposition.

"Accepted" has a rule that does not fit this ADR

The ADR index: "Accepted is a human status given on the pattern's guide ..., not on the decision alone" (ADR-0026, amended 2026-09-29). The glossary's Accepted: "An ADR is accepted on its pattern's guide." ADR-0032 is intent, qualifying gate "none", and belongs to no pattern. But D65 already makes an exception: "0001 and 0002 are accepted directly." Neither has been yet; both are still Proposed, unverified.

The map's destination says "the human has accepted one foundation ADR". Proposal: ADR-0032 is accepted directly, as D65 does for 0001 and 0002; D65 and the glossary's Accepted entry say so for intent records; the ADRs it links (0033-0038) keep their own status, each waiting on its gate and guide. ADR-0002 could be accepted in the same walk, since I59 just brought it in line.
