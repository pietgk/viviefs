How a request proves who sent it

Names on this page predate the naming pass (Q20). The code uses:
  • Principal is now Caller (person, provider account, roles)
  • AuthMiddleware / Authenticated is now BearerAuthentication (rpc.ts)
  • Authenticator is now TokenVerifier, returning a ProviderAccount (token-verifier.ts)
  • The device-side Identity is now SignInSession
  • Unauthenticated is now TokenRejected; NotMember is now MembershipMissing
The code sketches below show the shape; the linked files are the truth. See the P11 design review for every decision.

Q5 answers one question: when a device calls the server, how does the server know which person is calling, and how is that fact handed to the code that decides what they may do? This page builds the answer from the ground up: the parts, the token, the three flows, the code, and what each check stops.

The whole answer in four sentences
  1. The device signs in at Keycloak once and gets a short-lived access token, a signed JSON document that says "this is user sub".
  2. On every RPC call, a small piece of client middleware puts that token in the HTTP header authorization: Bearer <token>.
  3. On the server, AuthMiddleware checks the token's signature with Keycloak's public keys (fetched once and cached), plus its issuer, audience and expiry. It then hands a verified Principal to the handler.
  4. The handler never reads identity from the payload. It asks "is this Principal a member of the org it asked for?" (Q2, Q3), then does the work or returns a typed rejection.

1. Today (P09) vs after P11

In P09 the device and server ran in one Node process and talked through RpcTest, an in-memory pipe with no network and no HTTP headers. Every RPC payload carries org, and the server takes it at face value. That was fine for proving replication. It is exactly what D18 forbids in production.

Today trusts the client

  • Transport: RpcTest.makeClient(SyncRpcs), in-process (p09-checks.ts:175).
  • Who is calling? Unknown. Nothing on the wire says.
  • { org: "acme", ... } is believed. The server only checks that entity ids start with Oacme/, and that is a consistency check, not an access check.
  • envelope.actor is whatever the client wrote.
  • PutBlob does no membership check, and blobs.has(hash) is global.
  • apps/evidence-server is an empty slot.

After P11 server decides

  • Transport: real HTTP. apps/evidence-server runs RpcServer.layerHttp on Node, and the device uses RpcClient.layerProtocolHttp.
  • Who is calling? A verified Principal (iss + sub) from a checked token.
  • org becomes a selector: "I want to act in acme". The server checks membership before touching anything (Q3). Failing returns NotMember.
  • envelope.actor must equal the Principal (Q7).
  • Blobs are keyed per org, and PutBlob and CompleteDeferred go through the same middleware.
Why a real transport matters for this gate: the token travels in an HTTP header. With an in-memory pipe there is no header, so "the server checks the token" would be a test of a fake path. P11 has to exercise the path a phone actually uses.

2. The parts and how they connect

There are three places: the device, Keycloak (the identity provider, running in Apple Container on your Mac), and the evidence server (Node). The numbered arrows are the three flows the rest of this page explains.

Flow 1 - sign in

Rare: once, then silent refreshes. The user sees a Keycloak login page. The output is tokens stored on the device. Q6 decided this runs on iOS, Android and web.

Flow 2 - every call

Frequent: every push, pull, blob upload and command. The token rides along in a header. This is what Q5 is about.

Flow 3 - public keys

Rare: the server fetches Keycloak's public keys once and caches them. Checking a token is then local maths with no network call. This is the "locally against JWKS" part of Q5.

Keycloak is not on the path of every call. The server never asks Keycloak "is this token OK?" per request. It checks the signature itself. Section 10 covers why.

4. Inside an access token

A JWT is three base64url strings joined by dots. The first two are plain JSON that anyone can decode (try jwt.io). The third is a signature over the first two, made with Keycloak's private key. Change one character of the payload and the signature no longer matches.

eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxIn0.eyJpc3MiOiJodHRwOi8vbG9jYWxob3N0OjgwODAvcmVhbG1zL3ZpdmllZnMiLCJhdWQiOiJ2aXZpZWZzLXN5bmMiLCJzdWIiOiI3ZjNjLi4uIiwiZXhwIjoxNzkwMDAwMzAwfQ.Qm9ndXMtc2lnbmF0dXJlLWZvci10ZWFjaGluZy1vbmx5LW5vdC1yZWFs...

Illustrative token, shortened. Not a real signature.

Header

{
  "alg": "RS256",
  "kid": "k1"
}

alg: how it was signed. We only accept RS256, so an attacker cannot pick none.
kid: which of Keycloak's keys signed it. It selects the key from the JWKS.

Payload (claims)

{
  "iss": "http://localhost:8080/realms/viviefs",
  "aud": "viviefs-sync",
  "sub": "7f3c...",
  "exp": 1790000300,
  "iat": 1790000000
}

Each claim is checked (next table). sub is the stable user id: it becomes Principal.subject.

Signature

RSA-SHA256 over header.payload with Keycloak's private key. The server checks it with the matching public key from the JWKS.

Public key: can only check. Private key: can sign, and never leaves Keycloak.

ClaimWhat the server checksQuestion it answers
signatureValid under a key in Keycloak's JWKS, with alg RS256Did our IdP really issue this, unaltered?
issExactly http://localhost:8080/realms/viviefsIs it from our realm, not another realm or IdP?
audContains viviefs-syncWas it issued for this server, not for some other app using the same Keycloak?
exp / nbfNow is inside the validity window, with small clock toleranceIs it still fresh? This limits the damage of a leaked token.
subPresent. It becomes the Principal.Who is it?
Two Keycloak details P11 must get right (facts, not choices)
  • Audience: by default a Keycloak access token does not name our API in aud. Measured in P11 step 5: without a mapper, Keycloak 26.7.3 left aud out entirely (it can also say account, depending on scopes). The realm needs an audience mapper so tokens carry viviefs-sync. Without it the aud check either always fails or gets switched off, and switching it off is the classic mistake.
  • Issuer: iss is the URL the device used to reach Keycloak. The Android emulator normally reaches your Mac as 10.0.2.2 and iOS as localhost, which would give two different issuers. The fix (Q6) is a fixed KC_HOSTNAME=localhost:8080 plus adb reverse tcp:8080 tcp:8080, so every platform sees one issuer.

5. Where the token comes from (flow 1, PKCE)

Q5 is about using the token, but it helps to see where the token comes from. A mobile app cannot keep a secret: anyone can unpack the app binary. PKCE replaces the secret with a one-time random value that only the app instance which started the login knows.

sequenceDiagram
  autonumber
  participant App as Evidence app (Identity)
  participant Br as System browser sheet
  participant KC as Keycloak
  participant SS as Secure store
  App->>App: verifier = random 43+ chars, challenge = SHA256(verifier)
  App->>Br: open /auth?client_id, redirect_uri, code_challenge
  Br->>KC: user types username and password
  KC-->>App: redirect viviefs://auth?code=XYZ (one-time code)
  App->>KC: POST /token code=XYZ + verifier
  Note over KC: SHA256(verifier) == challenge? Only the original app knows verifier.
  KC-->>App: access_token (about 5 min), refresh_token, id_token
  App->>SS: keep refresh_token (Keychain / Keystore)

If another app intercepts code=XYZ (for example by registering the same URL scheme), it still cannot trade the code for tokens, because it does not have verifier. That is the whole point of PKCE.

6. What happens on every call (flow 2, the heart of Q5)

Follow one push("acme") from the app to the log and back. Steps 1-4 happen on the device, 5-8 in the server middleware, and 9-12 in the handler.

And when the token is bad, the handler never runs:

sequenceDiagram
  autonumber
  participant CM as Client middleware
  participant AM as AuthMiddleware (server)
  participant AU as Authenticator
  participant H as Append handler
  CM->>AM: authorization: Bearer (expired, forged, wrong aud...)
  AM->>AU: verify(token)
  AU-->>AM: fails
  AM-->>CM: Unauthenticated { reason }
  Note over H: never invoked, so nothing reads or writes the log

Why middleware and not a check in each handler?

If every handler had to remember yield* checkToken(...), one forgotten line would be an open door. With middleware attached to the whole RpcGroup, a handler cannot run unauthenticated, and adding a new RPC to the group makes it protected by default.

Why does the handler still check membership?

The middleware answers who. Only the handler knows what is being asked: which org, which execution's lease, which actor on the envelope. Authorization needs that context, so it lives next to the other server-side validation in server.ts.

7. Public keys and caching (flow 3)

To check a signature, the server needs Keycloak's public key. It fetches the JWKS the first time, keeps it in memory, and after that verifies with no network call. When Keycloak rotates keys, new tokens carry a new kid. The server does not know that key yet, so it re-fetches once. jose's createRemoteJWKSet does all of this, including a cooldown so a flood of bad kids cannot make the server hammer Keycloak.

sequenceDiagram
  autonumber
  participant AU as Authenticator (server)
  participant C as In-memory key cache
  participant KC as Keycloak
  AU->>C: key for kid k1?
  C-->>AU: miss
  AU->>KC: GET /realms/viviefs/protocol/openid-connect/certs
  KC-->>AU: { keys: [ { kid: k1, n, e } ] }
  AU->>C: store k1
  Note over AU,C: next thousands of calls: hit, no network
  AU->>C: key for kid k2? (Keycloak rotated)
  C-->>AU: miss
  AU->>KC: GET .../certs (at most once per cooldown)
  KC-->>AU: { keys: [k1, k2] }
Consequence: if Keycloak goes down, already-signed-in devices keep syncing until their access token expires (about 5 minutes). After that, refresh fails and calls get Unauthenticated. Local work keeps going into the outbox (offline-first is unchanged) and syncs once sign-in works again. Exact expiry and offline behaviour is a next-round question.

10. Why this design (the choices inside Q5)

Local verification (JWKS)

chosen
  • No network call per request, so it is fast.
  • The server keeps working through short Keycloak outages.
  • Works with any OIDC provider unchanged (D47).
  • Cost: a revoked token stays valid until exp. We don't care: membership is checked per request from the log (Q2), so revoking access is immediate anyway.

Introspection

rejected
  • The server asks Keycloak "is this token active?" on every call.
  • One more network hop per request. Keycloak becomes a hard runtime dependency of sync.
  • Its one advantage (instant token revocation) is already covered by per-request membership.

Hand-written WebCrypto

rejected
  • Feasible: crypto.subtle.verify plus base64url parsing.
  • But JWT validation is a well-known source of security bugs: alg confusion, kid handling, clock skew, key caching and rotation.
  • jose 6.2.12: MIT, zero dependencies, widely audited, runs on Node, browsers and edge runtimes.
Other choice inside Q5PickReason
Where the token travelsHTTP authorization headerStandard. Keeps identity out of RPC payload schemas, so the payload stays about the domain.
Session cookie vs bearer tokenBearercomplyj used server sessions with cookies for a browser. A native app has no cookie jar we want to rely on, and bearer works the same on iOS, Android and web.
Where auth is enforcedMiddleware on the whole SyncRpcs groupProtected by default. A new RPC cannot be added unprotected by accident.
What handlers receivePrincipal via Effect contextIdentity is a service in the type, like LogStore. Handlers cannot see raw tokens.
HTTP vs WebSocketHTTP nowOne request, one header, one check. WebSocket later only if live push is needed.

11. Where the fake identity fits (link to Q4)

Q4 chose a fake that issues real JWTs signed with a local key. Seen through Q5, the reason is clear: the fake replaces only the top of the picture (who signs tokens and where the public key comes from). Everything from the HTTP header down (middleware, jose verification, Principal, membership) is the same code in both setups.

12. Check yourself

Try to answer before opening each one.

Alice has a valid token but is not in org acme. She sends Append { org: "acme" }. Does the middleware let her through?

Yes. The middleware only answers "who is this?", and she really is Alice. The handler then rejects with NotMember. Authentication passed, authorization failed. If you expected the middleware to stop her, that is the one distinction worth remembering from this page.

Why doesn't the device need jose?

The device only carries the token. It never decides whether a token is valid; that is the server's job. So there is no JWT library in the Hermes bundle, which also helps the 10 MB bundle budget.

Bob's membership is removed at 10:00. His access token is valid until 10:04. What happens to his push at 10:01?

Rejected with NotMember. The token is still valid, so authentication passes. But membership is read from the log on every request (Q2), not from the token. This is why local verification's weakness (tokens can't be revoked early) doesn't matter here.

Someone copies a Keycloak token issued for a different app in our realm (say, an admin console). Which check stops it?

aud. The signature and iss are genuine; it really is from our Keycloak. But it was issued for another audience. That is also why the realm needs the audience mapper (section 4).

Keycloak is down for 10 minutes. Does a signed-in device keep syncing?

For a few minutes, yes. The server has the keys cached and the access token is still valid. Once the token expires, the device can't refresh, so calls get Unauthenticated. Local writes continue into the outbox and sync once Keycloak is back. How the app shows this is a next-round question.

A developer adds a new RPC ListMembers to SyncRpcs and forgets auth. What happens?

Nothing bad: the middleware is on the group, so the new RPC is authenticated automatically, and its handler can yield* Principal. They still have to write the membership check. That part can't be generic, which is why the P11 probe asserts it per RPC.

Why can't the P11 probe keep using RpcTest like P09?

There are no HTTP headers in an in-memory pipe, and no network between a simulator and a server. The gate says "PKCE from the simulator; membership enforced on sync". That needs the phone to send a real header to a real server. Node-only checks can still use the same layers for speed, but the gate's device checks go over HTTP.
