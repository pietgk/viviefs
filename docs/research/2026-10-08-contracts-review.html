What we might learn

  • Data rules and access rules are different things. AWS keeps "may this principal do this action" (IAM) apart from "is this resource state allowed" (Config). Our Q1 rules are the second; who may write is the first, and belongs with I54 and I16.
  • The case for policy as data is analysis, not change at run time. D118 rejected rules as datoms because vivief wanted to change them live. Cedar's reason is different: you can prove what a policy allows. That is a real argument for access policies, and it is not answered yet.
  • Explicit deny, default deny is the evaluation rule every one of these systems converged on.

The rabbit hole

  • IAM serves thousands of services and millions of accounts; permission boundaries, session policies, SCPs and resource policies each exist because of a scale we do not have. Copying its shape gives an app builder a policy language before they have two roles.
  • Designing our own policy language is the deepest part. If one is ever needed, Cedar exists, is open source and is typed against a schema.
  • The boundary: I50 decides data rules. Access is I54 (who may read), I16 (roles in use) and I15 (identity and keys).

Round 4: one checkpoint, and access as a pattern

The elegance, in our words

vivief got its elegance from one concept that runs everywhere. We can get the same from one place every change passes, which the glossary already names: authority "accepts or rejects every change".

Every check is declared once, runs early on the device and with authority on accept, and has a positive control in a suite. Preventive on accept, detective after it: the split AWS draws between IAM and Config.

Access as a pattern: minimal now, enterprise later, one contract

Not crazy: it is how I49 treated the Presenter (a reference implementation, then others checked against it) and what D123 says (the pattern is the final choice; implementations stay free). And unlike acceptance rules, access has real implementations to swap, so by D82 it would be a pattern.

// the contract (sketch): one question, asked by accept and by sync
decide({ subject, action, resource, context }) -> Allow | Deny(reason)

// action:   the command's name (Q9: every domain write names one)
// resource: the entities the changeset touches, with their attributes
// context:  organization, device, origin, time

4. policies    Cedar (open source, typed by a schema, provable by analysis)     enterprise

Why it could work

  • The four-part request (subject, action, resource, context) is the common shape of Cedar, OPA and OpenFGA checks, and of the OpenID AuthZEN Authorization API, a standard for exactly this separation. To be confirmed by the research record.
  • Q9 gives every write an action name, Q14 a declared set of attributes: the reference implementation is mostly already there.
  • D105 (2): the check must run on any node; code runs anywhere, and Cedar has a WebAssembly build.

Where it could go wrong

  • The contract is fixed once a gate proves it (D123). Shaped too small, Cedar does not fit later; shaped for Cedar, the reference carries fields nobody uses.
  • Analysis ("who can approve?") exists only in declarative implementations; the contract cannot promise it.
  • Reads: what a replica receives is also an access decision (I54), so the same contract must serve sync's filter, not only accept.

Setting the stage: four ways to answer "may this writer do this?"

All four answer the same request. The OpenID AuthZEN Authorization API 1.0, a Final Specification since 2026-01-12, standardizes its shape: subject (type, id), action (name), resource (type, id), optional context, answered with a boolean decision. The checker is the policy decision point (PDP); the code that asks and enforces is the policy enforcement point (PEP). In ViViEfs, accept and sync would be the PEPs.

{ "subject":  { "type": "person", "id": "P42" },
  "action":   { "name": "evidence.approveItem" },
  "resource": { "type": "item", "id": "O1/L1/I7" },
  "context":  { "org": "O1", "device": "D3", "origin": "P42" } }
-> { "decision": false, "context": { "reason": "reviewer is the author" } }

1. Code (our reference, today)

Membership, authority: 'server' and, with Q14, a command's declared writes. Fast, typed, runs on any node. Nobody can ask it "who may approve?" without reading the code.

2. Roles (I16)

A person holds a role in an organization ("reviewer"); a command names the roles that may run it. Still code, plus role datoms beside the membership datom.

3. Relations, Zanzibar-style

Google's Zanzibar (USENIX ATC 2019) stores every permission as a relation tuple, object#relation@user, where the user may itself be a set: object#relation. Its paper's examples: doc:readme#owner@10, group:eng#member@11, doc:readme#viewer@group:eng#member ("members of group:eng are viewers of doc:readme"). A per-namespace configuration adds userset rewrites: "every editor is also a viewer", "a document's viewers include its folder's viewers". A check asks "does user U have relation R to object O?" by walking those sets. OpenFGA and SpiceDB are open-source systems in this style.

In our domain, a tuple is nearly a datom [e a v]:
  item:O1/L1/I7#reviewer@person:P42           reviewer of one item
  list:O1/L1#editor@org:O1#member              every member of O1 edits list L1
  O1/membership/P42  viviefs/membership/granted  ...   (already one, today)

The lesson for us, from the paper: the new enemy problem. Alice removes Bob from a document, then adds new content; a check that reads an access list older than the content lets Bob see it. Zanzibar's answer is a consistency token, the zookie, stored with the content, so a check is never older than the change it guards. Today our one authority orders membership and content in one log, so accept always checks against current state and the problem cannot arise. With several nodes (I60) it can, and the zookie's role would be played by a tx: "check as of at least this tx".

When it pays: sharing per entity (this list with that person, that folder with a group), nested groups, and "list everything P42 can see".

4. Policies, Cedar

Cedar is AWS's open-source policy language (behind Amazon Verified Permissions). A request has a principal, an action, a resource and a context; policies are permit or forbid with optional when conditions over entity attributes. Its rules, from its documentation: default deny ("no request is authorized unless there is a specific permit policy that grants it"), forbid overrides permit, and a policy whose evaluation errors is skipped. An optional schema types entities and actions so policies are validated against the app's data, and because the language is small and decidable, tools can prove what a set of policies allows. A WebAssembly build (@cedar-policy/cedar-wasm) runs it in JavaScript.

// independent review, in our domain (sketch)
permit (
  principal in Role::"reviewer",
  action == Action::"evidence.approveItem",
  resource
) when { resource.author != principal };

// no agent grants membership, whatever its role
forbid (principal is Agent, action == Action::"membership.grant", resource);

When it pays: many roles and conditions, auditors who must see the rules apart from the code, and questions like "can anyone outside O1 read this?" answered by analysis.

What the explainers changed: where independent review belongs

The Q1 sketch put independent review among acceptance rules. Cedar writes it as an access policy, and that is the better line: a rule that names the writer ("the reviewer is not the author") answers question 1, may this writer do this; a rule about the data alone ("a title is not blank") answers question 3. Both are code in the reference implementation, so nothing is built twice; the line only decides which pattern owns a rule and which suite checks it (Q21).

Round 2: who writes, and must it be a command?

Never decided. D36 and ADR-0016 say "one write path for app and engine"; no decision says whether a changeset may come from anything other than a command. Today four kinds of writer exist or are decided:

So every changeset already names a command, but only some are produced by one.

A. Every writer uses a command

A changeset is always a registered command applied to an intent: screens, agents, enriching activities, the operator. An activity produces an intent ("gathered message M from origin O"), and a command turns it into datoms.

For: one write path in fact, not just in the ADR; the envelope's command always names real code, so "which code wrote this?" has an answer; agents and people use the same verbs (D95); rules about the request (who may approve, unchanged title) have one home; it is what re-running needs.

Against: the engine's journal is infrastructure with no domain rule, so wrapping each fact is ceremony; every enriching source needs an intent Schema and a command; commands alone still do not protect the data (a crafted client skips them), so Q1's rules are needed anyway.

B. Every domain writer uses a command; the engine's journal is the durable-workflow pattern's own

As A, with one named exception: journal facts (viviefs/workflow/* and the lease) are written by the engine and checked by its own rules (lease fencing, write-once), which its gate already proves (P06, P09).

For: A's benefits for everything that carries meaning; no ceremony where there is no meaning; the exception is one pattern, with a suite.

Against: one exception to teach; D36 and ADR-0016's "one write path for app and engine" is reworded.

C. Commands serve screens only

Anything may write a changeset; acceptance rules (Q1) are the only guarantee. Commands are a convenience for user requests.

For: least to build; enriching activities write batches freely.

Against: the envelope's command becomes a free label; request rules (who may approve) have no home outside screens; an agent's writes are whatever it assembles; re-running is impossible for most writes.

Re-running the command: valid or crazy?

Valid, and well known. It is the same move as durable execution's replay, and as systems that log commands and re-execute them on every replica.

Durable execution (D2, D10)A command, re-run by authority

Elsewhere: Ethereum validators re-execute every transaction rather than trust its result; VoltDB and Calvin log commands, not results, and replay them on replicas.

What it would buy

  1. Proof the changeset is what the named code makes from that intent: a client cannot claim renameList and also write a seal. (Most of this, cheaper: a command declares which attributes it may write, and authority checks that.)
  2. Re-validation after a rule changes: replay kept intents through the new code to find accepted changesets it would now reject, written as findings (Q2). This is vivief's "tests that never stop running" in our terms.
  3. Debugging: why did this changeset look like this? Run it again.

What it would cost

  • Two meanings, pick one. Verify: re-run on authority's read model as of the client's basis and compare; concurrency stays with basis and conflict policies (D34, D35''). Needs a read as of a cursor, deferred to I63. Rebase: re-run on today's data; equal is accepted, different is rejected. Needs no history, but replaces per-attribute conflict policy with the command's own reads, and a human-conflict attribute (both values kept) no longer behaves as D34 says. Verify keeps the conflict model; rebase changes it.
  • The intent becomes stored data: never renamed (D44 extends to intents), erasable when personal (ADR-0023 crypto-shredding covers it).
  • Command versions ship until drained, exactly as workflow versions do.

It only applies to writes that come from a command, so it waits for the question above.

Already settled

  • The Schema stays code, not datoms. D118 What a datom needs from storage (I52): one Schema per attribute that people, agents and the compiler read the same way. So vivief's "contracts as datoms" is already answered for the Schema part.
  • Every attribute gets a value Schema in the catalog (D121 Attribute value types, built in I66), and uniqueness is an acceptance rule checked by the node holding authority (D122 External identifiers, I68).
  • Acceptance rules must be able to run on any node against a read model (D105 What must stay possible (2)).
  • Where content came from is the origin in the envelope, and its trust is origin trust (D58' Envelope names the origin, D115 Origin trust, I49). This answers most of vivief's intake and asserted-versus-inferred rows.
  • Aggregation (deriving higher-level facts) is a projection or an enriching implementation (D111 Faster and enriching implementations).

So the first decision is not "data or commands" in the abstract. It is: where does a rule live so that the node holding authority checks it on every changeset, including changesets no command wrote (an enriching implementation's, a workflow activity's, an agent's).

Three ideas are in there, and they come apart:

  1. Placement: rules are checked by the one place every write passes through, whatever handler produced it.
  2. Representation: rules are datoms, queryable and changed without a release.
  3. Time: some rules are not about one write but about absence over time ("a session within 7 days"), checked later, with findings recorded.

D118 already rejected (2) for the Schema. The proposal below adopts (1) with rules as code, and handles (3) as an ordinary workflow.

Q1 worked: acceptance rules beside the catalog

A sketch, not a design of the API. Rules are code, declared with the attribute or entity type they constrain, and run by accept on every changeset against the authority's read model. The command calls the same rules, so a client rejects early with the same error the server would give.

// libs/datom catalog entry (sketch)
{ name: Attr.listTitle, policy: 'lww', value: NonBlankText }          // D121 value Schema: "blank title" moves here
{ name: Attr.supplierKvk, policy: 'lww', value: KvkNumber,
  unique: 'per-organization' }                                         // D122 / I68

// an entity-level rule (sketch): read model in, changeset in, finding out
const independentReview: AcceptanceRule = (read, changeset) =>
  approvalIn(changeset)?.reviewer === read.authorOf(approvalIn(changeset).item)
    ? Option.some(new RuleBroken({ rule: 'independent-review' }))
    : Option.none()

// the command keeps only what is specific to the request
export const renameList = (read, intent, mint) =>

Q2 worked: a rule over time is a workflow, not a check on write

"A high-risk client must have a session within 7 days" cannot be broken by one write: it is broken by nothing happening. A write-time rule cannot catch it. In ViViEfs's terms:

flowchart LR
  L[(Log)] -- "client marked high risk" --> W["Workflow: a durable wake-at clock (D24)"]
  W -- "after 7 days: query via a Presenter" --> Q{Session scheduled?}
  Q -- yes --> E[Done]
  Q -- no --> F["Changeset: a finding, origin = the rule"]
  F --> L
  F -.-> S["Screen: findings, a frame subscription"]

The finding is an ordinary changeset with the rule as its origin (D58'), seen through a Presenter, and a person can act on it. Nothing new: a workflow, a durable clock, a changeset. What would be new is a name for the kind of thing ("a standing rule"?) and a guide page; that waits until a consumer app has such a rule.
