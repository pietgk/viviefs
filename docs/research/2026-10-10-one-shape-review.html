One shape at every level?

I56 One shape at every level? asks whether vivief's (State, intent) => (State', [Effects]') describes ViViEfs at every level, and where it stops being useful. I47 What ViViEfs is about left it here on purpose; the human called it "close to an existential level discussion". It settles two rows of the vivief inventory, viviefs:changeset and vivief:fractal-factory, and reviews I30 Ideas batch: glossary entries written as effects and I33 Ideas batch: abstractions that constrain agents. The names (effectHandler, intent, effect) are map 3's; this ticket decides whether the shape is foundation, not what it is called.

The page in five lines

  1. Where the stack keeps the state as data and the code is deterministic (command, accept, projector, workflow, the IntentComposer, the gate ledger), the shape fits cleanly.
  2. At the data level it fits as two functions, not one: a command decides (state and intent to a changeset), the projector evolves (state and changeset to a new state), and accept sits between them. That split is what the code already does, and it answers viviefs:changeset: the changeset is the step, not State'.
  3. Reads (a Presenter's frame, a query atom) and pure helpers are not handlers: they make no new state. vivief drew the same line ("creation boundary").
  4. Above the code (a change and verify, a guide, an agent session, an app improving a part), it fits only as D98 Vision - View - Effects's loop: a person or an agent is in it, and the state is not one value.
  5. Proposed sweet spot: the shape is a foundation concept at the data level, shown by gates that already pass, and a lens for teaching and design above it.

Round 2, settled in conversation (2026-10-23)

  • Q4 B, with C's roles and A's order. Every level has the same four states, named by how settled a thing is: hot, created and open (decide); frontier, the sync, a checkpoint (accept); warm, kept with its history (keep); cold, net truth (derive). The levels are data, decisions, code, claims and patterns, ordered by how long a turn takes. Something cold that someone reads becomes a hot intent at another level. This closes Q3's "ordered by time constant".
  • Q5 At the frontier. Hot is intent creation, prepared for sync and still changeable. The sync (a grilling, accept, verify) is the frontier crossing. This follows vivief ADR 0050's tiers and ADR-0011's compaction horizon.
  • Q6 Recorded, with a new name: "a passing tree" becomes verified commit, a commit on which pnpm verify is green. A commit is to the repository what a changeset is to the log. The verdict gap becomes an issue, Decide when: a gate must know it ran on a verified commit. The word can be revisited in map 3.

Why "verified commit". Three candidates were weighed:

  • "Code changeset" clashes. "Changeset" is a data word, a pinned name (D44), and the glossary uses it only for facts in the log. A second meaning would undo that. So "code changeset" goes into Changeset's _Avoid_.
  • "Merged" or "a passing tree after merge" describes a workflow this repository does not have. Commits land directly on main, with no pull requests, and CI (.github/workflows/ci.yml) runs verify on push.
  • "Verified commit" names what is true: a commit, and verify passed on it. It clashes with GitHub's "Verified" badge, which means a signed commit. The glossary entry says so, and map 3 can revisit the word.

Found for map 3. "Change" has two meanings today: a data changeset in ADR-0035 Accepting a change, and a code change in the glossary's Verify entry ("every change must pass"). This becomes an issue, Decide when: map 3.

3. The loop as a process: vivief:fractal-factory

The inventory row: "the same retrieve, generate, evaluate loop at every scale, from a tool call to the product lifecycle; each cycle's output is the next cycle's callable input, so velocity compounds". Its question: "Is 'the same loop at every scale' part of what ViViEfs is about, and which of its loops (verify per change, a gate per claim, a guide per pattern) would it call one?"

D98 Vision - View - Effects already reads a gate and a guide as turns of one loop: intend, build, observe what happened, show it, check it against the intent. Each box below is one such loop at one level; the arrows are what one level hands to another:

What holds

  • Each level has the three parts of D98, and each turn leaves something kept that the next turn reads: the log, the verdict and the commit, the ledger, the decision, the handover, an issue.
  • The levels feed each other: a learner's finding and an app's gap both come back as warm-loop issues (dotted arrows).
  • vivief's temperature tiers order the levels by their time constants without pretending they are the same code. Corrected in 3b: vivief's tiers measure how settled data is, not how fast a loop turns.

What does not

  • "Callable input": a turn's output is read by the next, not called. Only app data is facts in one log; development artifacts are files, by decision (D129, D48').
  • "Velocity compounds" is a claim no gate can show. Whether an agent builds the next pattern faster from the guides is a question of evidence, which is map 4's.
  • Retrieve, generate, evaluate is a model-in-the-loop reading; the hot loop has no model in it.

3b. Three ways to draw the loop (round 2)

The drawing above mixes axes, as the human saw: hot and warm are named by time, cold by an artifact, coldest by an app. Before redrawing it, two things it got wrong or left open: what vivief's temperatures meant, and what "a passing tree" is (named verified commit in round 2; the drawings below use the new name).

vivief's temperatures measure how settled data is

vivief ADR 0050, "Three temperature tiers":

Tiervivief
HotVersions above the frontier. In memory, actively receiving, no compaction possible.
WarmClosed versions, consolidated and queryable. Each datom is still distinguishable.
FrozenFully compacted. Net state only: an assert and its retract cancel.

So temperature is not speed. It is how far something is from settled. ViViEfs has the same line under another name: "Snapshots and compaction only past a horizon every device has acknowledged" (ADR-0011 Log store pattern, read models, compaction and analytics). The human's "hot is intent creation, prepare for syncing" is closer to vivief than section 3 was.

Verified commit (was "a passing tree")

What exists. GitHub Actions runs pnpm verify (.github/workflows/ci.yml) on every push, and it prints GREEN · n checks or RED. That verdict is kept only in the CI run, not in the repository. pnpm qualify runs "on a committed tree", and each ledger entry records commit and dirty, not whether verify passed.

Definition. A verified commit is a commit on which pnpm verify is green.

Its relation to a changeset. A commit is to the repository what a changeset is to the log: one step, all or nothing. It is prepared in a worktree, as an open changeset waits in an outbox. It crosses a checkpoint: verify asks whether it is well formed and keeps the tree valid, and the human agreeing asks whether this writer may do it. It then lands on main and is kept in main's history, as a changeset is kept in the log, and CI runs verify again. The differences: it is files in git, not datoms (D48' Verify - Qualify - Teach, D129 Boundaries and live change). It can be rewritten before it lands on main, never after. And the checkpoint's verdict is not kept with the commit, while accept's verdict on a changeset is: the changeset is in the log, or there is a typed rejection.

One example, traced in every drawing: a list saved with a blank title. This is real. While deciding I50 Contracts checked as data or by commands, we found that the server accepts a crafted changeset with a blank title, because it never re-runs the command. The fix is I69 Accept checks every change, in phase 3. Steps marked to come have not happened yet.

A. The changeset is State'

It is not a state: it is three facts that mean nothing without the log they join. It can be rejected and never become anything. It is the step between states: vivief v6's datoms, the decider's events.

True of what the command will see next time, but the read model is derived, disposable and rebuilt (D99). Calling it the state makes the thing we throw away the thing we keep.

C. State' is the log after accept (proposed)

The log is the kept state; the changeset is the step a command proposes; accept turns it into State'; the read model is a view of the state, the one a command reads and a screen shows. Facts kept, meaning derived (D99), said in the formula's terms.

With C, the human's framing in I47 ("State can be read as the whole log store plus the output of the active projectors, with a local and a global context") becomes precise: the log is the state, the read models are its views, the device's log is the local context and authority's the global one.

5. The sweet spot (proposed)

Foundation: at the data level

A foundation concept in ADR-0032 What ViViEfs is about and its foundation concepts: every change to kept state goes state and input, to a step, to the next state. A command decides (read model and intent to a changeset, pure, its ids passed in); authority accepts the step into the log; the projector evolves the read models from the log. A workflow is the same over its journal, and an activity is the only place the world comes in, its result kept. Failure is data: a typed error, a rejection, a journaled exit.

Shown by gates that pass: P05 Changesets and projections (atomic steps, the rebuild fold), P06 Workflow engine crash matrix (replay over the journal), P09 Sync (accept). No new gate.

Not handlers: reads (a Presenter's frame, a query atom) and pure helpers.

Lens: above the code

A change and verify, a gate, a guide, an agent session, an app improving a part: each is a turn of D98's loop, with something kept that the next turn reads. Useful for teaching and as a design checklist (what is kept, what is derived, where is the check, where does a person or a model decide). Not a claim, not a function, no gate.

The rabbit hole is calling these handlers: it hides the person, and it invites "everything is a datom" for files the decisions keep out of the log.

ADR-0032: a new paragraph in the Design, after "Accepting a change"

One shape at every level (D130-D135, D98', I56). At the data level, every change to kept state goes from a state and an input, through a step, to the next state: a command decides (a changeset or a typed error, pure, its ids passed in), authority accepts the step into the log, and the projector evolves the read models from it. A workflow runs the same way over its journal, and an activity is the only place the world comes in, its result kept. Failure is data. The changeset is the step; the log after accept is the new state, and read models are its views. Reads and pure helpers make no new state, so they are outside the shape. Shown by P05, P06 and P09. vivief's effectHandler is adopted in this form; its name is map 3's. Above the code the shape is a lens, not a concept: people and agents compose intent, and apps and tools, themselves built from intent, carry it out to reach a goal. At every level (data, decisions, code, claims, patterns) a thing is hot while it is open, crosses a frontier where a checkpoint decides, is kept warm with its history, and turns cold as net truth others build on. Something cold that someone reads becomes a hot intent at another level. Intent comes in kinds from a WayFinder map down to a button press, and the more abstract the intent, the longer its turn. A verified commit, a commit on which pnpm verify is green, is the code level's crossing. A frame reaches a person through a surface of any modality, a screen being one. vivief's fractal factory is adopted as this lens; datoms for development artifacts and "velocity compounds" are not. Where Effect already names a concept, ViViEfs uses Effect's name and meaning.

Glossary

**Verified commit**:
A saved version of the code on which every check passed. A commit on which
`pnpm verify` is green. A commit is to the repository what a changeset is to
the log: one step, prepared in a worktree, checked by verify and agreed by the
human, then kept on `main`, where CI runs verify again. The verdict is kept
only in the CI run. Not GitHub's "Verified" badge, which means a signed commit.
_Avoid_: passing tree, code changeset, merged commit

**Changeset**: (unchanged, except)
_Avoid_: transaction (a datom's own unit), batch, patch, code changeset (a commit)
