I71: an append can land after a revocation

Alice is a member of organization acme. Her phone sends a changeset (renameList) at the same moment the operator revokes her membership. The server's Append handler does two things one after the other, with nothing tying them together: it checks membership, then it appends. Membership writes (grant, revoke) take a lock, but only against each other.

Why it matters

  • Removing someone from an organization should stop their writes. For a few milliseconds, a write already in flight still lands, and the log orders it after the removal, so the log itself says a non-member wrote it.
  • The test holds the append to make the window wide; in real use it is the time accept spends on its reads (transaction lookups, file checks, lease and write-once reads), each a point where a revoke can commit.

How it could be closed (decided with I54, not now)

  • Check where you write: check membership inside the append's transaction, against the state the append commits on (D124's first question, read at the position it appends on).
  • Order them: appends and membership writes for one organization take the same lock, so a revoke waits for an in-flight append or the other way round.
  • Accept the window: document it, as Zanzibar does for a check made just before a revocation.

How the test pins it down

  1. Starts the evidence server's real composition: sync RPCs over HTTP, the PGlite log store the deployed server uses, the real accept, a fake sign-in issuer, memberships granted and revoked by the operator commands.
  2. One test seam: a wrapper around the log store that holds a device's append until the test releases it (the server's own membership writes pass straight through). No sleeps.
  3. Alice's Append goes out over HTTP, passes the membership check and every accept check, and waits at the append (steps 1-4 above).
  4. The test runs revoke to completion (steps 5-7), then releases the append (steps 8-9).
  5. Two tests: a normal one checks the revoke happened and the control is refused (MembershipMissing); a known-bug test (it.live.fails) asserts no datom of the held changeset lands after the revocation. It fails today, so verify stays green; when a fix closes the window it turns red and becomes a normal test.
