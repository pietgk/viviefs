The clock: vivief's ULID against our HLC

vivief: a ULID

01JC8Z4K7M  7Q2V9XR4HN8B3WKD
|-48-bit ms-| |---80 random bits---|
device wall clock, as it is

Coordination-free: any peer mints offline. Last-writer-wins orders by the highest ULID, so a phone whose clock is ten minutes fast wins every conflict for ten minutes.

ViViEfs: an HLC, ULID-shaped

01JC8Z4K7M  0001  A3F9QX2B  7KDE
|-48-bit pt-| |c| |device| |entropy|
pt = corrected time, never below anything seen

Same 26 characters, same sort. The counter c keeps order when time does not advance; a tx more than 5 s ahead is refused (ADR-0007 Hybrid logical clock, P04).

Worked: a phone with a clock 10 minutes fast

Stepvivief ULIDViViEfs HLC
Phone (fast clock) renames the list at 10:00 real timetx says 10:10Device time was corrected against the server at sync: pt says 10:00
Laptop (correct clock) renames it at 10:05tx says 10:05: loses to the earlier editpt says 10:05: wins, as a person expects
Phone offline for days, rebooted, its wall clock now 10 min fast-Its tx is refused on push as future skew; the trace flags it
A wording finding against D105 (1). ADR-0007 says server-corrected time and "Server rejects future skew"; ADR-0011 says "the server's log is never compacted". D105 (1) asks that no ADR assume the holder of authority is a server process. The mechanism does not depend on it: time is corrected against whichever node holds the ordering duty, and that node's log is the audit trail. Only the words change.

Entity ids: a path against a flat ULID

vivief: flat

01JC8Z4K7M7Q2V9XR4HN8B3WKD   a todo
:todo/list   -> 01JC8Y...    its list
:todo/org    -> 01JC80...    its organization

Every relation is an attribute. Nothing about the entity can be read from its id.

ViViEfs: a path for strict composition

Oacme/L1/I2       an item, part of list 1, can never move
Oacme/E9          evidence; its list is a reference attribute
Oacme/W{exec}/A{activity}#{attempt}   a journal entry
A{sha256(iss,sub)}                    server-only account

Prefix scans drive isolation (OrgMismatch), tree deletes, compaction, Reactivity keys, and D114's partial sync on demand.

A gap: nothing decides the local segment. listId(org, list) takes the 1 in Oacme/L1 as an argument; only the suites call it, with '1', '9'. Two phones creating a list offline need segments that never collide. This is where vivief's ULID fits inside our path.

Values: one text column against typed columns

-- vivief (PostgreSQL design, not built)
datoms(e, a, v_type, v_text, v_num, v_bool, v_date, v_ref, v_bytes, v_vec, tx BIGINT, op BOOLEAN, asserted_at)
  + partial AVET indexes per type   "better than JSONB for indexed queries"

-- ViViEfs: who answers "lists with title Q3"?
query (D108)  -> a read model     (typed, rebuilt from the log)
              -> never the log    (the log is read by e, a and cursor only)

Typed columns pay off where values are queried: in read models and, when it is built, the columnar copy (one column per attribute, typed from the catalog, I63). The log is appended, scanned by prefix and streamed by cursor; it is never filtered by value. I19 (op as a boolean) already waits for a storage budget. Settled in round 1: keep ours, on the condition that the Schema knows each attribute's type, so DuckDB and other implementations get a real SQL column type (numeric sort and filter).

Round 2 finding: that condition is not met today. The glossary says an attribute is "Schema-typed", but the catalog does not carry a type: 
// libs/datom/src/catalog.ts
type AttributeSpec = { name; policy: 'lww' | 'write-once' | 'human-conflict'; defining?; authority?: 'server' }
                                          // no value Schema

// libs/datom/src/read-models.ts: the one read model is generic, not typed
projected_facts(e, a, v TEXT, op, cs, commit_tx, member_tx, commit_seq)

-- so "items sorted by quantity" today sorts text:  "10" < "9"
Every exemplar value is text or a reference, so P05 never needed a type. D37's "typed read models" and I63's "typed from the catalog" both assume a type the catalog does not have yet. 
// What it could look like (illustration, not a decision)
{ name: 'acme/item/quantity', policy: 'lww', value: Schema.Int }
//   -> SQLite INTEGER, Postgres BIGINT, DuckDB BIGINT, Parquet INT64   (each implementation maps the Schema)
//   -> v in the log stays text: the Schema's one canonical encoding, "10"

// The reference read model for a type: one typed column per attribute, from the catalog
item(e TEXT PRIMARY KEY, title TEXT, quantity INTEGER, ...)   -- rebuilt on a new attribute, never migrated (D44)

External identifiers

Oacme/S17   acme/supplier/name        "Brouwer BV"
Oacme/S17   acme/supplier/kvk-number  "12345678"     -- an ordinary attribute; travels with S17
A9f3c...    viviefs/account/person    "P42"          -- server-only root; never replicated (ADR-0022)

vivief: an entity carries several external ids as datoms, found through AVET, and they travel with the entity. ViViEfs has one external id today, the provider account, and keeps it server-only because it maps a sign-in to a person. A supplier number is not a credential, so it can be an ordinary attribute; a lookup by value is a read model. Two open points: whether "unique in the organization" is an acceptance rule (D105 (2): a rule any node could run against a read model), and that a national id is personal data, so encrypted per subject (ADR-0023 Data at rest and crypto-shredding).

Settled (rounds 1-3, in conversation, 2026-10-08)

  • D118 What a datom needs from storage. The log store contract; provenance, schema as datoms and a read as of a tx left out on purpose (ADR-0011 "Left out on purpose").
  • D119 Time corrected by authority. The HLC stays, worded for the node holding authority (ADR-0007, ADR-0011, glossary HLC).
  • D120 Minted and derived id segments. Path ids stay; segments minted by the HLC's encoder or derived (ADR-0010; I67; glossary Derived id).
  • D121 Attribute value types. A value Schema per attribute in the catalog; typed columns in the reference read model; layout (per type, or one table under a checked cap below 1600 columns) to I66 with I63.
  • D122 External identifiers. Ordinary attributes; unique: 'per-organization' checked on accept (I68); "organization" means only ViViEfs's isolation unit, a KvK number identifies a company; personal ones encrypted, the blind index noted on I54.
  • D123 The final choice is the pattern. Its contract and conformance check are fixed by a gate; implementations stay free.
