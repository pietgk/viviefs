Map 2, the foundation concepts - I54 2026-10-26, round 1 Design review, not a decision record

Trust, encryption and who may sign in

I54 Trust, encryption and who may sign in asks whether encryption in ViViEfs serves access and consent, as vivief's Trust Contract does, or only erasure and data at rest; whether access is part of each read or a check around sync and commands; and, with the rows moved here from map 6, how people sign in, what an organization and its membership are, what a device is, whether a key authenticates a device apart from membership, and whether stored history can be shown untouched. It settles 11 rows of the vivief inventory (10 of its own and vivief:peer-validation-as-contract, handed over by D146 One checkpoint enforces trust), decides the access pattern I70's research prepared, answers whether an agent may have its own identity (D141 The actor is the accountable identity), and reviews I10, I15, I16, I17 and I18. Effect's eventlog is read first (D135 Effect's names first).

The page in five lines

  1. vivief makes a key the access check: who may read a value is who can derive its key, and consent is a datom whose revocation rotates a key. That works for one counselor with a passphrase. In an organization whose authority must read values to accept a change, it cannot: a rule cannot check what its checker cannot read (vivief's own "trust over structure"), and a rotated key does not recall what was already read.
  2. Proposal: encryption serves erasure and data at rest only; access is a decision, made on authority at two points, accept (what may be written) and sync's filter (what a replica receives), and run early on the device for feedback. Effect's EventLog has the same two points (authorizeWrite, authorizeRead); its encryption is for a server that may not read one owner's log, a different problem.
  3. Access becomes a pattern with today's code as its reference implementation (membership, server-only attributes, a command's declared writes), I70's AuthZEN-shaped request (a changeset is a batch, one evaluation per touched entity), a position the decision read, and "an error denies". Roles, relations and Cedar are later implementations, each triggered by an app.
  4. An agent may get its own identity, an agent account that signs in, holds a membership and is refused what a person may do; built when an app runs an agent that writes on its own.
  5. Keys wait for proof: tamper-evidence first as a hash chain with device-held checkpoints, signed changesets and device keys only when an app needs proof against the operator or a node accepts from a peer. Six findings, one of them that the lease fence trusts a device id nobody authenticates.

1. vivief's trust in one page

Sources (vivief at 3071cb2): docs/contract/vivief-concepts-v6.md §2.2 Projection, §2.4 Contract ("Trust Contract", "Trust over structure"); docs/contract/counseling/platform-v2.md §2.4 Projection Encryption, §6.4 encrypted value design, §12 (4, 5, 8); docs/contract/adr/0047-datom-store-sync.md §9 Identity; docs/contract/datom/architecture.md §11.4 Keypair and Device Linking; docs/contract/vivief-concepts-impl-kb.md §2.3 P2P & Replication.

Access lives in the Projection

A Projection carries capability: CapabilityToken, scope: "own" | "consented" | "all" and decryptionKey?: DerivedKey beside its query. "A capability scope IS a Projection": "client Maria can read her own data" is a filter on client:42 plus Maria's decryption key. "The same query engine that renders Surfaces also enforces access control."

The Trust Contract

derivation:
  "passphrase → PBKDF2 → HKDF per-entity"
roles: {
  owner:      { derives: "all" }
  scopedUser: { derives: "own-entity-only" }
  ai:         { derives: "consented-only",
                constraint: "read + draft-write" }
  system:     { derives: "none",
                sees: "metadata only" }
}
consent: {
  grant:  "datom assertion with why-chain"
  revoke: "retraction → key rotation effect"
}

Selective value encryption

"Only the Value field of sensitive datoms is encrypted. Entity, Attribute, Tx, and Op remain cleartext so the system can route, index, and query without decryption." AES-256-GCM in v_bytes, key HKDF(client_key, "attr:" + attribute). "No key database, no key server. Keys exist only in memory during a session." Search over sealed values is an in-memory index decrypted at login. Consent scopes (ai-analysis, transcription, portal-access, data-sharing, supervisor-review) bind the AI's key: "revocation changes the key". GDPR is met "architecturally", with "legal review still recommended".

Two identity layers, and peers

A keypair (Noise Ed25519, later Iroh) "IS the peer identity" and authenticates a peer; Trust and Projection Contracts authorize: "these are separate concerns and must not be conflated". A new device is linked from a primary one by a QR code; the native client asserts identity/device with the new public key, and the server matches handshake keys against those datoms. "Peers are remote actors governed by the same Contracts as local actors": "Peer validation = Contract enforcement on incoming datoms".

Who vivief was designing for

One counselor, her clients, an AI and a system process. The counselor holds the master key, "she just remembers her passphrase", and the system only routes. There is no organization of many members and no authority that must read a value to accept a change. And its crypto-shredding meets a key that comes back: the counselor's passphrase derives every key again whenever she signs in. That is the reading to keep in mind for section 4, examples (b) and (c).

4. Worked examples

(a) Where access is checked, on today's evidence app

sequenceDiagram
  participant C as Command on P42's phone
  participant P as Presenter on P42's phone
  participant R as P42's local replica
  participant A as Authority, accept
  participant L as Log
  participant F as Authority, sync filter
  Note over C: early access decision, advice only
  C->>A: Append from the outbox
  Note over A: 1 may this writer do this
2 is it well formed
3 does the data stay valid
  A->>L: accepted
  R->>F: Pull from its cursor
  Note over F: may this replica receive it
  F-->>R: only what P42 may see
  P->>R: reads with no access rule

The two enforcement points are accept and sync's filter; both run on authority. The phone runs the same decision early so a refused rename shows at once, but authority decides again (D124 One checkpoint). A Presenter on the phone reads its replica with no access rule, because the replica only ever received what P42 may see (D107 The Presenter pattern). vivief's Projection would carry a capability token into every read instead.

(b) Why a key cannot be the access check here

Suppose evidence/list/title were sealed as vivief seals a session recap, and only members holding the list key could derive it. P42 renames O1/L1 to a blank title from a modified client, skipping renameList's check.

datom  { e: "O1/L1", a: "evidence/list/title", v: <ciphertext>, op: "assert" }
accept: membership ok, actor ok, catalog ok
        acceptance rule "a title is not blank" (D125, I69): cannot read v
        → accepts, or rejects every sealed value it cannot read

vivief states it itself: "When a Trust Contract restricts access to something a Schema Contract requires, the Trust Contract wins." For a counselor who is her own authority that is fine. For an organization it means authority can only check that a sealed value is present and well shaped. Revoking P42 by rotating the key also leaves every title P42 already decrypted on P42's phone: "previously disclosed plaintext cannot be recalled" (communication architecture §5). A decision on authority stops the next pull at once, which P11 shows.

(c) A derived key cannot be destroyed

vivief:  client_key(42) = HKDF(PBKDF2(passphrase), "client:42")
         erase client 42 → forget the key → next login derives it again
ours:    subject_key(P7) = 32 random bytes, kept where P16 decides
         erase P7 → destroy every copy → ciphertext unreadable for good

Crypto-shredding needs a key that exists only as stored bytes, so destroying them is final. A key derived from a passphrase, or from any secret that outlives the subject, comes back. vivief's "no key database, no key server" and its crypto-shredding cannot both hold unless a random salt per subject is stored and destroyed, which is a key database again. So the derivation part of vivief:selective-value-encryption is rejected, and its value-only shape is what D51 already has.

(d) An agent three ways

Where the agent writesactororiginWhat access can refuse the agent
In P42's session, on P42's phone (a chat that edits lists)P42the modelNothing P42 may do. Trust on the origin keeps the content out of a gated commit until a person reviews it (D117 Trust strategies as commit paths).
Inside a server workflow (an enriching activity)serverthe modelOnly what its command may write (declared writes, D127). The server may write server-only attributes, so a guardrail cannot tell this agent from the operator.
With its own agent account (a nightly triage agent that files findings)agent G3the modelAnything a guardrail denies agents: granting membership, committing on the gated path, writing as a reviewer. Its membership and roles are its own, revoked like a person's.

The first two are today's rule (D141). The third is the question D141 handed here (Q4): it gives an agent that acts on its own an accountable identity that is neither a person nor the operator, so an access decision can read "this is an agent" as a fact about the identity, not from the envelope.

(e) An operator rewrites history

sequenceDiagram
  participant P as Phone of P42
  participant S as Server
  participant D as Database administrator
  P->>S: Pull
  S-->>P: changesets up to seq 120, chain head h120
  Note over P: keeps h120 as its checkpoint
  D->>S: UPDATE a datom at seq 87
  P->>S: Pull from seq 120
  S-->>P: seq 121 names h120' as the head before it
  Note over P: h120' differs from h120, history before 120 changed

Today nothing notices: the phone already holds seq 87 and never sees it again, and a new phone receives the edited value as if it were always there. A hash chain over accepted changesets, each naming the head before it, hashed over stored ciphertext (so erasure does not break it, ADR-0023), lets any device that kept a head catch a rewrite. It does not show who wrote a changeset, only that accepted history did not change after a device saw it. Showing who wrote what needs signatures (Q6).

The fence compares a label the device chooses. It exposes nothing new, because any member may already take a run by raising the epoch (ADR-0022 Known limitations), but it means the device id is trusted in exactly one place. 5. Findings

F1. The lease fence trusts an unauthenticated device id. server.ts:577 and :596 compare envelope.device with the stored holder. Not a new exposure (any member can take a run), but the one place a self-chosen id decides anything. Proposed: a comment on I80 Build the journal fence that the fence reads the chain, never envelope.device, and that P06 and P09 include a forged device id.
F2. The roles in Caller are not per organization. They are Keycloak's realm roles (oidc.ts:29-36, :70), the same in every organization and absent with other providers (found by I70). They cannot be the roles of I16. Proposed: roles are per-organization facts (Q3, item 11); Caller.roles leaves when roles are built.
F3. No attribute is personal yet. The catalog has no personal flag and @viviefs/crypto-shred exports nothing. So nothing in the evidence app is erasable, which is right for a lab app and must not be assumed by a consumer app before P16. Where subject keys live and whether a device holds them is P16's design, not settled anywhere.
F4. "Who may take a lease" is answered. I15 and ADR-0022 list it as unspecified. ADR-0036 (D14') answers it: a takeover is always allowed on the head, and who runs a run is policy (the holder resumes, another device continues when a person asks, a server runner after the step's timeout). Proposed: I15 drops it.
F5. The append and revoke race is already being closed. I70's question 17: I71 reproduced it and is in phase 3, before I80. Zanzibar tolerates the same window; ours closes it because check and append become one step (ADR-0036). Nothing to decide but to confirm.
F6. Effect's Identity is a key. The glossary keeps "identity" as the name of the pattern only (P11's pass); Effect uses it for a keypair; D141 says "accountable identity" for the actor. Three uses. Proposed: record the clash for map 3 with I78's list (Q8).

6. The access contract, I70's questions answered

I70's research proposed the smallest contract Cedar still fits, with today's code as its reference implementation. Its 17 questions, each with a proposed answer. Q3 asks for the whole table at once; an item you disagree with goes in its notes.

// One question, asked by accept (writes) and by sync's filter (what a replica receives).
decide(
  evaluations: NonEmptyArray<{
    subject:  { type: string; id: string }   // the actor: a person, the server, later an agent
    action:   { name: string }                // the registered command, or sync.pull
    resource: { type: string; id: string }   // one entity, or the organization for sync
    context:  Record<string, Json>           // organization, device, origin, the writes
  }>,
  at: Position,                              // the state the decision read: the cursor today
): Allow | Deny<{ index: number; reason: AccessReason }>
// AND over the evaluations; an evaluation error is a Deny.

On example (a): P42's rename is one evaluation, { person P42, evidence.renameList, list O1/L1, writes [evidence/list, evidence/list/title] } at cursor 1207. The reference implementation has four rules: a non-member is denied everything; a device writer is denied a server-only attribute; a write outside the command's declared writes is denied; a member may read the whole organization.

#I70's questionProposed answer
1A pattern with a reference implementation and a conformance table? Which gate?Yes. The pattern access; its reference implementation is today's code; the conformance table is a suite (access/decisions) every implementation runs for the steps it claims. Qualified by P11 again, built in phase 3 right after I69, which builds the declared writes it checks (a new issue).
2AuthZEN-shaped, a changeset a batch with AND?Yes: subject, action, resource, context; one evaluation per touched entity, deny on first deny. No changeset-level resource: it would lose per-entity rules, which are the point of relations and Cedar.
3A position at?Yes: the cursor today; a holder epoch with its sequence when authority moves; a frontier when it is shared (I60). In the contract now so it never has to be added.
4Does an error deny?Yes, in the contract. Every adapter enforces it (Cedar skips an erroring policy, so its adapter checks for errors).
5Which state does a write check read?The state at at, before the changeset, with the changeset's own writes in each evaluation's context. "The approver is not the author" reads the author from the state, or from the writes when the same changeset sets it.
6Membership: access or structure?Access, the reference's first rule. D124 already says so.
7Declared writes: access or structure?Access, as guardrails no grant overrides, with server-only attributes beside them: both say what an action may never write (IAM's boundary).
8The reason vocabulary?A closed set owned by the contract: MembershipMissing, ServerOnlyAttribute, UnknownCommand, WriteOutsideCommand, Forbidden (a rule denied, with the rule's name). An implementation maps its own reasons (a Cedar policy id) to one tag with detail; Rejection stays typed.
9Search in the contract?An optional capability, not in the smallest contract. First needed by partial sync (I12), not by a screen.
10A read scope for partial sync?I12's, at its trigger. Direction kept: a read scope is a strict-composition subtree, and accept refuses a changeset that spans two.
11Roles per organization?Yes: role facts per person (or agent) per organization beside membership, at I16's trigger. The identity provider's realm roles are not used for access (F2).
12Relations as datoms, rewrites as code?Yes: relation facts in the organization's log; the rewrites are code beside the catalog, as acceptance rules are (D118, D125).
13Cedar policies with the release?Yes, analysable in CI with D118 intact. Policies an organization changes without a release are deferred; they would reopen D118 and D129.
14Must every implementation run on the phones?No. A higher step may run on authority only, and the device's early check then answers "unknown" (SpiceDB's conditional result). Cedar on Hermes needs a probe before Cedar is an implementation.
15"Who can do X" as a proof?SymCC in verify comes with the Cedar step. Before it, "who can approve I7 today" is a read-model query an app builds when an auditor asks.
16A revocation concurrent with a write under shared authority?I60's. The contract leaves room through at.
17Close the append and revoke race?Yes, as I71 already does in phase 3 (F5).

The ladder, each step triggered by an app, never by size: 1 code (today), 2 roles (a command some members may run and others may not, I16), 3 relations as datoms (permission per entity, or partial sync by permission, I12), 4 Cedar policies (conditions and guardrails hard to read in code, an auditor, or a proof). Membership and the guardrails stay at every step.
