Pattern, concept, contract, abstraction

I90 Pattern, concept, contract, abstraction gives the architecture words a newcomer meets first one meaning each, under I89 How a word is chosen and written's rules: a single word only where it matches Effect and the platforms and libraries we use (D170 One word only where it matches), a compound written whole every time (D172 The compound, every time), and an entry that ends with _Like_, _Not_ and _Avoid_ lines (D174 Like, Not and Avoid lines). I89's sweep left three of its clashes here: Pattern, Contract and Feature. Round 1 (section 6) asks one question per word. Round 2 will settle the inventory rows and what is left of I33 Ideas batch: abstractions that constrain agents, which depend on round 1.

Answered

Round 1, Q1-Q5 all A (2026-10-28): concept is the wider word, with entries Concept and Foundation concept; "abstraction" stays plain English; Pattern stands with its _Like_ and _Not_ lines and .agents/patterns/ becomes .agents/extracts/; Contract and Feature stand with theirs, and "no feature code" becomes "no production code". Round 2 (section 7): Q6 and Q7 A, the rows as the table and I33 narrowed to map 4. Recorded as D181-D185; see I90's Answer.

The page in six lines

  1. The real clash is inside our own text. D82 Patterns build on each other says a candidate is a pattern when it has a contract, a suite and a gate, "otherwise it is a concept": concept means not a pattern. ADR-0032's first foundation concept is Pattern. Pattern is then a concept and not a concept at once (section 2).
  2. One small change of reading fixes it with no rename: concept is the wider word, a named idea of the stack; a pattern is a concept that has a contract, a suite and a gate; every other concept is owned by one pattern. D82's rule and the guides' Concepts pages read the same; Pattern sits in the table without contradiction (section 3).
  3. "Abstraction" is then not needed as a term. Effect uses neither "abstraction" nor "pattern" as a name; concept is already the wider word I33 was looking for, and "a boundary you work through" is what Service, Layer and Schema already name (section 4).
  4. Pattern keeps its word, with a _Like_ line (a design pattern, except it is built and proven once) and a _Not_ line (a pattern something is matched against: Effect's Match, the web's URLPattern). One second sense lives in our own repository: .agents/patterns/ holds Effect usage notes, not patterns (section 4).
  5. Contract matches Effect (its sources say "the procedure contract", "the service contract" in our sense); only vivief's Contract differs, and it already landed as accepting a change (D124 One checkpoint). A _Like_ and a _Not_ line (section 5).
  6. Feature matches what a web or Nx developer calls a feature; only vivief's Feature slice differs. One stray sense: "no feature code before its gate passes" means any production code, including libs (section 5).

Ideas worth keeping, and whether the words keep them

  • A short list a newcomer holds as one loop. Kept: Start here and ADR-0032's table. The word for its rows is this ticket's question (Q1).
  • "Compose, don't extend": a pattern adds no new kind of thing. Ours says the same differently: patterns build on each other and do not nest (Builds on). Kept.
  • "A Contract declares, an effectHandler enforces": the promise is separate from what keeps it. Ours: the contract is separate from its implementations, and a suite checks every one. Kept, as Contract and Implementation.
  • One word for spec, test and guard. We split it on purpose: a contract (the promise), a suite (the test), an acceptance rule (the guard at accept). The _Not_ line on Contract is where a vivief reader learns the split (Q4).

Option A drawn. The foundation concepts are a selection across both kinds, which is why the word must cover both.

A. Concept is the wider word

A concept is any named idea of the stack. A pattern is a concept that has a contract, a suite and a gate; every other concept is owned by one pattern. A foundation concept is one of the twelve.

Rewrites: none of the 75 "foundation concept" uses. D82's row stays as written (a decision row), and a new row records the reading. Glossary: two new entries, Concept and Foundation concept, in the Patterns group; Builds on and Pattern say "a concept". ADR-0032's "each is a pattern" becomes "each is a pattern or a concept one pattern owns".

B. Keep D82's concept, rename foundation concept

Concept stays "not a pattern"; the twelve get another name, such as "foundation" or "cornerstone".

Rewrites: ADR-0032's title (and every reference name pnpm refs fix writes from it), Start here, 75 uses. And the new word still covers patterns and concepts both, so it needs A's reading anyway.

C. A compound for D82's sense

D82's "concept" becomes a compound written every time, such as "pattern concept"; bare "concept" is plain English.

Rewrites: the guide template's Concepts page and its rule, ADR-0026, Builds on, every guide. A compound for an idea people say in one word in every sentence ("a concept of the changesets pattern").

The entries under A

**Concept**:
A named idea people and agents use to think about the stack, such as a datom, a lease or a pattern.
A pattern is the kind of concept that has a contract, a suite and a gate; every
other concept is owned by one pattern and taught once, on the Concepts page of
that pattern's guide ([D82 Patterns build on each other][D82], D181).
_Avoid_: abstraction (for this meaning)

**Foundation concept**:
One of the twelve ideas the whole stack is built on, which a newcomer learns first.
Listed in one table read as one turn, each with its owning pattern and the gate
that shows it ([ADR-0032 ...][ADR-0032], [D160 The foundation concepts][D160]).
Some are patterns, such as sync; others are concepts a pattern owns, such as the
datom. The set is open.

4. Pattern, and whether "abstraction" names anything

I33's question, "is abstraction a better name than pattern for what ViViEfs delivers?", came with two arguments: "abstraction" is wider (a contract, a Layer, a suite, a branded id, a Schema are abstractions and not patterns), and the kinds of intent ordered "by how abstract" (I56's comment). Under Q1's A, concept is already the wider word for the stack's ideas; what "abstraction" would add is the code-level sense, "a boundary you work through", which Effect already names one by one (Service, Layer, Schema). And "how abstract an intent is" is plain English, not a term.

Pattern, the entry with its marks

**Pattern**:
A proven way to build one part of an app, written down once so every app here builds that part the same way.
A concept with one contract, one or more implementations,
suites every implementation passes and a gate that proves
its claims ([D82][D82]) ... (rest as today)
_Like_: a design pattern, except that it is built once as
working code with checks that prove every implementation.
_Not_: a pattern something is matched against, as in
Effect's `Match`, the web's `URLPattern` or a file glob.
_Avoid_: framework, template, abstraction (for this meaning)

The second sense in our repo

.agents/patterns/ holds four files (effect-cli.md, effect-schema.md, effect-services-layers.md, effect-vitest.md), each headed "Agent extract. Source of truth: repos/effect/LLMS.md". They are how to write Effect code, not patterns of this stack. Named in AGENTS.md (four places), ADR-0029 and the docs home page's diagram (".agents/patterns Effect itself").

"Agent extract" is already their name in prose. Renaming the folder to .agents/extracts/ makes the path say it. No pinned name, no code reads it; skills-lock.json does not cover it.

A compound for Pattern ("stack pattern", "proven pattern") was weighed: the clash is with a different core (matching) that context never confuses ("the log store pattern" is never read as a regex), so under D170 a _Not_ mark is enough, and 431 uses plus ADR titles (ADR-0033 The Presenter pattern) stay.

5. Contract and Feature

Contract

**Contract**:
What a part of the system promises to the code that uses it, written down so a check can catch a broken promise.
In code it is an Effect service and its types; its suites
check that every implementation keeps it.
_Like_: an interface, except that it also promises
behaviour, which suites check on every implementation.
_Not_: vivief's `Contract`, a rule checked whenever data is
written: here that is an acceptance rule, checked at accept.
_Avoid_: interface (alone), API (for the promise)

Matches Effect's prose sense (I78: "Effect's sense is ours: a declared shape both sides read"). The acceptance rule's entry already says _Avoid_: contract (for this meaning). Where ADR-0032, ADR-0023, ADR-0034 and ADR-0037 name vivief's sub-types ("vivief's Trust Contract", "Sync Contract") they already say vivief's; ADR-0032's From vivief column writes them in code font like its other vivief names.

Feature

**Feature**:
One piece of what the app does for its users, such as collecting evidence, kept together from screen to server.
In code it is a vertical slice split into `model`,
`client` and `server` projects.
_Like_: an Nx feature library, except that it is three
projects that reach from the screen to the server.
_Not_: vivief's Feature slice, data and logic with no
screen, a step in adopting its concepts.
_Avoid_: module, domain package

The stray sense: "No feature code before its gate passes" (AGENTS.md, 10-open-items-and-risks.md, bootstrap/00-next-session.md) is D27's design before code, which covers libs too (the SQLite store waited for P02 SQLite drivers). It becomes "No production code before its gate passes", the wording the inventory row already uses ("no production or feature code").

Feature stays on the docs linker's everyday-terms list (only "Feature" mid-sentence links), as it is a single word. Concept, if added, joins that list for the same reason.
