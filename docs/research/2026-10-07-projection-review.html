I49 asks whether ViViEfs names one concept over its read models, the projector, query atoms and delivery, as vivief's Projection does for query, access, encryption, delivery, freshness and trust scope; whether a read can be as of a tx; and which shapes beyond relational read models and the analytics projection the stack names. 17 rows of the vivief inventory. It decides against ADR-0032 What ViViEfs is about, especially D99 (facts kept, meaning derived) and D105 (what must stay possible).

vivief's Projection

vivief v6 §2.2: "Lens + Seal merged. Query + access + encryption + delivery + freshness + trust in one concept." A Projection is what a consumer (a Surface, an actor, an LLM context load) asks for:

interface Projection {
  filter: DatomQuery; sort: SortSpec; group?: GroupSpec; depth?: DepthSpec   // Query
  capability: CapabilityToken; scope: "own" | "consented" | "all"         // Access
  decryptionKey?: DerivedKey                                               // Encryption
  delivery: "snapshot" | "live" | "live-persistent" | "replay"             // Delivery
  freshness?: "committed" | "in-flight"
  trustThreshold?: number                                                  // Trust
}
Projection.live(query, capability)   // named profiles: snapshot, live, stream

vivief docs/contract/vivief-concepts-v6.md §2.2, HEAD 3071cb2. The same DatomQuery also scopes encryption, checks Contract invariants and finds handlers ("One query model, used everywhere", cp §2.6).

What this shows. Every vivief dimension that ViViEfs has, it has as a separate part with its own gate. Access and encryption sit at different boundaries (sync and storage), not in the read, and that is why a read on a replica needs no access rule: the replica only ever receives what the account may see.

The word: "projection" already means something here

In ViViEfs: deriving a store from the log

The projector projects committed changesets into read models; projection_cursor is how far it got; analytics is "one more projection of the log, to Parquet or DuckLake" (D37); ADR-0023 says "projections show erased"; the trace projector reads the log from its own cursor and derives durable spans (ADR-0018 Tracing and telemetry sinks). Direction: log → store, done once per store, upstream of any reader.

In vivief: what a consumer asks for

A Projection is a consumer's request: this filter, delivered live, with this capability and trust threshold. Direction: store → reader, one per reader. vivief's materialization (D2TS, indexes) is underneath it and has no name of its own at this level.

Adopting vivief's meaning would give "projection" two meanings in one stack (the projector does not make Projections). Keeping ours means vivief's Projection maps to a read (query atom or one-off SQL) over a projection.

A keeps the parts as patterns and gives the derivation side one name, which also answers the shapes question (each shape is a projection into a store built for it). B gives the read side one name and a delivery vocabulary, and has to rename the projector or live with two meanings. C moves access into every read, which only pays once a replica can hold data its reader may not see (I12, partial sync, or roles enforced within an organization), and is I54's to decide with vivief:projection-access.

The patternA screen asks a Presenter for data with a query and keeps a frame subscription to the frame it returns; reads never write. vivief's Projection read side is adopted in this form; "projection" keeps its ViViEfs meaning. D107.
The queryData, written in code, translated by each implementation (SQL for SQLite, Postgres and DuckDB, Polars, a remote node, an outside source); vivief's entity operations are part of it; plain code allowed where it declares it reads its whole input. D108.
FrameTyped rows with each value's origin and the frame's status; one entity is a one-row frame; gathering commits in batches; the frame subscription ends with its screen. D109.
ImplementationsThe reference (SQLite read models with query atoms) is what every other is checked against. Faster ones give the same answer sooner; enriching ones (outside sources, models) write ordinary changesets naming their origin first. Intermediates are derived, one organization, erasable, gone at sign-out. The app builder chooses. D110-D113.
Partial nodesA Presenter's query can say what a partial node fetches, under I12's new trigger, with I53. D114.
Origin trustTrust belongs to an origin, named in the envelope (D58'); derived when read, the least trusted of a value's origin and its inputs' origins; five levels set per organization by authority; vivief's trust strategies are commit paths. D115-D117.
DeferredThe columnar copy, with the human's one-wide-table design (I63); the Presenter conformance gate (I62); building origin trust (I64); redaction; in-flight freshness.
