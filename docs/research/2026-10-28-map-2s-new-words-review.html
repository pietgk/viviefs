2. node: four other senses in the libraries we use

D103's meaning: one installation of an app that keeps all or part of an organization's data and writes changes to it. A device is the one a person uses, and the server is the one that holds authority. A tool is an app but not one of these, because it keeps no replica and writes no changesets. D103 put it in code font until map 3 because of Node.js. The human's hint then was: write Node.js as node-js where a name is needed, so that node stays free for a node in a network.

A. Sync node (recommended)

**Sync node**:
One installation of an app that keeps an organization's data and sends its changes: a device or the server.
It keeps all or part of an organization's data and writes changesets to it ([D103 Nodes and authority][D103]); a device is the sync node a person uses, and the server is the sync node that holds authority. A tool is an app but not a sync node: it keeps no replica and writes no changesets.
_Like_: a node in a peer-to-peer network, except that today one sync node, the server, holds authority for every organization.
_Not_: Node.js, the web's DOM `Node`, React's `ReactNode`, or a Kubernetes node.
_Avoid_: `node` (alone, our word until [D199][D199]), peer

It goes in the Sync group, before Device. "Node" alone, in prose and in code, then means Node.js, as it does in Effect. Nothing in the code is renamed.

A. Screen now, the general word deferred (recommended)

**Screen**:
One full view of an app that a person moves to, such as a list or one item's details.
What a link or a route opens ([D73 Links and routing][D73]); it asks a Presenter for frames and renders them. A screen is the visual way a frame reaches a person, one of several ([D134 Presenting in any modality][D134]).
_Like_: a screen in React Navigation or Expo Router, the component a route renders, except that it gets its data only as frames from a Presenter.
_Avoid_: page, view (the View of Vision - View - Effects is wider)

In the Reading group, after Presenter. The foundation concept keeps its accepted name, "Presenter, frame and surface", with surface in plain English; Start here's Entries column gains Screen. Decide when: a frame is presented on something other than a screen, such as speech, or the Presenter gate (I62) names its input.

B or C. Name the general word now

B. Surface, bare, with _Not_: React Native's surface (a running React root), Android's Surface, Material's Surface, an API or attack surface. The app shell code meets React Native's sense in native logs and crash traces.

C. Presentation surface, a compound, written whole every time. ADR-0032's foundation concept would become "Presenter, frame and presentation surface", an amendment to an accepted ADR.

Either way Screen is added too, for the visual case.

4. Frame, frame subscription, trust level

I89's sweep held Frame here as a clash. Effect has no public Frame (only internal comments in SchemaBinary.ts). The other senses in the platforms: an animation frame and a frame rate (the web's requestAnimationFrame, React Native's 60 frames a second), the web's <iframe>, a stack frame in Node.js and Hermes, and a WebSocket frame under the sync RPC. None of them shares our core: typed rows with each value's origin and a status.

Nearly every one of those senses comes with its qualifier: "animation frame", "frame rate", "stack frame", "dropped frames". In our living documents, every bare "frame" is ours, and no code identifier uses the word yet. A compound ("Presenter frame") would also force "Presenter frame subscription", by D172.

**Frame**:
The rows a screen shows, with typed columns, where each value came from and how fresh it is.
A Presenter's result; one entity is a one-row frame, and its status says fresh, gathering, remote or failed ([D109 Frame and frame subscription][D109]).
_Not_: an animation frame or a frame rate, a web `<iframe>`, a stack frame, or a WebSocket frame.
_Avoid_: data frame, result set

Frame subscription is already a compound, and Trust level has no clash found. Both stand as written.

I77: ADR-0035 ("Accepting a change") means a data changeset; the glossary's Verify entry ("every change must pass") means a code change. Of 412 lines, almost all read correctly from their page: ADRs about data mean a changeset, and pages about verify mean a commit. The only place where both meet is the glossary, where Verify's hover line sits a few groups below "Changes and accept".

The new and changed entries

Presentation surface (Reading, after Frame subscription)

**Presentation surface**:
Where what an app shows reaches a person: a screen, a speaker, or a vibration.
Any modality: a screen (text, diagrams, pictures), a speaker (speech, music), haptics, or ways not known yet; the Presenter's contract names none ([D134 Presenting in any modality][D134], [D200][D200]). A screen is one kind. An agent reads a frame through a model's tool, not a presentation surface.
_Like_: a CSS media type (screen, print, speech), except that it is where a Presenter's frame arrives, not what a style targets.
_Not_: React Native's surface (a running React root in a host view), Android's `Surface`, Material's `Surface` component, or an API or attack surface.
_Avoid_: surface (alone), output, display

Screen (Reading, after Presentation surface)

**Screen**:
One full view of an app that a person moves to, such as a list or one item's details.
What a link or a route opens ([D73 Links and routing][D73]); it asks a Presenter for frames and renders them. It is the visual kind of presentation surface ([D200][D200]).
_Like_: a screen in React Navigation or Expo Router, the component a route renders, except that it gets its data only as frames from a Presenter.
_Avoid_: page, view (the View of Vision - View - Effects is wider)

Sync node and Frame's _Not_ line as in sections 2 and 4. Verify's hover line: "The full set of checks every change to the code must pass before it is done."
