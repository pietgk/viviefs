What an app is to a device and a node

I48 asks two things. Where the server-independent goal is recorded, so the five peer-to-peer rows of the vivief inventory cite a ViViEfs source instead of the 2026-09-30 communication research alone. And, widened by I47: what an app is to a device and a node, so that D100 (out of scope means not yet) holds for a server-independent mode. Your framing: client-server can be read as peer-to-peer where one or more nodes carry a server signature. Below, today's four running things are worked through both readings on the real code.

What this shows. The server already writes into the log the way a device does: same envelope, its own device id in the clock. What sets it apart is not the data but the authority it holds for each organization. And the glossary's Device entry ("one installation of an app, on one phone or in one browser", Avoid: client, peer) describes the phone and the browser only, while the App entry ("such as the phone app or the server") and D102 (tools are apps) already reach wider.

Two readings of the same system

Client-server (today's words)

Two kinds of thing: devices and the server. The server is a different kind of thing, so a word, an ADR or an attribute can quietly assume there is exactly one, and that it is not a device.

One kind of thing: a node, a running app that keeps a replica and writes changesets. Authority for an organization (accept, order, grant membership, fence leases) is a role a node holds. Today exactly one node per organization holds it, and it is the server; that is client-server, unchanged. The dotted line is what must stay possible (D100).

The same code either way. Nothing in today's protocol changes under the second reading: the phone still sends its outbox to the one node that holds authority, and catches up by that node's sequence. The difference is what the words let a later decision assume.

"Server signature". Today authority is held by position: the device syncs with whatever URL it was given, and trusts what comes back over TLS. A signature would let a node prove that a changeset was accepted by the node holding authority, so a peer could relay accepted history it cannot accept itself (the comms research's "enterprise with peer exchange"). Whether acceptance is signed is I15's (signed changesets, device keys). This page reads "signature" as the authority role, and leaves the cryptography to I15.

What the words would say (if Q1 is A)

Drafts to judge Q1 by, not entries yet. The App entry stays as written; its plain sense against its in-code sense is map 3's (D102).

Node (new)

One running installation of an app that keeps a replica of an organization's data and writes changes to it: the app on a phone, in a browser, or the server. A tool such as verify is an app but not a node.

Avoid: peer (for now), host

Device (narrowed)

A node a person uses: one installation of an app on one phone or in one browser. Unchanged in meaning; it now says what kind of thing it is.

Avoid: client, peer

Server (defined by its role)

The node that holds authority for an organization: it accepts or rejects every change, orders the accepted ones, grants membership and fences leases. Today one server holds it for every organization.

Whether "authority" gets its own entry is map 3's.

Round 1

Three questions with no open prerequisite. The words for Device and Node, tools, the consumer app shape, what must stay possible, and the rows wait on these.

Q1 - Which reading do ViViEfs's words take?

The question is what the glossary and the ADRs may assume, not what the code does: today's protocol is the same under A and B.

Q2 - Where is the server-independent goal recorded?

The comms research calls it "the confirmed goal" but changes nothing: no open item, no issue, no Decide when:. D100 says every out-of-scope item says what must stay possible; D101 says some items are learnable in the lab. The comms research names the next evidence: a paired exemplar doing the same operation in both modes.

Q3 - What does "server-independent" mean?

Scenario 4: the operator is gone. Your framing ("one or more nodes carry a server signature") reads as authority that can move. The comms research's independent group dissolves authority instead: signed permission history and merge rules, a second acceptance contract. The comms definition: "the original application operator is unnecessary for the agreed operations"; relays, discovery and storage replicas may help if they are replaceable and hold no authority; "no infrastructure whatsoever" stays undecided.
