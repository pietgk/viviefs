Where tests live, and how the engine owns its suites

D78 moves the engine suites into libs/workflow-engine. Built as written, that is a dependency cycle, which lint refuses. This page shows why, compares two ways out, and proposes one location convention for every kind of test, so the answer also settles where future tests go.

1. Why the move is a cycle

libs/testing is a hub: it holds every pattern's suite, so it depends on datom, the engine, telemetry and identity. A project that libs/testing depends on can never run a suite from it. Store projects can run the engine suites only because nothing in libs/testing depends on a store.

It is not only the engine. The same wall stands in front of every suite that should run next to its implementation: the trace projection suite in libs/telemetry, the token verifier suite in libs/identity (its tests live in libs/testing today for this reason), and later the sync and membership suites, now in tools/qualification.

2. Two ways out

R1: the registry owns, runs stay where they are

Nothing moves. The engine suites keep running in the store projects' integration tests (split into their own test file), the memory-engine positive control joins them, and each test is tagged with its suite id. engine.ts's registry entry names the three suites, and verify checks they passed in the integration producer.

Convention it implies: a suite runs in the project of the implementation that varies. The engine is one; the stores vary, so each store proves the engine survives on it.

Pros

  • No moves, no new entries, no new lint rule; smallest change.
  • A new store adapter runs every store-dependent suite in one place, as the native and wasm stores already do on devices.

Cons

  • The hub stays. The telemetry, identity and sync suites cannot move next to their code later either.
  • Someone reading libs/workflow-engine finds none of its main evidence there; only the registry points to it.
  • Suites that do not vary by store (token verifier, sync) have no natural home under the convention.
Recommended

R2: suites ship with their contract

Each suite moves into the lib that owns the contract it checks, under src/suites/, exported as @viviefs/<lib>/suites. libs/testing shrinks to generic helpers that depend on no @viviefs lib, so it sits at the bottom of the graph. Implementations run the suites in their own tests.

Convention: a suite lives with its contract; it runs in the project of the implementation under test.

Pros

  • No hub, so no cycles, now or when the next pattern arrives.
  • A lib holds its contract, its suites and, for the engine, their runs: what a guide's testing page points to is in one place.
  • Matches D75: a suite belongs to exactly one pattern, and now also sits in it.

Cons

  • Test code inside production libs, behind a ./suites entry. A lint rule must keep it out of production imports (only tests, src/suites/, tools/ and the evidence apps may import it), replacing today's "core may not import @viviefs/testing" rule.
  • About 15 files move, 4 package.json exports added, imports updated in the stores, the evidence app and tools/qualification.
  • The engine's tests depend on the store adapters (test-only edges).
