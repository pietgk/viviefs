1. What is a pattern, and what is only a concept

The glossary: a pattern is a reusable solution with one contract and possibly several implementations, delivered on its guide. A suite belongs to exactly one pattern and is named <pattern>/<aspect>. That gives a test anyone can apply: does it have a contract code depends on, a suite that checks it, and a gate that qualified it? If yes, it is a pattern and gets a guide. If no, it is a concept, and it lives in the guide of the pattern whose contract defines it.

Patterns do not nest; they build on each other. Nesting would mean a guide inside a guide, and a concept taught twice. Instead each pattern owns its concepts and links to the patterns it builds on. One rule decides every concept: it lives in the guide of the pattern whose contract defines it and whose suite checks it. Every other guide links there.

One consequence to decide: ADR-0011

ADR-0011 Log store pattern (full title "Log store pattern, read models, compaction and analytics"). Its main design (several stores, one suite, compaction, analytics as a projection) is the log store, proven by P04 Log store conformance. One sentence of it is read models: "disposable, rebuilt from the log, never migrated", proven by P05 Changesets and projections.

A. ADR-0011 on the log-store guide (recommended, your pick)

The guide states the rule as the log store's promise ("you may drop any read model") and links to the changesets guide for how they are rebuilt. Because ADR-0011 cites two gates, the guide names both, P04 Log store conformance and P05 Changesets and projections, and both run before it is accepted.

Cost: P05 Changesets and projections runs at acceptance for one sentence. Every ADR is named by exactly one guide, which guides can check.

B. ADR-0011 on the changesets guide

The log-store guide names ADR-0006 One datom log and ADR-0007 Hybrid logical clock, and only P04 Log store conformance.

Cost: the ADR titled "Log store pattern" is accepted on a guide that does not teach the log store, and the log-store guide cannot cite its own pattern ADR as the why.

C. ADR-0011 on both guides

Each guide names it; it is Accepted when the first is.

Cost: an ADR accepted on material that does not exist yet, and D63's "accepted guide's ADRs are all Accepted" means less.

4. metadata.guides, on the real projects

The exemplar of a pattern is the smallest real code showing it end to end. For the log store that is libs/datom (the LogStore itself) and the four store projects (its implementations). For changesets it is libs/datom again: projector.ts, manifest.ts, visibility.ts. So one project is the exemplar of two patterns. The stores are not exemplars of changesets: they only run its suite.

6. Every gate and ADR reference reads as its name and is a link

From your comment on section 3: a bare "P04" or "0011" makes a reader stop and look it up. On this page every reference now reads as its id and its name, and links to its evidence note or ADR (the nodes in the diagrams too). Proposed as a rule of the guide template, so it holds in every guide without anyone remembering it:

In a guide page (MDX)

Both run before acceptance: <Gate id="P04" />
and <Gate id="P05" />. The why is <Adr id="0011" />.

Renders as

Both run before acceptance: P04 Log store conformance and P05 Changesets and projections. The why is ADR-0011 Log store pattern.

Rules

  • <Gate> links to the gate's newest evidence note, <Adr> to the ADR page; an unknown id fails the site build, like a missing sample region does.
  • Gate names get one home in code: a name field in tools/qualification/src/gates.ts (today the names exist only in the table in 06-qualification-gates.md), and the Status block uses the same component.
  • The guides check refuses a bare P\d\d or ADR-\d{4} in a guide's prose; frontmatter stays ids, because it is data.
