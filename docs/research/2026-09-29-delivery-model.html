How a pattern is delivered

This page shows how everything we build fits together: patterns, ADRs, gates, evidence, the exemplar, guides, samples, exercises and lessons. It uses the terms from CONTEXT.md and the agreed decisions (D28-D30, D46, D48', D57, ADR-0026 as amended today). It also marks where what we built has drifted from what we designed, so we can fix it at a planned time.

The whole model in five sentences
  1. A pattern is a reusable way of building something. Its ADRs record why it has this shape, and the claims it depends on.
  2. Qualify proves those claims: each gate runs a retained probe (with a positive control) and writes the ledger, and a dated evidence note records it. Then the ADR is Qualified.
  3. Verify keeps the exemplar, the code that uses the pattern, true to its contract on every change: types, lint, and tests at the lowest layer that owns each behaviour.
  4. Teach writes the pattern's guide: concepts, how-to, a review checklist, lessons that cite evidence, and exercises and samples that verify checks. When you accept the guide, the ADRs are Accepted.
  5. A pattern is delivered when all three hold and the exemplar and the guide link to each other.

1. Three questions, three mechanisms

Each question has its own tool, so a contract check never ends up in the ledger, and a claim about the stack never ends up in every pull request.

Verify

Does the code keep its contract?

pnpm verify: static -> unit -> integration -> ui -> quality. It runs on every change, in CI too. Done means green.

Proves: this code, at this commit.

Qualify

Is this claim about the stack true?

pnpm qualify: gates P01-P15, probes on devices and labs, an append-only ledger, and one sequential full run.

Proves: a fact we depend on, until its inputs change (then it is stale).

Teach

Can a person or an agent learn it from what we wrote?

Guides in apps/docs (Starlight), samples and exercises checked by verify, lessons citing evidence.

Proves: nothing new. It explains, and points at what Verify and Qualify proved.

The one rule that holds the model together: claims come from gates, never from lessons. A lesson says "P05 showed X" and links the evidence. If a lesson is wrong, fix the lesson. If the claim is wrong, the gate fails.

7. The crash matrix, explained

The workflow engine makes one promise (D2, D3, ADR-0012): kill the app at any moment, start it again, and the workflow carries on where it was, with no side effect done twice and no step lost. A normal test cannot show that, because it never kills anything. The crash matrix is the test that does.

1. Kill at a boundary

A workflow run has moments where its state is half-written, for example "the activity ran, but its result is not in the journal yet". Each such moment is a boundary. The engine calls a CrashHook at every boundary (libs/workflow-engine/src/crash-hook.ts). Normally it does nothing. Armed at one boundary, it stops the run there, and the test then drops all in-memory engine state, which is what a process kill does.

2. Relaunch on the same store

A fresh engine opens the same datom store, like the app starting again. It finds the run in the journal and replays: stored activity results are reused, not re-executed.

3. Check the outcome

The run finishes with the right result, and every external effect (counted by idempotency key) happened at most once. The "matrix" is every boundary times every store: sqlite-node and Postgres (PGlite) in P06. P07 adds the device column: a real force-quit on the iOS and Android simulators.

flowchart LR
  S(["start"]) --> K1{{"kill 1<br/>before activity"}} --> A["activity<br/>runs"]
  A --> K2{{"kill 2<br/>during activity"}} --> K3{{"kill 3<br/>after activity,<br/>before journal"}} --> J[("journal:<br/>activity result")]
  J --> K4{{"kill 4<br/>waiting for a<br/>human step"}} --> K5{{"kill 5<br/>during a<br/>durable clock"}} --> K6{{"kill 6<br/>during a<br/>lease handoff"}} --> K7{{"kill 7<br/>during a<br/>file upload"}} --> D(["done"])
  classDef kill fill:#7f1d1d,stroke:#fca5a5,color:#fff
  class K1,K2,K3,K4,K5,K6,K7 kill
CheckAfter the relaunch, this must hold
1. before activityThe activity runs once, and the result is correct.
2. during activityThe activity runs again (it never finished), but its idempotency key keeps its external effect visible only once.
3. after activity, before journalThe hardest case: the effect happened, but the engine does not know it. It re-runs, and the idempotency key makes the second run harmless.
4. during a human stepThe run comes back still waiting for the DurableDeferred. Completing it after the relaunch finishes the run.
5. during a durable clockThe wake-at datom survived, and the clock fires after the relaunch.
6. during a lease handoffA killed handoff leaves the old device holding epoch 1. A finished handoff gives device B epoch 2, and the stale device's write is refused.
7. during a file uploadThe blob exists once (content hash plus idempotency key).
typed failures survive a killA typed error from before the kill comes back as the same typed error after it, not as a decoding error.
positive controlThe same matrix on Effect's in-memory engine must fail (activities re-run, and the run is gone after a kill). This proves the matrix can detect lost durability, so its passes mean something.
Why it matters for Verify: today the matrix (runCrashMatrix in libs/testing) runs only when P06 is qualified. A change that breaks resume passes pnpm verify and is caught only at the next P06 run. libs/workflow-engine even declares evidenceOwner: "crash-matrix", an owner that verify never runs. D26 asks for more: every workflow (not only the engine's probe workflow) ships with its own crash-matrix test.

8. Drift between design and what we built

This is what you asked me to check. Each item names the design source it drifts from. None of them is a failing check. They are places where the design promises more than the build enforces.

D1. The crash matrix is not a merge bar

D20 calls the crash matrix "the engine's merge bar", and D26 says "every workflow ships with a crash-matrix test". Today it runs only in P06 (qualify), so a change to the engine or a new workflow passes verify without it. ADR-0025 already lists this rule as unverified. The integration stage's own description says "conformance suites and crash matrix", which is not true today.

D2. There is no coverage ratchet

05 and D48' describe a ratchet lockfile for coverage and budgets, where regressions fail and improvements need one command. Only the bundle-size baseline exists.

D3. The web E2E smoke is an empty step

e2e-web is in the stage table, but no project has the target, so no Playwright journey runs. 05 also says "Web keeps Lighthouse budgets", and nothing measures them.

D4. "Schema at every boundary" is not enforced

D26 and ADR-0025 name it, and it is marked unverified. No lint rule or test fails when a boundary (for example an SQLite row or an HTTP body) is not decoded through Schema.

D5. "Lowest owning layer" is declared, not checked

The ownership check only confirms that each project declares an evidence owner. Nothing links a behaviour to the one layer that proves it. That is the gap your note points at: patterns should shape which layer tests what. A guide section "how this pattern is tested" would make it explicit for each pattern.

D6. The docs-only path rule does not exist yet

05 says "done" for a docs-only diff is a path rule. There was nothing to route before apps/docs. It becomes real now.

In line with the design, and not drift: device E2E belongs in qualify until there is a release; conformance runs cheap implementations in verify and every implementation in qualify; lint rules keep growing through guardrails.test.ts.

9b. Speed and weight: what each part costs

Measured on 2026-09-29 on this Mac: CI=true (all projects), Nx cache skipped. The qualify times come from the ledger of the sequential P01-P11 run on 54e724786.

verify, about 2.5 min
static (sync, typecheck, lint, scope, ownership, audit)23 s
unit (includes the full P09, P10, P11 host checks)10 s
integration (log store conformance on sqlite-node + Postgres, evidence-server)15-17 s
ui ("storybook" = Vitest + jsdom + axe; e2e-web empty)3 s
quality (build 34 s, bundle-size 45 s)79 s
+ crash matrix (Q16), measured as P06+6 s
qualify P01-P11, 30 min
Device and lab gates: P01, P02, P03, P04, P05, P07, P113, 3.5, 2, 2.5, 2, 7, 9 min
Host-only gates: P06, P08, P09, P106 s, 7 s, 2 s, 22 s
What the numbers say: speed does not split verify from qualify. What splits them is what a check needs (only the host, or a device or lab container) and what it produces (a contract check, or a claim in the ledger). The heavy part is devices and labs, and that is already qualify. Crash matrix, coverage and component tests are host-only and fast, so they belong in verify. The P09-P11 host checks already work this way: the same probe function runs in verify as a check, and in qualify as a recorded claim.
