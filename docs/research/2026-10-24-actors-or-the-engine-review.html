Actors or the engine?

I51 Actors or the engine asks whether the datom-backed workflow engine is ViViEfs's answer to vivief's actor runtime, whether anything that is not a workflow needs supervision, and whether the stack needs an event bus beside Reactivity invalidation and the cursor stream. It settles 13 rows of the vivief inventory and reviews I8 Engine scale-out and a multi-runner server and I29 Ideas batch: agents that record a replayable run. I56 One shape at every level? already settled the shape at the data level (D130 One shape at the data level), so this page does not ask about the shape again. Effect's cluster is read first: a concept Effect already names takes Effect's name (D135 Effect's names first).

The page in five lines

  1. vivief's actor is a handler with identity, a queue, a lifecycle and a typed protocol, for multi-step, streaming or cancellable work. Its runtime was never built: routing, supervision, concurrency and lifecycle are listed as open choices (kb §5).
  2. Effect's actor is the Cluster Entity, and Effect builds its durable workflow on it: in ClusterWorkflowEngine each workflow type is an Entity and each execution an entity id.
  3. Our engine gives an execution every actor property (identity, state, protocol, mailbox, lifecycle, one owner) and replaces supervision with something stronger: a crashed run resumes from its journal. So the durable workflow is ViViEfs's actor level, and "actor" keeps its narrow meaning.
  4. Nothing else in the stack needs a supervisor: every other loop rebuilds from a cursor. The rule is "if it must not lose progress on a crash, it is a workflow; otherwise it rebuilds from its cursor". There is no event bus: Reactivity in process, the cursor stream between nodes, push only as a wake-up hint.
  5. Found on the way: a lease never expires today. D14 Leases with fencing says "renewed while active ... until the lease expires", but the engine writes expiresAtMs: null and nothing renews; a lease moves only by an explicit handoff (section 5).

4. Worked examples on real code

(a) A workflow killed mid-activity, against an Entity restarted on a defect

Ours (P06, kill point during-activity).

  1. The workflow starts; viviefs/workflow/started is in the log.
  2. Activity upload runs; the process is killed before its exit is journaled.
  3. Next launch, EngineSweep.sweep finds an execution started with no result (engine.ts:715-731) and calls resume.
  4. The body re-runs from the top. Activities with a journaled exit return it; upload has none, so it runs again, made harmless by its idempotency key.
  5. The run continues. Nothing in memory was needed.

Effect Entity.

  1. A message arrives; the entity's handler runs.
  2. The handler dies with a defect.
  3. The entity manager logs "Defect in entity, restarting", waits per defectRetryPolicy and rebuilds the entity (entityManager.ts:397-420).
  4. Persisted messages without a reply are delivered again.
  5. The entity's in-memory state starts empty; anything it needs it must rebuild from its own storage.

Both replay what was persisted. Ours replays the whole run, because the journal is the state; an Entity replays only the unanswered messages, and its state is its own concern. That is why ClusterWorkflowEngine needs no extra supervision for workflows either: the workflow body's replay is the restart.

(b) A loop that is not a workflow

Today the stack has no long-running loop besides the engine. The sync client pulls when asked (client.ts:446), the projector invalidates after it projects (projector.ts:686-689), and the trace projector exports from its trace cursor when called (trace-sink.ts:1-10). Candidates to come: a sync loop on the device, projector catch-up, a trace export loop, server jobs such as compaction or a sweep of due clocks.

Each of them reads the log from a cursor it advances only when its work is acknowledged (glossary Acknowledged cursor; ADR-0011 Log store pattern, read models, compaction and analytics). A crash loses no progress: the loop starts again from its cursor. So it needs a retry, not a supervisor:

// A sketch, not code to write: a trace export loop as a scoped Layer.
export const traceExportLoop = Layer.effectDiscard(
  exportFromCursor.pipe(                          // reads from the trace cursor, advances on ack
    Effect.repeat(Schedule.spaced("5 seconds")),
    Effect.retry(Schedule.exponential("1 second")),
    Effect.forkScoped,                            // interrupted when the Layer's scope closes
  ),
)

// The same job on a server with more than one runner, where exactly one runner may run it:
export const traceExportSingleton = Singleton.make("trace-export", exportForever)
// or, on a timetable:  ClusterCron.make({ name: "compaction", cron, execute: compactOnce })

The rule this gives: if a piece of work must not lose progress on a crash, it is a workflow; otherwise it rebuilds from its cursor and runs as a scoped Layer with a Schedule. A server job that must have one owner becomes a Singleton or a ClusterCron only once the server has more than one runner (I8); on one runner the scoped Layer is already the only owner.

Killed after model:plan#1, the run resumes and replays the model's answer from the journal with no model call. That is I29's "replay with no model call" for one run. What it does not give is I29's replay on the next run, against a changed app, with hand-off on drift: that is a recording keyed by its input, a different thing, and stays with map 6. The actor on the envelope stays the person or the server who ran it.

5. Found: a lease never expires

What the decisions say. D14 Leases with fencing and ADR-0014: "One lease per execution, renewed while active, with a fencing counter ... other devices show the execution read-only until the lease expires." The glossary's Lease: "Fenced, and renewed while active."

What the code does. The lease value has an expiresAtMs field (journal.ts:13-16), and every place that writes one sets it to null (engine.ts:226 on grant, :744 on handoff). Nothing renews it, nothing reads the field, and the server checks only the epoch and the device (server.ts:557-585). A lease moves only by Leases.handoff. P09 tested a handoff, not an expiry.

Why it matters here. Expiry is how an owner that died is replaced without its help. Effect's shard lock has it (expiration 35 s, refresh 10 s). Without it, a device that is lost or wiped holds its executions forever, and P14 Quarantine after a lost lease has no "lost" lease to start from except a handoff.

Proposed. A new issue, I80 "A lease never expires", Decide when: P14's grilling or I53 Sync and conflict's, whichever comes first, since both need a lease that can be lost. ADR-0014 gains an Observed line now. Not a code change in this ticket.

A is not possible. Cluster assumes its runners are always-on, always-connected server processes that call each other. A phone is none of these.

C is the simpler and more elegant one. One way to own a run (a fenced lease), one journal (datoms), one engine, one tracing path (the trace projector reads the journal; it could not read MessageStorage). A server runner becomes one more holder, as the server already is one more node (D103 Nodes and authority). Workflows never message each other directly: they talk through the log (deferreds are datoms, D40 Server-side human steps), so Cluster's main strength, routing a message to the live owner of an entity, is not something we use.

What C borrows from Cluster. Cluster keeps one lock per shard alive, not one per entity. C should do the same: a holder is alive while it heartbeats, and each lease stays valid while its holder is alive. "Renewed while active" (D14) would write a datom for every active run every few seconds; liveness per holder writes none. Liveness is operational state kept beside the log, like the compaction horizon's device_cursors (ADR-0011). Two policies, one mechanism: a runner that misses its heartbeats for seconds loses its leases; a device that is offline for days must not, because its offline work is legitimate. A device's lease moves by handoff, or by a person or authority declaring the device lost (P14 Quarantine after a lost lease, D15 Server authority after a lost lease).

When C would be a bad idea. Many short server workflows per second, where a claim through accept and a wake-up through the store are too slow next to Cluster's in-memory routing. Nothing in the plan comes near this, and today the server runs no workflow at all (the engine runs only on devices and in tests). If it ever does, Cluster is still there behind WorkflowEngine, and that is I8's to decide.

What it changes. D39 One engine everywhere says "Effect Cluster is the later scale-out path behind the same interface". Under C that becomes: scale-out means more runners holding leases, and Cluster is an option only if a measured load needs it (D39'). I8 Engine scale-out and a multi-runner server is rewritten to match. I80 (a lease never expires) becomes the first step: holder liveness, with the two policies.

13. Q7 explained: the fenced lease, today and everywhere

13a. The idea in five sentences

  1. A lease says who may run one workflow run: {holder, epoch}, a datom on the execution (viviefs/lease/holder on O{org}/W{exec}).
  2. The epoch is a number that only goes up. Every takeover writes the next number.
  3. Every journal write carries the holder and epoch it was made under, in its envelope (device, leaseEpoch).
  4. Fencing: authority accepts a journal write only if that pair is the current lease. A write from an older epoch is rejected, however late it arrives.
  5. So two holders can both run for a while, but only one can write, and the loser finds out and stops. Fencing makes a takeover safe; it does not say when a takeover is allowed. That second part is policy, and it is what is missing.

14. The human's alternative: takeover always allowed, the journal detects overlap

The idea (2026-10-26). State that a takeover is always allowed. A run is being run by someone else because its first runner is not doing it, so liveness mostly takes care of itself, and no heartbeat is needed. Two engines on one run show up as overlap in the journal.

14a. What holds

  • Safety never needed a heartbeat. A heartbeat only decides when a takeover may happen automatically. What keeps two runners from both writing is the fence, and the fence works however the takeover was triggered.
  • "Always allowed" is today's rule. Accept takes any higher epoch from any member device (section 13b, gap 2); D14's "read-only until it expires" was never enforced.
  • Overlap is already detectable from the journal. Every journal fact is write-once at accept (server.ts:89-95, plus viviefs/activity/started by catalog policy, catalog.ts:119): when two engines journal the same step, the second gets BasisRejected.

14b. Where write-once alone breaks: a spliced history

Write-once rejects the same fact twice. It does not reject a fact that was computed from a history that lost. Phone A goes offline mid-run; phone B takes over:

14c. The idea, completed: the journal head is the fence

Keep the idea and fence by history: every journal write names the fact of this run it followed (the run's head as the writer saw it), and accept takes it only if that is still the run's head. This is a compare-and-append per run, the glossary's Basis ("the point in the log a change was made from, used to notice when someone else changed the same thing since") scoped to one run. A device's own offline writes chain on each other, so they stay valid until the first one meets a head someone else moved.

In 14b: A's step 3 names step 2 as its parent, but the head is now B's step 3, so it is rejected; A's steps 4 and 5 name A's own step 3, which is not in the journal, so they are rejected too. The whole losing history is refused, as with the epoch, and there is no lease, no epoch and no heartbeat.

  • D is simpler than C. One concept fewer (no lease object, no epoch), no heartbeat table, no takeover rule, and the fence is the history itself, so it cannot disagree with it. 15. Option D in full: the journal is the fence

15a. In one paragraph

A run's journal is one chain of facts. Every fact the engine writes names the fact it follows. Authority accepts an engine fact only if the fact it follows is still the last one in the chain (the head). Whoever is up to date may write the next fact: phone, browser or server runner, and it does not matter who wrote the one before. A writer that is not up to date is refused, and so is everything it built on top. That one rule keeps every run a single, coherent history, without a lease, an epoch or a heartbeat. Who should run a run is then a policy read from the journal, not a lock.

15f. Who runs a run: policy, not safety

The rule in 15c keeps the history whole whatever anyone does. Separately, each engine decides when to run a run, so that writers rarely collide:

  • The holder resumes on its own: on launch, on a wake-up, when a deferred completes. Everyone else leaves the run alone and shows "last worked on by phone A, 3 days ago".
  • Another device continues only when a person asks ("Continue on this phone?"). A phone offline for days may be doing legitimate work, so nothing takes over a device's run automatically.
  • A server runner takes over a runner's run whose head has not moved for longer than the running step's timeout (case 6). The timeout belongs to the activity, not to the runner.
  • Claim before acting, when online (optional). A writer that is online can wait for its "step started" fact to be accepted before running the side effect. Then case 3 duplicates nothing: the loser is refused before it acts. A phone offline cannot wait, and proceeds as in case 4. Server runners are always online, so for them this is free.

New ADR-0036: The journal is the fence

Summary: A run's journal fences its own writers: every engine fact names the fact it follows and is accepted only on the run's head, so a takeover is always allowed and no lease is needed. Status: Proposed, unverified. Qualifying gate: P06 and P09, qualified again on the journal fence. Related: D14', D39', D2, D10, D11, D13, D15, D40, D103; ADR-0012, ADR-0014 (its lease design superseded once this qualifies); I71, I80, I51.

Problem. One run must have one history, written by one writer at a time, across phones that go offline and server runners that pause. Today a lease per run with an epoch does it (ADR-0014), but the lease never expires, any member device may take it, and its check is not atomic with the append (I71). A lease is also a second record of who runs a run, beside the journal, and would need liveness (heartbeats, expiry) to move without its holder. Effect Cluster's shard lock fences by time only and cannot be held by a device.

Design. Engine facts (start, activity start and exit, clock, result) form one chain per run: each names the engine fact it follows. Authority accepts an engine fact only if it follows the run's head (a start only when the run has none), in one step with the append; otherwise it is refused, and so is anything built on it. Outside inputs are write-once on their own entity, outside the chain. Takeover is always allowed; the holder is derived from the head. Policy, not safety, decides who runs: the holder resumes on its own; another device continues when a person asks; a server runner takes over after the running step's timeout; an online writer may claim a step before acting. viviefs/lease/holder and the envelope's leaseEpoch are no longer written; old values decode; nothing is renamed (D44). Where "follows" lives (an envelope field or a journal attribute) is I80's. Revisit if a measured server load needs Cluster's routing in memory.

Trade-offs. Lease everywhere with liveness (heartbeats, a takeover rule, two policies): safe, but more parts and a second record. Cluster on the server: two journals and a time-only fence. Write-once facts alone: lets a spliced history in. The journal fence: the least stored and one record, at the cost of re-qualifying P06 and P09 and a per-run head read at accept. Out-of-scope items: none made harder; the head check is a duty of authority, so the server-independent mode (I60, D105) can hold it on any node that holds authority.

Failure-handling. Two writers on one step: the second is refused, the loser stops; at most one side effect is duplicated, made harmless by its idempotency key, and none when the step was claimed before acting. An offline phone overtaken: its history from the divergence is refused whole; user content goes to quarantine (P14, D15). A paused runner: its late write follows a fact that is no longer the head and is refused. Two starts with one idempotency key: the second is refused. To be shown by P06 (kill during a takeover) and P09 (a second writer refused, a spliced history refused, an outside input not moving the head).

Outcome. Expected: one history per run, whoever writes, with no lease. Observed: not yet run.
