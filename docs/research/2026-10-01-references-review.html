2. One mechanism: references are resolved when the site renders

Every page, Markdown and MDX alike, already passes through one Sätteri plugin chain (repo-links.ts rewrites file links there today). Extend that chain: the source keeps short ids, readable on GitHub and quick to write; the site shows each as its id and name, linked, with a preview on hover. Nobody has to remember anything, and an id that does not exist fails the build.

Left alone

  • Code blocks, and inline code that is not a repository path.
  • Headings (anchors must stay stable) and text that is already a link, except a link whose label is only an id, which gets the name.
  • Paths with a placeholder: guides/<pattern>/, NN.MM-name/.
  • Paths relative to a project (src/lib/guides.ts): they name no repository file.

Fails the build

  • A gate, ADR or decision id that does not exist (P99, D4, ADR-0099).
  • A path under apps/ libs/ features/ tools/ docs/ exercises/ that does not exist: a stale path, caught when the file moves.
  • An ADR or decision without a name or summary, so a reference cannot render.

What this replaces. The <Gate> and <Adr> components and the guides rule against bare ids (D86, this morning) become unnecessary: a plain P04 in any page renders named and linked. One way to write a reference, everywhere. D86's intent stays; its mechanism changes, so D86 is amended.

A. Our own preview card (recommended)

The plugin writes the name and summary into each link at build time (data attributes); one small script shows a card on hover and on keyboard focus, styled with Starlight's colours. No network fetch, works offline, nothing to keep in sync.

Cost: about 80 lines we own; tested with a story in the browser once P12 runs stories in Chromium.

B. The browser's tooltip

A title attribute with the summary. Zero code.

Cost: appears after a delay, unstyled, plain text, not on keyboard focus or touch.

C. No preview

Named links only.

Cost: no quick check of what a reference means without leaving the page.

6. The exercise loop, and what the lesson must say

Your run was the expected first step. problem/ is code that runs but is wrong on purpose; the exercise is to fix it. pnpm exercise log-store 01.01 runs the exercise's check against your problem/. Red, with a message saying what is still missing, means not yet. Green means you have done the one thing the lesson teaches, with your own hands, on the real log store. The Check yourself questions then ask about exactly that, so you answer from what you just made happen, not from what you read.

flowchart LR
  READ["Read the lesson"] --> RUN["pnpm exercise log-store 01.01"]
  RUN --> RED{"passes?"}
  RED -- "no: the message says what is missing" --> EDIT["edit problem/send.ts"]
  EDIT --> RUN
  RED -- "yes" --> CMP["compare with solution/"]
  CMP --> CHECK["Check yourself, then the next lesson"]

What got in the way: the lesson never says that red is the start, the path to edit is not a link, and the output buries one line of hint under an Effect log line, a stack through Effect internals and Vitest's framing. Proposed output, from a small reporter that pnpm exercise uses instead of Vitest's default:

The lesson's Your turn section gets the same steps in words, with the file as a link. The guide template's lesson page gets a short "How an exercise works" paragraph, so every lesson in every guide says it the same way. Note: the terminal path is clickable in most terminals; on the site, a path links to GitHub, because the site cannot open a file in your editor.
