## Durable execution

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d10"></a>D10 | Effect Workflow over our engine | Use Effect's `Workflow` / `Activity` / `DurableDeferred` / `DurableClock` API everywhere, over our own `WorkflowEngine` implementation. Workflows are versioned by name (`Inspection.v3`). Activities must not suspend (a suspending activity re-runs on replay). | One workflow API on device and server; public interfaces only. Effect has no versioning API. |
| <a id="d11"></a>D11 | Human steps as deferreds | A human step is a `DurableDeferred` inside the workflow. **Workflows own durable business progress; machines and atoms own ephemeral interaction.** A killed app resumes at "waiting for step X" and the UI rebuilds. | Clean split between durable and ephemeral state. |
| <a id="d13"></a>D13 | Server holds workflow state | The sync server holds full workflow state (execution, journal, pending deferreds and clocks) so another device can resume. The server stores it and never runs device workflow code. | Needed for device switching; still just storage. |
| <a id="d14"></a>D14 | Leases with fencing | One lease per execution, renewed while active, with a fencing counter. Stale holders' writes are rejected; other devices show the execution read-only until the lease expires. | Activities have real side effects that cannot be merged afterwards. |
| <a id="d14p"></a>D14' | The journal is the fence | As [D14 Leases with fencing][D14] for its purpose (one writer per run; a stale writer refused), with the lease replaced by the journal. Every engine fact (the start, an activity's start and exit, a clock, the result) names the engine fact of its run it follows; authority accepts it only if that is still the run's head, checked in one step with the append ([I71 An append can land after a revocation][I71]). A takeover is always allowed: whoever is up to date writes on the head. A writer that is behind is refused, and so is everything it built on, so a run is always one history. Outside inputs (deferred completions, [D11 Human steps as deferreds][D11], [D40 Server-side human steps][D40]) are write-once on their own entity and do not move the head. The holder is derived: whoever wrote the head. Only the holder resumes on its own; another device continues when a person asks; a server runner takes over a run whose head has not moved within its running step's timeout; an online writer may claim a step before acting. No lease datom, epoch or heartbeat. A "lost lease" in [D15 Server authority after a lost lease][D15] and [P14 Quarantine after a lost lease][P14] now reads as a refused history, and [D103 Nodes and authority][D103]'s duty "fence leases" as "fence each run's journal". Decided in [I51](../../issues/0051-actors-or-the-engine.md) ([ADR-0036 The journal is the fence][ADR-0036]); built by [I80 Build the journal fence][I80]; until then the lease runs and is safe ([ADR-0014 Leases, fencing and server authority][ADR-0014]). | A lease beside the journal is a second record of who runs a run, which can disagree with the first and needs liveness to move. Write-once facts alone let a spliced history in (an offline phone's later steps on top of another device's step); fencing each history by its head closes that, with nothing to expire. |
| <a id="d15"></a>D15 | Server authority after a lost lease | Server authoritative. A device that lost its lease drops its divergent journal entries and replays from the server. User content (photos, recordings, drafts) is never dropped; it is quarantined for human resolution. | Idempotency keys make side effects harmless; user work is never silently lost. |
| <a id="d20"></a>D20 | Crash matrix as the merge bar | The engine's merge bar is a crash matrix: engine tests with `TestClock` killing at every boundary, plus a simulator force-quit E2E. | In-memory-only durability proves nothing. |
| <a id="d24"></a>D24 | Durable clocks and notifications | Long `DurableClock` sleeps write a `wake_at` datom and schedule a local notification (expo-notifications; Android `alarmClock` delivery for time-critical). The engine sweeps due clocks on launch and foreground; expo-background-task sweeps opportunistically. Notification actions complete the matching `DurableDeferred`. | Turns "resume on next launch" into mechanism. |
| <a id="d25"></a>D25 | Browser engine leader | Browser: one leader tab per profile runs the engine (Web Locks); other tabs render and forward events via BroadcastChannel. Each browser profile counts as one device for leases. | Several tabs are several engines on one OPFS database. |
| <a id="d39"></a>D39 | One engine everywhere | One engine: our datom-backed `WorkflowEngine` on device and server alike. Effect Cluster (`ClusterWorkflowEngine`) is the later scale-out path behind the same interface. | One journal format is the point of [D31 One datom log][D31]. |
| <a id="d39p"></a>D39' | One engine, one journal, one fence | As [D39 One engine everywhere][D39]: our datom-backed engine on device and server alike. Scale-out on the server is more runners writing on the journal head ([D14' The journal is the fence][D14']): each sweeps for runs whose head has not moved within their step's timeout and claims before acting. Effect Cluster is not the scale-out path: it fences by time only, keeps its journal in `MessageStorage` (a work queue with claims and deletes, which fits the log poorly), and assumes runners that are always reachable, which a device is not. It stays possible behind `WorkflowEngine` if a measured load needs its routing in memory ([I8 Workflow engine scale-out and more workflow runners on the server][I8]). Decided in [I51](../../issues/0051-actors-or-the-engine.md) ([ADR-0036 The journal is the fence][ADR-0036]). | One journal format was [D39 One engine everywhere][D39]'s point; Cluster would add a second journal and a second fence. |
| <a id="d40"></a>D40 | Server-side human steps | Server-side human steps (a reviewer approves on the web) write a deferred-completion datom under `O{org}/W{exec}/D{name}` in the same changeset as the review. It syncs down; the device engine resumes. Push is only a wake-up hint. | Signals become ordinary datoms: deduplicated, fenced, traced, auditable. |

## One datom log, three views

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d31"></a>D31 | One datom log | One datom log is the single substrate: the engine journal, domain data and sync all use it; tracing is derived from it. | One storage format, one sync protocol, one audit trail. Realises vivief's "observability is projection over effect datoms". |
| <a id="d32"></a>D32 | Traces derived from the log | Trace context is written in each changeset's envelope ([D58 Envelope per changeset][D58]). Spans are derived from the log with deterministic span ids (`executionId + activity + attempt`), so replays never duplicate spans. Export is durable: a projector reads the log from a cursor and posts OTLP via Effect's native exporter. Live `withSpan` detail inside activities is parented to durable spans. The tracing backend is never the store the engine reads from. | Tracing and durability become one concept without trusting a lossy, sampled, non-transactional store for durability. |
| <a id="d33p"></a>D33' | Hybrid logical clock for tx | `tx` is a hybrid logical clock `(pt, c)`. `pt` is server-corrected time: monotonic clock anchored to the server offset within a boot session, wall clock + persisted offset after a reboot; never below the last persisted HLC. `c` is a tie-break counter used only when `pt` would not advance. Receive rule: `last = max(last, received)`. Server rejects future skew and flags measured gaps. Encoded ULID-shaped: 48-bit ms, 16-bit counter, remaining bits random + device id. | Offline for days must still work; corrected clocks alone cannot handle backwards jumps or cross-device causality. |
| <a id="d34"></a>D34 | Per-attribute conflict policies | Conflict policy is declared per attribute in its Schema: **LWW** (domain scalars), **write-once fenced** (journal facts, lease grants), **human conflict** (references, evidence attachments, approvals: both values kept, a conflict datom raised). | One global LWW rule is wrong for GRC, ERP and the journal. |
| <a id="d34p"></a>D34' | Per-attribute conflict policies, decided at accept | As [D34 Per-attribute conflict policies][D34]: LWW, write-once fenced and human conflict, per attribute. A commit's basis is the server cursor its writer had pulled when the command ran, which gives the basis of [D35'' Single-datom transactions with changesets][D35''] one meaning on every `node`. The `node` holding authority decides a human conflict at accept: a fact for the same entity and attribute accepted after the basis from another device is a conflict (the writer's own earlier outbox is not), and authority writes a `viviefs/conflict` fact in the same step as the append, so every `node` shows the same conflict and a command can close it. Projectors read conflicts from the log; a device may show a preview. An orphan (user content whose owner is not visible, [D38 Entity ids and strict composition][D38]) is decided at accept too, with [I69 Accept checks every change][I69]'s read model. Per value, the later of its assert and retract wins: a replace writes "retract old, assert new", so one writer leaves one value and two concurrent replaces leave both, marked by the open conflict; a resolving command retracts the values not chosen and closes the conflict. Effect's `EventLog` finds conflicts on the server on ingest the same way. Decided in [I53](../../issues/0053-sync-and-conflict.md) ([ADR-0009 Per-attribute conflict policies][ADR-0009]); built by [I81 Build conflicts decided at accept][I81], with [P05 Changesets and projections][P05] and [P09 Sync][P09] qualified again with two devices. | Found in [I53 Sync and conflict][I53]: the basis was a sequence number in whichever log projected it, and every changeset outside [P05 Changesets and projections][P05] sent 0; a conflict was a row each projector derived, never a fact; the server checked write-once only (`BasisRejected`); and a human-conflict attribute kept every value ever asserted, so a retract removed nothing and no conflict could be resolved. No gate put two devices on human conflict. |
| <a id="d35pp"></a>D35'' | Single-datom transactions with changesets | **Single-datom transactions with a changeset id.** Datom = `[e, a, v, tx, op, cs]`. A changeset becomes visible when its commit datom arrives, carrying a manifest (count + hash of members). Conflicts are ordered by the commit `tx`; the commit records its basis and the server checks, per attribute policy, whether touched attributes changed since. `cs == tx` means self-committed (a checkbox toggle stays one datom). Commit and abort are write-once; open changesets may expire. Authors see a "committed + my open changesets" view. Keep the defining attribute for entity lifecycle. | Keeps web-interview's one-datom wire and storage simplicity, gives atomic multi-attribute and cross-entity changes enforced once by the projector, and makes drafts native (Studio drafts, evidence review, ERP draft orders). |
| <a id="d58"></a>D58 | Envelope per changeset | The envelope (actor, device, lease epoch, trace context, command) is one fixed-shape record per changeset, keyed by `cs`, stored in the `changesets` table (not as datoms) and sent with the commit datom, or with the datom when `cs == tx`. One mechanism for every changeset size; the commit datom carries only manifest and basis. | The changeset is the unit of intent. Uniform, keeps the one-datom shorthand, queryable by joining on `cs`. Replaces a dual mechanism (commit datom vs columns) that was never decided. |
| <a id="d58p"></a>D58' | Envelope names the origin | The envelope gains `origin`: a reference to the origin entity the changeset's content came from (a person, a mail account or chat workspace, a website, a model and its version, a system activity), apart from the actor who committed it. An enriching changeset ([D111 Faster and enriching implementations][D111]) also names the origins of its inputs. For data a person types, the origin is that person. The `datoms` table does not change. Decided in [I49 Projection: one concept or several patterns][I49] ([D115 Origin trust][D115]); built with [I64 Build origin trust][I64]. | Trust belongs to an origin ([D115 Origin trust][D115]), so every changeset must say where its content came from; one field per changeset, not per fact, because gathering commits per batch per origin ([D109 Frame and frame subscription][D109]). |
| <a id="d36"></a>D36 | Shared commands | Commands are shared pure Effect functions `(readModel, intent) -> changeset or DomainError`, run on client and server. The client applies optimistically and queues in an outbox; the server revalidates (Schema, membership, authorization, invariants such as independent review, lease fencing) and accepts or rejects the whole changeset with a typed error. On rejection the client rebuilds from confirmed data and reapplies its remaining outbox. | Server authoritative, offline-capable, one write path for app and engine. |
| <a id="d36p"></a>D36' | Shared commands, as built | As [D36 Shared commands][D36], corrected by what [P09 Sync][P09] built ([ADR-0016 Commands, server validation and rejection][ADR-0016] Observed): the server does not re-execute the command. It accepts or rejects the changeset by [D124 One checkpoint][D124]'s three questions; the command runs on the device and calls the same acceptance rules ([D125 Acceptance rules][D125]), and every domain writer uses a registered command ([D127 Registered commands][D127]). | [D36 Shared commands][D36] named "invariants such as independent review" among what the server revalidates; nothing on the server checked a domain rule, so a crafted changeset with a blank title was accepted. |
| <a id="d16"></a>D16 | SQLite drivers | SQLite drivers: Effect's official drivers, `@effect/sql-sqlite-react-native` (op-sqlite 17.x pinned) on native and `@effect/sql-sqlite-wasm` (OPFS) on web, after a gate. Fallback: our own `SqlClient` over expo-sqlite (one driver for iOS, Android, web). | Less custom code at the most failure-sensitive layer. |
| <a id="d37"></a>D37 | Log store tables | SQLite locally: one append-only datom table with EAVT and AEVT indexes; typed read-model tables (one per entity type, Schema-defined) updated incrementally in the same SQLite transaction. Snapshots and a compaction horizon only past what every device acknowledged. The log store is a pattern with swappable implementations (SQLite device, SQLite Node, Postgres) under one conformance suite. Analytics is a projection to Parquet or DuckLake queried by DuckDB, never the durable log. | Read models are disposable projections; lock-in is avoided because the contract is tested. |
| <a id="d38"></a>D38 | Entity ids and strict composition | Entity ids encode their parent **only for strict composition** (part of the parent, shared lifetime, can never move), declared per entity type: `O{org}/...` root, list -> todo, order -> line, execution -> journal entries. Everything else uses reference attributes. One projection rule: visible iff the defining attribute is asserted and the owner is visible. Orphaned writes to user-content types raise a conflict. Separator `/`, ids are branded Schema types. Guideline: "can it ever move? then it is a reference". | Keeps one-datom tree deletes and prefix scans, makes `O{org}/` the backbone for isolation and sync, avoids immutable ids that cannot move. |
| <a id="d21"></a>D21 | Sync as datom replication (superseded) | Superseded by [D31 One datom log][D31] + [D35'' Single-datom transactions with changesets][D35''] + [D36 Shared commands][D36]: sync is datom replication (outbox up, cursor stream down), server-authoritative validation per changeset. Effect EventLog was studied as a design reference, not adopted (no server rejection, device-clock ordering, no RN path). | See research/03. |
| <a id="d43"></a>D43 | Files by content hash | Files are stored by content hash (`blob:sha256...`): local file storage on device, object storage on server. A datom references the hash; the upload is an idempotent retryable activity; a changeset referencing a file commits only once the file exists on the server (manifest extends to file references). | Bytes in object storage, provenance in the log. |
| <a id="d44"></a>D44 | Never rename, never migrate | Attributes are never renamed or retyped (new attribute + projector mapping instead). Read models are rebuilt, never migrated. Workflows versioned by name, old versions ship until drained. The server refuses unknown attributes with a typed "upgrade" error. | An append-only vocabulary keeps a log-based system migratable for years. |
| <a id="d44p"></a>D44' | Never rename, never migrate, the RPC too | As [D44 Never rename, never migrate][D44], and the sync RPC and every HttpApi or RPC contract shared with the client ([D8 Effect everywhere][D8]) are additive too: a method or field is never renamed or removed while a client that uses it may still run. A version handshake answering an old client with a typed upgrade error is deferred, `Decide when:` the first consumer app ships to a store with old versions in the field. vivief's migration as creation is not adopted for the log; a label that changes is a translation, not a rename. | The attribute check covered data, not the calls that carry it; an old client calling a changed method gets a decode error with no way to say "upgrade". |
| <a id="d50"></a>D50 | Data at rest on device | Data at rest on device: OS file protection as baseline; SQLCipher via op-sqlite with keys in Keychain/Keystore (expo-secure-store) as a qualified option per consumer app, passing the same conformance suite. | GRC probably needs it, BirVana does not. |
| <a id="d51"></a>D51 | Crypto-shredding | Erasure via crypto-shredding: attributes marked `:personal` store values encrypted with a per-subject key; erasure destroys the key; projections show "erased". Bulky personal files are content-hashed blobs that can be deleted. Qualified by a gate proving unreadability on every replica and projection. | Keeps the log immutable and syncable while meeting the right to erasure. |

## Presenters and origin trust (2026-10-08)

From [I49](../../issues/0049-projection-one-concept-or-several-patterns.md), the third ticket of

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d107"></a>D107 | The Presenter pattern | A Presenter is a pattern: a client asks for data with a query, gets a frame back and keeps a frame subscription to it. Reads never write. vivief's `Projection` read side (query, delivery, freshness, trust scope) is adopted as this pattern; access and encryption stay at their boundaries, the server's check on sync and encryption at rest and for erasure ([I54 Trust, encryption and who may sign in][I54]). "Projection" keeps its ViViEfs meaning: deriving a store from the log (the projector, the trace projector, the analytics projection). | Every vivief dimension ViViEfs has, it has as a separate part with its own gate; what was missing is the whole a screen asks of. Naming the read side by what it produces avoids giving "projection" two meanings. |
| <a id="d108"></a>D108 | The query is data | The query is a typed expression, written in code, that each implementation translates: to SQL for SQLite, Postgres and DuckDB, to Polars, or to parameters for a remote `node` or an outside source. It is passed down the chain read model, log store, remote `node`, outside source, each answering what it can. An implementation may be plain code instead of a translated query; it declares that it reads its whole input and applies the query's filter and sort afterwards, so it runs only where that input is held. vivief's L1 idea, queries written in code that an LLM can write, is this decision; its entity operations (`entity`, `pull` with depth) are part of the query's vocabulary, and an entity with its children comes back as a frame per level, linked by id. | A SQL string cannot be passed to Parquet, another `node` or a mail server; an expression can. People and agents write the same query ([D95 App creation][D95]). |
| <a id="d109"></a>D109 | Frame and frame subscription | A frame is typed rows with each value's origin and the frame's status (fresh, gathering, remote, failed); one entity is a one-row frame (map 5 may revise). Freshness is committed, or committed plus my open changesets ([D42 Live reads with query atoms][D42]). Gathering commits in batches and the frame grows through invalidation. A frame subscription ends with its screen; the gathering activity is durable and goes on committing after it. A snapshot is a one-off read. Cursor consumers (sync pull, trace export, the compaction horizon) stay their own pattern. Output shown before it is committed (vivief's in-flight freshness) is deferred, `Decide when:` a screen needs output finer than a committed batch. | One input shape for screens gives one generic table view; durability belongs to the gathering, not to the frame subscription, so there is no second lifecycle. |
| <a id="d110"></a>D110 | The reference implementation | Every implementation of the Presenter returns the reference implementation's frame for the same query at the same `tx`. SQLite read models with query atoms are the reference and today's default ([P05 Changesets and projections][P05], [P08 UI three-way prototype][P08]). The default can change; the reference changes only by decision. In-memory datom indexes with vivief's entity interface, and engines that keep answers up to date incrementally (`D2TS`, differential dataflow), are candidate faster implementations. | Improving an implementation over time is only safe against a trusted one; this is [P05 Changesets and projections][P05]'s "full rebuild equals incremental" lifted to the pattern. |
| <a id="d111"></a>D111 | Faster and enriching implementations | Implementations come in two kinds. Faster ones only make reading quicker: they give exactly the answer the reference gives, and the conformance check proves it. Enriching ones add information the log cannot compute itself, by fetching from outside (mail, chat, the web, files) or by asking a model (classify, summarize, extract). An enriching implementation first writes its result to the log as an ordinary changeset that names its origin and its inputs' origins ([D58' Envelope names the origin][D58']); from then on it is ordinary data, and a faster implementation presents it. Outside content arrives as blobs linked from datoms. A result that is shown but never written must say so on its frame. | A model's answer kept only in a read model changes on the next rebuild with no new fact, and fetched content may be gone next week; [D99 Facts kept, meaning derived][D99] keeps facts and derives meaning. |
| <a id="d112"></a>D112 | Intermediate presentations | Anything an implementation prepares (an index, a Parquet file, an embedding, a cache) is derived and rebuildable, never mixes organizations, can be erased (ciphertext, or rebuilt when a subject is erased, [D51 Crypto-shredding][D51]), and goes away with the local replica at sign-out. | An embedding of a personal email is personal data; the rules hold for every implementation, so they are the pattern's, not each implementation's. |
| <a id="d113"></a>D113 | Who chooses the implementation | The app builder, person or agent, declares an implementation per Presenter; it is swapped without touching the screen. Choosing automatically at run time is a later implementation, qualified like any other. | Choosing automatically is a query planner; declared choice lets the pattern ship with the implementation that exists. |
| <a id="d114"></a>D114 | Partial sync on demand | A Presenter's query can say what a partial `node` fetches ([D105 What must stay possible][D105] (3)): the facts land in its log and the projector builds the read model, so a read model stays derived from the local log and works offline for what was fetched. vivief's subscription filter is the direction; it is built under [I12 Partial sync, history consolidation and client data access][I12]'s new trigger, a Presenter needs data its `node` does not hold, with [I53 Sync and conflict][I53] owning the sync details. | A log that grows large makes a phone a partial `node`; refreshing it through the log avoids a second kind of read model that cannot be rebuilt offline. |
| <a id="d115"></a>D115 | Origin trust | Trust belongs to an origin, not to data. Every changeset names its origin ([D58' Envelope names the origin][D58']); trust in an origin is datoms on the origin entity, so its history is kept. A value's trust is derived when it is read: the least trusted of its origin and its inputs' origins (vivief's `min` rule), a default policy that can be replaced; a person's review raises only that changeset to the reviewer's level. In a Presenter, trust is a companion column per value when the query asks for it, a threshold is a filter, and the trust context defaults to no filter. vivief's `:tx/source` maps to the origin, and its `:tx/trust-score` set at ingestion is not adopted. | Lowering trust in one origin lowers everything it produced, the way destroying one key erases one person ([D51 Crypto-shredding][D51]); a score fixed at ingestion cannot be withdrawn, and without lineage withdrawal leaks through derived data. |
| <a id="d116"></a>D116 | Trust levels and who sets them | Five ordered levels: `revoked < untrusted < unreviewed < trusted < verified`. Verified: checked by something deterministic (a gate, a validation, an exact source). Trusted: a person, or an origin the organization trusts. Unreviewed: model output or gathered content nobody has checked. Untrusted: kept, but left out of an agent's context by default. Revoked: the organization withdrew trust; shown only to a reviewer. Trust is per organization. Defaults per kind of origin live in the app's catalog; an organization's override is a datom on the origin entity that only authority writes (`authority: 'server'`), until roles loosen it ([I16 Roles in use, invitations and self-service membership][I16]). | A number suggests a precision nobody can defend, and the `min` rule works on levels; lowering an origin's trust changes what every agent and screen sees, closer to granting membership than to editing a title. |
| <a id="d117"></a>D117 | Trust strategies as commit paths | vivief's three trust strategies are commit paths for an enriching implementation, chosen by its origin's trust level: authoritative commits directly; sandboxed keeps the output an open changeset seen only in its author's draft view ([D35'' Single-datom transactions with changesets][D35''], [D42 Live reads with query atoms][D42]); gated is sandboxed plus a durable deferred asking a person to commit it ([D11 Human steps as deferreds][D11], [D40 Server-side human steps][D40]). The person who commits is recorded as reviewer ([D115 Origin trust][D115]). vivief's Trust Contract (keys, roles, consent) is encryption and stays with [I54 Trust, encryption and who may sign in][I54]; an actor category for agents in the envelope stays with [I51 Actors or the engine][I51] and map 6. | Drafts and approval steps already exist without agents; the strategies need no new mechanism, only a rule for which path a source of output takes. |

## Attribute value types, before the build (2026-10-30)

Decided with the human in [I66](../../issues/0066-attribute-value-types.md), on [the review page](../../research/2026-10-29-attribute-value-types-review.html), in three rounds: the human withdrew a closed set of value types in favour of Effect's Schema, and asked for Polars, DuckDB on the device and TanStack DB to be weighed. The numbers are the page's: a throwaway measurement at 10M datoms on one Mac, not qualification evidence. The log does not change: one `datoms` table and a text `v` ([D121 Attribute value types][D121]).

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d209"></a>D209 | The value is an Effect Schema | An attribute's value Schema ([D121 Attribute value types][D121]) is a plain Effect Schema, so the catalog declares no value types of its own. Its type is the Schema, its range is Effect's checks, its description is Effect's `description` annotation. The text in `v` is derived: `Schema.toCodecStringTree` for a single value, `Schema.toCodecJson` and JSON text for a structured one. A text is canonical when decoding it and encoding it again gives the same text, which rejects `010` for an integer without a rule per type. A column type is the one thing written by hand: one function per implementation over `Schema.toRepresentation`, with Arrow types for the columnar side, which Parquet, DuckDB and Polars all read. A value that does not decode, or is not canonical, makes the projector reject its changeset, as an unknown attribute does; checking it on accept is [I69 Accept checks every change][I69]'s ([D125 Acceptance rules][D125]). Conflict policy, defining and authority stay plain fields of the attribute: they say how the catalog treats a fact, not what a value is. A boolean keeps Effect's `true` and `false`. Not chosen: a closed set of value types; moving those fields into Schema annotations; a shorter boolean text, which saves about 12 of a datom's 384 bytes (3%) even if every datom were a boolean, because `v` is stored in the table and two indexes, while a read model already stores 0 or 1. | Effect's Schema already holds the type, the range and the description, and a second way of declaring them is a second thing to keep true. Effect's `effect/schema/Model` builds variants for tables an app writes, is marked unstable and creates no tables, so it does not fit a derived read model. |
| <a id="d210"></a>D210 | The row store and the columnar copy differ | The reference read model keeps one table per entity type, [D37 Log store tables][D37] as written, on SQLite and Postgres. [I63 The columnar copy as a Presenter implementation][I63] keeps its one wide table per organization, in a columnar engine, derived from a cursor. They no longer have to make the same choice ([D121 Attribute value types][D121] asked them to): each gives a frame per entity type, so [D110 The reference implementation][D110]'s check holds across them. Polars cannot be the reference, because a read model runs on every sync node and Polars has no official build for a device, and a DataFrame is not a store; it stays a candidate for the columnar copy on a server. DuckDB on a device is a candidate for the same copy, not for the read model. Not chosen: one table for all types; one table per organization in the row store. | SQLite stores a header byte per column, empty or not. At 1500 attributes one wide table is 5,881 MB against 286 MB per entity type, and takes 7 s against 2.3 ms for a scan. DuckDB's wide table stays at 162 MB, but reading by id or parent and updating a row are 40 to 50x slower than the SQLite tables, and one transaction cannot span a SQLite log and a DuckDB file, as [D37 Log store tables][D37]'s read model needs. |
| <a id="d211"></a>D211 | A typed row while an attribute is in conflict | One column holds one value, and an attribute in human conflict holds several ([D34' Per-attribute conflict policies, decided at accept][D34']). The column holds the value committed last, and the row has a `conflicts` column naming the attributes in conflict. A screen shows a value and can show that it is in conflict without a second read; the other values come from the conflict. Not chosen: an empty column while in conflict, which makes a required attribute look missing; a side table of values, the second table [D144 A set is entities][D144] avoided. | Several values are the exception and a screen still needs something to show. |
| <a id="d212"></a>D212 | Required comes with its check | An attribute's "required" is declared with [I69 Accept checks every change][I69], on the same `AttributeSpec`, not before it. The range needs no such wait: it is in the value Schema, so the projector checks it from the start. | Required is an acceptance rule, and a rule without a positive control fails `verify` ([D125 Acceptance rules][D125]). Nothing can be that control before [I69 Accept checks every change][I69]'s rule runner exists. |
