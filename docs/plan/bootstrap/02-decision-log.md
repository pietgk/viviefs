## Durable execution

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d10"></a>D10 | Effect Workflow over our engine | Use Effect's `Workflow` / `Activity` / `DurableDeferred` / `DurableClock` API everywhere, over our own `WorkflowEngine` implementation. Workflows are versioned by name (`Inspection.v3`). Activities must not suspend (a suspending activity re-runs on replay). | One workflow API on device and server; public interfaces only. Effect has no versioning API. |
| <a id="d11"></a>D11 | Human steps as deferreds | A human step is a `DurableDeferred` inside the workflow. **Workflows own durable business progress; machines and atoms own ephemeral interaction.** A killed app resumes at "waiting for step X" and the UI rebuilds. | Clean split between durable and ephemeral state. |
| <a id="d13"></a>D13 | Server holds workflow state | The sync server holds full workflow state (execution, journal, pending deferreds and clocks) so another device can resume. The server stores it and never runs device workflow code. | Needed for device switching; still just storage. |
| <a id="d14"></a>D14 | Leases with fencing | One lease per execution, renewed while active, with a fencing counter. Stale holders' writes are rejected; other devices show the execution read-only until the lease expires. | Activities have real side effects that cannot be merged afterwards. |
| <a id="d14p"></a>D14' | The journal is the fence | As [D14 Leases with fencing][D14] for its purpose (one writer per run; a stale writer refused), with the lease replaced by the journal. Every engine fact (the start, an activity's start and exit, a clock, the result) names the engine fact of its run it follows; authority accepts it only if that is still the run's head, checked in one step with the append ([I71 An append can land after a revocation][I71]). A takeover is always allowed: whoever is up to date writes on the head. A writer that is behind is refused, and so is everything it built on, so a run is always one history. Outside inputs (deferred completions, [D11 Human steps as deferreds][D11], [D40 Server-side human steps][D40]) are write-once on their own entity and do not move the head. The holder is derived: whoever wrote the head. Only the holder resumes on its own; another device continues when a person asks; a server runner takes over a run whose head has not moved within its running step's timeout; an online writer may claim a step before acting. No lease datom, epoch or heartbeat. A "lost lease" in [D15 Server authority after a lost lease][D15] and [P14 Quarantine after a lost lease][P14] now reads as a refused history, and [D103 Nodes and authority][D103]'s duty "fence leases" as "fence each run's journal". Decided in [I51](../../issues/0051-actors-or-the-engine.md) ([ADR-0036 The journal is the fence][ADR-0036]); built by [I80 Build the journal fence][I80]; until then the lease runs and is safe ([ADR-0014 Leases, fencing and server authority][ADR-0014]). | A lease beside the journal is a second record of who runs a run, which can disagree with the first and needs liveness to move. Write-once facts alone let a spliced history in (an offline phone's later steps on top of another device's step); fencing each history by its head closes that, with nothing to expire. |
| <a id="d15"></a>D15 | Server authority after a lost lease | Server authoritative. A device that lost its lease drops its divergent journal entries and replays from the server. User content (photos, recordings, drafts) is never dropped; it is quarantined for human resolution. | Idempotency keys make side effects harmless; user work is never silently lost. |
| <a id="d20"></a>D20 | Crash matrix as the merge bar | The engine's merge bar is a crash matrix: engine tests with `TestClock` killing at every boundary, plus a simulator force-quit E2E. | In-memory-only durability proves nothing. |
| <a id="d24"></a>D24 | Durable clocks and notifications | Long `DurableClock` sleeps write a `wake_at` datom and schedule a local notification (expo-notifications; Android `alarmClock` delivery for time-critical). The engine sweeps due clocks on launch and foreground; expo-background-task sweeps opportunistically. Notification actions complete the matching `DurableDeferred`. | Turns "resume on next launch" into mechanism. |
| <a id="d25"></a>D25 | Browser engine leader | Browser: one leader tab per profile runs the engine (Web Locks); other tabs render and forward events via BroadcastChannel. Each browser profile counts as one device for leases. | Several tabs are several engines on one OPFS database. |
| <a id="d39"></a>D39 | One engine everywhere | One engine: our datom-backed `WorkflowEngine` on device and server alike. Effect Cluster (`ClusterWorkflowEngine`) is the later scale-out path behind the same interface. | One journal format is the point of [D31 One datom log][D31]. |
| <a id="d39p"></a>D39' | One engine, one journal, one fence | As [D39 One engine everywhere][D39]: our datom-backed engine on device and server alike. Scale-out on the server is more runners writing on the journal head ([D14' The journal is the fence][D14']): each sweeps for runs whose head has not moved within their step's timeout and claims before acting. Effect Cluster is not the scale-out path: it fences by time only, keeps its journal in `MessageStorage` (a work queue with claims and deletes, which fits the log poorly), and assumes runners that are always reachable, which a device is not. It stays possible behind `WorkflowEngine` if a measured load needs its routing in memory ([I8 Engine scale-out and a multi-runner server][I8]). Decided in [I51](../../issues/0051-actors-or-the-engine.md) ([ADR-0036 The journal is the fence][ADR-0036]). | One journal format was [D39 One engine everywhere][D39]'s point; Cluster would add a second journal and a second fence. |
| <a id="d40"></a>D40 | Server-side human steps | Server-side human steps (a reviewer approves on the web) write a deferred-completion datom under `O{org}/W{exec}/D{name}` in the same changeset as the review. It syncs down; the device engine resumes. Push is only a wake-up hint. | Signals become ordinary datoms: deduplicated, fenced, traced, auditable. |

## One datom log, three views

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d31"></a>D31 | One datom log | One datom log is the single substrate: the engine journal, domain data and sync all use it; tracing is derived from it. | One storage format, one sync protocol, one audit trail. Realises vivief's "observability is projection over effect datoms". |
| <a id="d32"></a>D32 | Traces derived from the log | Trace context is written in each changeset's envelope ([D58 Envelope per changeset][D58]). Spans are derived from the log with deterministic span ids (`executionId + activity + attempt`), so replays never duplicate spans. Export is durable: a projector reads the log from a cursor and posts OTLP via Effect's native exporter. Live `withSpan` detail inside activities is parented to durable spans. The tracing backend is never the store the engine reads from. | Tracing and durability become one concept without trusting a lossy, sampled, non-transactional store for durability. |
| <a id="d33p"></a>D33' | Hybrid logical clock for tx | `tx` is a hybrid logical clock `(pt, c)`. `pt` is server-corrected time: monotonic clock anchored to the server offset within a boot session, wall clock + persisted offset after a reboot; never below the last persisted HLC. `c` is a tie-break counter used only when `pt` would not advance. Receive rule: `last = max(last, received)`. Server rejects future skew and flags measured gaps. Encoded ULID-shaped: 48-bit ms, 16-bit counter, remaining bits random + device id. | Offline for days must still work; corrected clocks alone cannot handle backwards jumps or cross-device causality. |
| <a id="d34"></a>D34 | Per-attribute conflict policies | Conflict policy is declared per attribute in its Schema: **LWW** (domain scalars), **write-once fenced** (journal facts, lease grants), **human conflict** (references, evidence attachments, approvals: both values kept, a conflict datom raised). | One global LWW rule is wrong for GRC, ERP and the journal. |
| <a id="d35pp"></a>D35'' | Single-datom transactions with changesets | **Single-datom transactions with a changeset id.** Datom = `[e, a, v, tx, op, cs]`. A changeset becomes visible when its commit datom arrives, carrying a manifest (count + hash of members). Conflicts are ordered by the commit `tx`; the commit records its basis and the server checks, per attribute policy, whether touched attributes changed since. `cs == tx` means self-committed (a checkbox toggle stays one datom). Commit and abort are write-once; open changesets may expire. Authors see a "committed + my open changesets" view. Keep the defining attribute for entity lifecycle. | Keeps web-interview's one-datom wire and storage simplicity, gives atomic multi-attribute and cross-entity changes enforced once by the projector, and makes drafts native (Studio drafts, evidence review, ERP draft orders). |
| <a id="d58"></a>D58 | Envelope per changeset | The envelope (actor, device, lease epoch, trace context, command) is one fixed-shape record per changeset, keyed by `cs`, stored in the `changesets` table (not as datoms) and sent with the commit datom, or with the datom when `cs == tx`. One mechanism for every changeset size; the commit datom carries only manifest and basis. | The changeset is the unit of intent. Uniform, keeps the one-datom shorthand, queryable by joining on `cs`. Replaces a dual mechanism (commit datom vs columns) that was never decided. |
| <a id="d58p"></a>D58' | Envelope names the origin | The envelope gains `origin`: a reference to the origin entity the changeset's content came from (a person, a mail account or chat workspace, a website, a model and its version, a system activity), apart from the actor who committed it. An enriching changeset ([D111 Faster and enriching implementations][D111]) also names the origins of its inputs. For data a person types, the origin is that person. The `datoms` table does not change. Decided in [I49 Projection: one concept or several patterns][I49] ([D115 Origin trust][D115]); built with [I64 Build origin trust][I64]. | Trust belongs to an origin ([D115 Origin trust][D115]), so every changeset must say where its content came from; one field per changeset, not per fact, because gathering commits per batch per origin ([D109 Frame and frame subscription][D109]). |
| <a id="d36"></a>D36 | Shared commands | Commands are shared pure Effect functions `(readModel, intent) -> changeset or DomainError`, run on client and server. The client applies optimistically and queues in an outbox; the server revalidates (Schema, membership, authorization, invariants such as independent review, lease fencing) and accepts or rejects the whole changeset with a typed error. On rejection the client rebuilds from confirmed data and reapplies its remaining outbox. | Server authoritative, offline-capable, one write path for app and engine. |
| <a id="d36p"></a>D36' | Shared commands, as built | As [D36 Shared commands][D36], corrected by what [P09 Sync][P09] built ([ADR-0016 Commands, server validation and rejection][ADR-0016] Observed): the server does not re-execute the command. It accepts or rejects the changeset by [D124 One checkpoint][D124]'s three questions; the command runs on the device and calls the same acceptance rules ([D125 Acceptance rules][D125]), and every domain writer uses a registered command ([D127 Registered commands][D127]). | [D36 Shared commands][D36] named "invariants such as independent review" among what the server revalidates; nothing on the server checked a domain rule, so a crafted changeset with a blank title was accepted. |
| <a id="d16"></a>D16 | SQLite drivers | SQLite drivers: Effect's official drivers, `@effect/sql-sqlite-react-native` (op-sqlite 17.x pinned) on native and `@effect/sql-sqlite-wasm` (OPFS) on web, after a gate. Fallback: our own `SqlClient` over expo-sqlite (one driver for iOS, Android, web). | Less custom code at the most failure-sensitive layer. |
| <a id="d37"></a>D37 | Log store tables | SQLite locally: one append-only datom table with EAVT and AEVT indexes; typed read-model tables (one per entity type, Schema-defined) updated incrementally in the same SQLite transaction. Snapshots and a compaction horizon only past what every device acknowledged. The log store is a pattern with swappable implementations (SQLite device, SQLite Node, Postgres) under one conformance suite. Analytics is a projection to Parquet or DuckLake queried by DuckDB, never the durable log. | Read models are disposable projections; lock-in is avoided because the contract is tested. |
| <a id="d38"></a>D38 | Entity ids and strict composition | Entity ids encode their parent **only for strict composition** (part of the parent, shared lifetime, can never move), declared per entity type: `O{org}/...` root, list -> todo, order -> line, execution -> journal entries. Everything else uses reference attributes. One projection rule: visible iff the defining attribute is asserted and the owner is visible. Orphaned writes to user-content types raise a conflict. Separator `/`, ids are branded Schema types. Guideline: "can it ever move? then it is a reference". | Keeps one-datom tree deletes and prefix scans, makes `O{org}/` the backbone for isolation and sync, avoids immutable ids that cannot move. |
| <a id="d21"></a>D21 | Sync as datom replication (superseded) | Superseded by [D31 One datom log][D31] + [D35'' Single-datom transactions with changesets][D35''] + [D36 Shared commands][D36]: sync is datom replication (outbox up, cursor stream down), server-authoritative validation per changeset. Effect EventLog was studied as a design reference, not adopted (no server rejection, device-clock ordering, no RN path). | See research/03. |
| <a id="d43"></a>D43 | Files by content hash | Files are stored by content hash (`blob:sha256...`): local file storage on device, object storage on server. A datom references the hash; the upload is an idempotent retryable activity; a changeset referencing a file commits only once the file exists on the server (manifest extends to file references). | Bytes in object storage, provenance in the log. |
| <a id="d44"></a>D44 | Never rename, never migrate | Attributes are never renamed or retyped (new attribute + projector mapping instead). Read models are rebuilt, never migrated. Workflows versioned by name, old versions ship until drained. The server refuses unknown attributes with a typed "upgrade" error. | An append-only vocabulary keeps a log-based system migratable for years. |
| <a id="d44p"></a>D44' | Never rename, never migrate, the RPC too | As [D44 Never rename, never migrate][D44], and the sync RPC and every HttpApi or RPC contract shared with the client ([D8 Effect everywhere][D8]) are additive too: a method or field is never renamed or removed while a client that uses it may still run. A version handshake answering an old client with a typed upgrade error is deferred, `Decide when:` the first consumer app ships to a store with old versions in the field. vivief's migration as creation is not adopted for the log; a label that changes is a translation, not a rename. | The attribute check covered data, not the calls that carry it; an old client calling a changed method gets a decode error with no way to say "upgrade". |
| <a id="d50"></a>D50 | Data at rest on device | Data at rest on device: OS file protection as baseline; SQLCipher via op-sqlite with keys in Keychain/Keystore (expo-secure-store) as a qualified option per consumer app, passing the same conformance suite. | GRC probably needs it, BirVana does not. |
| <a id="d51"></a>D51 | Crypto-shredding | Erasure via crypto-shredding: attributes marked `:personal` store values encrypted with a per-subject key; erasure destroys the key; projections show "erased". Bulky personal files are content-hashed blobs that can be deleted. Qualified by a gate proving unreadability on every replica and projection. | Keeps the log immutable and syncable while meeting the right to erasure. |

| # | Name | Decision | Why |

| <a id="d107"></a>D107 | The Presenter pattern | A Presenter is a pattern: a client asks for data with a query, gets a frame back and keeps a frame subscription to it. Reads never write. vivief's `Projection` read side (query, delivery, freshness, trust scope) is adopted as this pattern; access and encryption stay at their boundaries, the server's check on sync and encryption at rest and for erasure ([I54 Trust, encryption and who may sign in][I54]). | <a id="d108"></a>D108 | The query is data | The query is a typed expression, written in code, that each implementation translates: to SQL for SQLite, Postgres and DuckDB, to Polars, or to parameters for a remote `node` or an outside source. It is passed down the chain read model, log store, remote `node`, outside source, each answering what it can. An implementation may be plain code instead of a translated query; it declares that it reads its whole input and applies the query's filter and sort afterwards, so it runs only where that input is held. vivief's L1 idea, queries written in code that an LLM can write, is this decision; its entity operations (`entity`, `pull` with depth) are part of the query's vocabulary, and an entity with its children comes back as a frame per level, linked by id. | A SQL string cannot be passed to Parquet, another `node` or a mail server; an expression can. | <a id="d109"></a>D109 | Frame and frame subscription | A frame is typed rows with each value's origin and the frame's status (fresh, gathering, remote, failed); one entity is a one-row frame (map 5 may revise). Freshness is committed, or committed plus my open changesets ([D42 Live reads with query atoms][D42]). Gathering commits in batches and the frame grows through invalidation. A frame subscription ends with its screen; the gathering activity is durable and goes on committing after it. A snapshot is a one-off read. Cursor consumers (sync pull, trace export, the compaction horizon) stay their own pattern. Output shown before it is committed (vivief's in-flight freshness) is deferred, `Decide when:` a screen needs output finer than a committed batch. | One input shape for screens gives one generic table view; durability belongs to the gathering, not to the frame subscription, so there is no second lifecycle. |
| <a id="d110"></a>D110 | The reference implementation | Every implementation of the Presenter returns the reference implementation's frame for the same query at the same `tx`. SQLite read models with query atoms are the reference and today's default ([P05 Changesets and projections][P05], [P08 UI three-way prototype][P08]). The default can change; the reference changes only by decision. In-memory datom indexes with vivief's entity interface, and engines that keep answers up to date incrementally (`D2TS`, differential dataflow), are candidate faster implementations. | Improving an implementation over time is only safe against a trusted one; this is [P05 Changesets and projections][P05]'s "full rebuild equals incremental" lifted to the pattern. |
| <a id="d111"></a>D111 | Faster and enriching implementations | Implementations come in two kinds. | <a id="d112"></a>D112 | Intermediate presentations | Anything an implementation prepares (an index, a Parquet file, an embedding, a cache) is derived and rebuildable, never mixes organizations, can be erased (ciphertext, or rebuilt when a subject is erased, [D51 Crypto-shredding][D51]), and goes away with the local replica at sign-out. | An embedding of a personal email is personal data; the rules hold for every implementation, so they are the pattern's, not each implementation's. |
| <a id="d113"></a>D113 | Who chooses the implementation | The app builder, person or agent, declares an implementation per Presenter; it is swapped without touching the screen. Choosing automatically at run time is a later implementation, qualified like any other. | Choosing automatically is a query planner; declared choice lets the pattern ship with the implementation that exists. |
| <a id="d114"></a>D114 | Partial sync on demand | A Presenter's query can say what a partial `node` fetches ([D105 What must stay possible][D105] (3)): the facts land in its log and the projector builds the read model, so a read model stays derived from the local log and works offline for what was fetched. vivief's subscription filter is the direction; it is built under [I12 Partial sync, history consolidation and client data access][I12]'s new trigger, a Presenter needs data its `node` does not hold, with [I53 Sync and conflict][I53] owning the sync details. | A log that grows large makes a phone a partial `node`; refreshing it through the log avoids a second kind of read model that cannot be rebuilt offline. |
| <a id="d115"></a>D115 | Origin trust | Trust belongs to an origin, not to data. Every changeset names its origin ([D58' Envelope names the origin][D58']); trust in an origin is datoms on the origin entity, so its history is kept. A value's trust is derived when it is read: the least trusted of its origin and its inputs' origins (vivief's `min` rule), a default policy that can be replaced; a person's review raises only that changeset to the reviewer's level. In a Presenter, trust is a companion column per value when the query asks for it, a threshold is a filter, and the trust context defaults to no filter. vivief's `:tx/source` maps to the origin, and its `:tx/trust-score` set at ingestion is not adopted. | Lowering trust in one origin lowers everything it produced, the way destroying one key erases one person ([D51 Crypto-shredding][D51]); a score fixed at ingestion cannot be withdrawn, and without lineage withdrawal leaks through derived data. |
| <a id="d116"></a>D116 | Trust levels and who sets them | Five ordered levels: `revoked < untrusted < unreviewed < trusted < verified`. Verified: checked by something deterministic (a gate, a validation, an exact source). Trusted: a person, or an origin the organization trusts. Unreviewed: model output or gathered content nobody has checked. Untrusted: kept, but left out of an agent's context by default. Revoked: the organization withdrew trust; shown only to a reviewer. Trust is per organization. Defaults per kind of origin live in the app's catalog; an organization's override is a datom on the origin entity that only authority writes (`authority: 'server'`), until roles loosen it ([I16 Roles in use, invitations and self-service membership][I16]). | A number suggests a precision nobody can defend, and the `min` rule works on levels; lowering an origin's trust changes what every agent and screen sees, closer to granting membership than to editing a title. |
| <a id="d117"></a>D117 | Trust strategies as commit paths | vivief's three trust strategies are commit paths for an enriching implementation, chosen by its origin's trust level: authoritative commits directly; sandboxed keeps the output an open changeset seen only in its author's draft view ([D35'' Single-datom transactions with changesets][D35''], [D42 Live reads with query atoms][D42]); gated is sandboxed plus a durable deferred asking a person to commit it ([D11 Human steps as deferreds][D11], [D40 Server-side human steps][D40]). Implementations behind the contract stay free to change and to multiply ([D110 The reference implementation][D110], [D111 Faster and enriching implementations][D111]). A choice of connectivity (Iroh, WebRTC) gets its own gate when [I60 Server-independent mode][I60] picks it up ([D105 What must stay possible][D105] (7)). | The human's note: a pattern with several implementations is a more robust final choice than one implementation, and keeps the freedom to implement it in several ways. vivief started on its final protocol from day one and changed it three times in about two months. |

## Accepting a change (2026-10-09)

From [I50](../../issues/0050-contracts-checked-as-data-or-by-commands.md), the fifth ticket of
[the foundation concepts map](../foundation-concepts/map.md), grilled with the human on
[the review page](../../research/2026-10-08-contracts-review.html) and in conversation.
[ADR-0035](../../adr/0035-accepting-a-change.md) states [D124 One checkpoint][D124]-[D128 Rules over time][D128]; [D129 Boundaries and live change][D129], [D36' Shared commands, as built][D36'] and [D44' Never rename, never migrate, the RPC too][D44'] amend what was there.
Checking the code found that the server does not re-execute a command ([ADR-0016 Commands, server validation and rejection][ADR-0016] Observed), so a rule that lives only in a command, such as `renameList`'s blank title, is never checked by authority.

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d124"></a>D124 | One checkpoint | Authority accepts or rejects every change by asking three questions in order: **may this writer do this** (an access decision, [I54 Trust, encryption and who may sign in][I54] and [I16 Roles in use, invitations and self-service membership][I16]), **is it well formed** (the structural checks accept runs today: actor, manifest, organization, catalog, files, lease, write-once; membership belongs to the first question), and **does the data stay valid** (acceptance rules, [D125 Acceptance rules][D125]). Each check is declared once, runs early on the device for feedback and with authority on accept as the guard, and has a positive control in a suite. Enforcement follows trust: no writer (a client, an agent, an enriching activity) is trusted to check itself, so authority always enforces. A rule broken by nothing happening is detective, after accept ([D128 Rules over time][D128]). vivief's `Contract` is adopted for its placement (one place every write passes) and for being spec, test and runtime guard at once; contracts as datoms are rejected ([D118 What a datom needs from storage][D118]). A rule that names the writer ("the reviewer is not the author") is an access decision; a rule about the data alone ("a title is not blank") is an acceptance rule. | vivief's elegance was one concept running everywhere; ours is one place every change passes, which the glossary already gives authority. AWS draws the same line between preventive controls (IAM) and detective ones (Config). The server checked structure only, and [D36 Shared commands][D36] claimed more. |
| <a id="d125"></a>D125 | Acceptance rules | An acceptance rule is a rule about the data alone that every changeset must keep, whoever wrote it. Rules are code declared beside the catalog: the value Schema ([D121 Attribute value types][D121]), uniqueness ([D122 External identifiers][D122]), required attributes, allowed transitions of a value (vivief's state machine mode), and entity rules written against a read model so any `node` could run them ([D105 What must stay possible][D105] (2)). A rule is always a guard; vivief's aggregation mode is a projection or an enriching implementation ([D111 Faster and enriching implementations][D111]), and its closed set of six contract sub-types is not adopted: each lands on one pattern's contract, and [D82 Patterns build on each other][D82] keeps that set open. Commands call the same rules, so a device rejects early with the error authority would give. Acceptance rules are a concept of the changesets pattern ([D82][D82]), checked by the suite `changesets/acceptance`; a rule without a positive control fails `verify` (vivief's declared against verifiable). A rule that warns instead of rejecting is deferred, `Decide when:` an app needs a rule people may knowingly break. Built with [I69 Accept checks every change][I69]. | A rule bound to a command misses every changeset no command wrote, and [I49 Projection: one concept or several patterns][I49] made those normal (enriching implementations, agents). The rules have no implementation to swap, so by [D82 Patterns build on each other][D82] they are a concept, not a pattern. |
| <a id="d126"></a>D126 | No worse | A changeset is rejected when it breaks an acceptance rule for an entity where the rule held before it, or for an entity it creates. Data accepted before a rule shipped stays editable; a one-off workflow lists it as findings ([D128 Rules over time][D128]). vivief's invariants are likewise not retroactive. | Writes never make the data worse, old data never blocks work, and the findings make the debt visible. Strict checking would freeze every old entity a new rule catches. |
| <a id="d127"></a>D127 | Registered commands | Every domain writer uses a command: screens, agents, enriching activities and the operator. A command is registered with a name, an intent Schema, a version name and its declared writes, the attributes it may write; accept rejects an unknown command or a write outside its set, which gives an agent least privilege by command. vivief's `produces.required` becomes an acceptance rule on the entity. The one exception is the workflow engine's journal (`viviefs/workflow/*` and the lease), written by the durable-workflow pattern and checked by its own lease fencing and write-once rules ([P06 Workflow engine crash matrix][P06], [P09 Sync][P09]). Re-running a command on accept, as durable execution replays a workflow, is deferred: `Decide when:` an app needs proof that a changeset is exactly what the named command makes, with reads as of a cursor ([I63 The columnar copy as a Presenter implementation][I63]) so authority can re-run it on the data the device saw; commands stay pure with their mint passed in and versions named so it stays possible. Built with [I69 Accept checks every change][I69]. | The envelope always names a command, but only screens' writes came from one; the engine and the operator wrote with a label. One write path in fact gives "which code wrote this?" an answer and gives request rules one home. Re-running would need the intent stored, never renamed and erasable, and every command version shipped until drained, for a proof declared writes mostly give. |
| <a id="d128"></a>D128 | Rules over time | A rule broken by nothing happening ("a high-risk client has a session within 7 days") is a workflow with a durable clock ([D24 Durable clocks and notifications][D24]) that queries through a Presenter and writes a finding as an ordinary changeset whose origin is the rule ([D58' Envelope names the origin][D58']); a screen sees findings through a frame subscription. Deferred: `Decide when:` a consumer app has such a rule. vivief's post-commit validation point maps here; its in-flight point is deferred with in-flight freshness ([D109 Frame and frame subscription][D109]). | No write breaks such a rule, so no check on accept can catch it. Built from parts that exist; a post-commit hook beside the projector would put meaning into its SQL transaction. |
| <a id="d129"></a>D129 | Boundaries and live change | Data coming in decodes through Schema at every boundary ([D79 Schema at every boundary, linted][D79]) and names its origin ([D58' Envelope names the origin][D58']); data going out leaves through an activity; vivief's bridge is not named as one pattern. Trust at a boundary is origin trust ([D115 Origin trust][D115]): outside text comes from an origin that defaults to `unreviewed` or `untrusted`, so it stays out of an agent's context by default ([D116 Trust levels and who sets them][D116]). vivief's intake trust per source is origin trust; inferred facts name their inputs' origins ([D111 Faster and enriching implementations][D111]), and a source span (document, page, offset) is deferred, `Decide when:` an app cites a place in a document. Which code handles a request stays fixed at composition ([D52 Four project kinds][D52]); vivief's handlers as data are rejected, and feature flags are deferred, `Decide when:` a consumer app must try a change on one organization without a release, their form open. The ledger and the Schema stay out of the log ([D48' Verify - Qualify - Teach][D48'], [D118 What a datom needs from storage][D118]), and an app's own run-time evidence is that app's data. | [I49 Projection: one concept or several patterns][I49] already answered vivief's trust at the boundary; what was left was naming it. A missing Layer is a compile error only because composition is fixed. |

## One shape at every level (2026-10-24)

From [I56](../../issues/0056-one-shape-at-every-level.md), the sixth ticket of
[the foundation concepts map](../foundation-concepts/map.md), grilled with the human on
[the review page](../../research/2026-10-10-one-shape-review.html) and in conversation over four rounds.
[ADR-0032 What ViViEfs is about and its foundation concepts][ADR-0032] records [D130-D135 One shape at every level][D130-D135] among the foundation concepts; [D98' Vision - View - Effects, at every level][D98'] amends [D98 Vision - View - Effects][D98].

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d130"></a>D130 | One shape at the data level | Every change to kept state goes from a state and an input, through a step, to the next state. A command **decides**: read model, intent and mint to a changeset or a `DomainError`, pure, its ids and time passed in ([D36' Shared commands, as built][D36']). Authority **accepts** the step into the log ([D124 One checkpoint][D124]). The projector **evolves** the read models from the log, a fold that a rebuild runs again from empty ([D37 Log store tables][D37]). A workflow body is the same over its journal, and an activity is the only place the world (time, ids, IO, models) comes in, its result kept ([D2 Temporal model][D2]). Workflow and Activity are Effect's own (`effect/workflow`), and the engine implements its `WorkflowEngine` ([ADR-0012 Durable execution over one datom-backed engine][ADR-0012]). Failure is data: a typed `DomainError`, a typed `Rejection`, a journaled activity exit. Reads (a Presenter's frame, a query atom) and pure helpers are not handlers: they make no new state, as vivief's creation boundary says. Shown by [P05 Changesets and projections][P05], [P06 Workflow engine crash matrix][P06] and [P09 Sync][P09]. vivief's `effectHandler` is adopted in this form; its name and the formula's terms are map 3's. | The code already works this way under other names: it is event sourcing's split into decide and evolve. Named once, a newcomer sees command, accept, projector and workflow as one idea, and an agent sees that a command cannot write and a projector cannot decide. |
| <a id="d131"></a>D131 | The changeset is the step | The changeset is the step between two states, not `State'`: it means nothing without the log it joins, and it can be rejected. `State'` is the log after accept. Read models are its views: the one a command reads, and the one a person is shown ([D99 Facts kept, meaning derived][D99], [D134 Presenting in any modality][D134]). The device's log is the local context, and authority's log the global one. `viviefs:changeset`: keep ours, with this reading. | vivief v6 moved the same way: a handler returns datoms, not a new state. Calling the read model the state would make the thing we throw away the thing we keep. |
| <a id="d132"></a>D132 | Four states at every level | Above the code, the shape is a lens, not a concept. In one line: people and agents compose intent; apps and tools, themselves built from intent, carry it out to reach a goal. At every level a thing passes four states, named by how settled it is: **hot**, created and open, prepared for sync and still changeable (decide); **the frontier**, the sync, where a checkpoint decides (accept); **warm**, kept with its history (keep); **cold**, net truth that others build on (derive). The levels are data, decisions, code, claims and patterns. For data: an open changeset, accept, the log, the read model. For decisions: a review page, the human settling a round, the decision log, the ADR and the glossary. For code: a worktree change, verify green and the human agreeing, main's history, a qualified commit. For claims: a probe, qualify, the ledger, gate state. For patterns: a guide draft, accepting it, its history, an accepted guide. At every level an intent is composed while hot and reviewed and submitted at the frontier, as the IntentComposer does at the data level. The kinds of intent run from a WayFinder map, a grilling with docs, a grilling, a prompt and one decision, down to a button press. Ordered by how abstract the intent is, they are also ordered by how long a turn takes, and that orders the levels. A skill is vivief's Markdown/LLM implementation strategy and the IntentComposer its StateMachine one (v6 §2.5); vivief's aperture (trust, freshness, how many handlers act) is a different axis and stays with its own row. Something cold that someone reads becomes a hot intent at another level. The tiers follow `vivief ADR 0050` and [ADR-0011 Log store pattern, read models, compaction and analytics][ADR-0011]'s compaction horizon. The four words are not glossary terms yet: hot, warm and cold clash with hot reload and cold and warm start, so the words wait for map 3, and so does "abstraction" ([I33 Ideas batch: abstractions that constrain agents][I33]). `vivief:fractal-factory`: adopted, narrowed, as this lens. Not adopted: datoms as the substrate for development artifacts ([D129 Boundaries and live change][D129], [D48' Verify - Qualify - Teach][D48']), and "velocity compounds" as a claim; whether agents build faster from the guides is map 4's evidence question. An app is not a pattern: a pattern is one part, and patterns do not nest ([D82 Patterns build on each other][D82]). What repeats across apps, their shape ([D106 Consumer app shape][D106], [D52 Four project kinds][D52], the app shell of [P12 UI on every platform][P12] and [P13 Links and routing][P13]), is a candidate pattern when phase 3 builds the app shell. | One axis for every level, with vivief's meaning of temperature (how settled, not how fast). It puts a grilling, accept, verify and qualify at the same place, the crossing, and shows that a WayFinder map and a button press are the same move at different sizes. No gate can show that a guide or a session is a function, so it stays a lens. |
| <a id="d133"></a>D133 | Verified commit | A verified commit is a commit on which `pnpm verify` is green. A commit is to the repository what a changeset is to the log: one step, all or nothing. It is prepared in a worktree, crosses the code level's frontier (verify green, the human agrees), and lands on `main`, where CI runs verify again. It is files in git, not datoms ([D48' Verify - Qualify - Teach][D48'], [D129 Boundaries and live change][D129]). Unlike accept's verdict, verify's is not kept with the commit, only in the CI run ([I76 Verify's verdict is not kept per commit][I76]). "Changeset" stays a data word ([D44 Never rename, never migrate][D44]), so "code changeset" is avoided. | "A passing tree" was a phrase with no definition. "Merged" names a workflow this repository does not have: commits land on `main` directly. GitHub's "Verified" badge means a signed commit; the glossary entry says so, and map 3 can revisit the word. |
| <a id="d134"></a>D134 | Presenting in any modality | A frame reaches a person through a surface of any modality: a screen (text, diagrams, pictures), a speaker (speech, music), haptics, or ways not known yet. A screen is one kind. The Presenter's contract already names no modality. An agent reads a frame through a tool, not a surface. "Surface" is map 3's leading candidate for the word. It clashes with the `Surface` component of React Native Paper and Material, with "API surface" and "attack surface", and with vivief's Surface, whose six modes are all visual. "Screen" stays in existing text until map 3, and where the meaning is visual ([D73 Links and routing][D73]). | A screen is one way to present. Naming the visual case as the general one would make every other way an exception. The word clashes, so it waits, by the map's rule. |
| <a id="d135"></a>D135 | Effect's names first | A concept Effect already names takes Effect's name and meaning. A new name is checked against Effect's modules (the core and `ai`, `cluster`, `eventlog`, `persistence`, `reactivity`, `rpc`, `sql`, `workflow`) before it is adopted. A deliberate difference says why, as [ADR-0006 One datom log as the substrate][ADR-0006], [ADR-0016 Commands, server validation and rejection][ADR-0016] and [ADR-0017 Sync: outbox and cursor stream over Effect RPC][ADR-0017] do for EventLog. Where the stack runs this already holds: Service, Layer, Schema, Workflow, Activity, Durable clock, Reactivity, Atom, Rpc and Sql are used as Effect means them. Not compared yet: `ai` and most of `cluster`. [I78 Research: Effect's vocabulary against ours][I78] compares them before map 3, and [I51 Actors or the engine][I51] reads `cluster` (Entity, Sharding, Singleton) first. Known clashes: Envelope, Journal (`EventJournal`), Entity, Decision and "decide" (`ai/Decision`, `DecisionModel.decide`), Tool, Prompt. | We build on Effect and keep its source in the repository. vivief's concepts were written before anyone read it, so taking them over could rename or reinvent what Effect already has. An agent that knows Effect then reads our code the way Effect's own documentation does. |

## Actors or the engine (2026-10-26)

From [I51](../../issues/0051-actors-or-the-engine.md), the seventh ticket of
[the foundation concepts map](../foundation-concepts/map.md), grilled with the human on
[the review page](../../research/2026-10-24-actors-or-the-engine-review.html) and in conversation over three rounds.
[ADR-0032 What ViViEfs is about and its foundation concepts][ADR-0032] records [D136-D141 Actors or the engine][D136-D141] among the foundation concepts; [ADR-0036 The journal is the fence][ADR-0036] records [D14' The journal is the fence][D14'] and [D39' One engine, one journal, one fence][D39'], which amend [D14 Leases with fencing][D14] and [D39 One engine everywhere][D39] and are placed after them.

| # | Name | Decision | Why |
|---|---|---|---|
| <a id="d136"></a>D136 | The actor level is the durable workflow | vivief's two handler levels are a command (the function) and a durable workflow (the actor). The workflow is the actor's type and each execution one actor: its identity `O{org}/W{exec}`, its state the journal, its typed protocol the workflow's schemas and its deferreds, its mailbox the outside inputs ([D11 Human steps as deferreds][D11], [D40 Server-side human steps][D40]), its lifecycle started, suspended, interrupted, done, and one writer at a time ([D14' The journal is the fence][D14']). Supervision is resume from the journal (restart), failure as data (escalate) and interrupt (stop). There is no actor runtime: the engine, the projector and query atoms stay separate parts. Effect builds its own durable workflow on Cluster's Entity; ours is built on the log. Shown by [P06 Workflow engine crash matrix][P06], [P07 Device resume E2E][P07] and [P09 Sync][P09]. `vivief:handler-levels` is adopted in this form; `vivief:actor-runtime`: keep ours. "actor" keeps its meaning as the envelope field ([D141 The actor is the accountable identity][D141]). | Every property of vivief's actor already has an answer in the execution, and two are stronger: its state survives a crash, and its fence holds across devices, not only across servers. A second runtime would duplicate it. |
| <a id="d137"></a>D137 | One meaning of entity | An entity is a thing with an identity, a type and an id, that facts are about: a person, a location, a list, a photo, a workflow run. Some entity types also act: they have a protocol and one writer at a time. The execution is the only one today. Effect's Cluster `Entity` is an entity type that acts; its runtime (sharding, a mailbox in memory, `MessageStorage`) is not adopted ([D39' One engine, one journal, one fence][D39']). In code Effect's `Entity` names the type and our `entity` an instance's id; the word for an entity that acts is map 3's. | The two share their core, an identity facts are about; what differs is whether it acts. Calling it a clash would split one idea in two. |
| <a id="d138"></a>D138 | A workflow, or a cursor | Work that must not lose progress on a crash is a workflow. Anything else rebuilds from its own acknowledged cursor and runs as a scoped Layer with a Schedule retry, with no supervisor. A recurring server job that must have one owner is a server workflow that loops on a durable clock, so it needs no Singleton or ClusterCron. Drain before close stays a rule for owned resources; a workflow needs no drain, because an interrupted run resumes. `viviefs:drain-before-close`: keep ours. | Every loop in sight (sync pull, trace export, compaction, projector catch-up) reads from a cursor it advances only on acknowledgement, so a crash loses nothing. A supervisor tree would be a second lifecycle beside Effect's scopes. |
| <a id="d139"></a>D139 | No event bus | Reactivity invalidation routes a change inside a process ([D42 Live reads with query atoms][D42]); between `node`s each consumer reads the log from its own cursor ([ADR-0017 Sync: outbox and cursor stream over Effect RPC][ADR-0017]); a push is only a wake-up hint carrying no logic ([D40 Server-side human steps][D40]). No broker. `vivief:event-broker`: reject; `vivief:cross-cutting-needs`: keep ours. | A broker would carry every commit twice, and the second copy would need its own deduplication, ordering, retention and access checks, which the log already has. |
| <a id="d140"></a>D140 | Commands and the engine are the handler runtime | What vivief asks of an `effectHandler` runtime, ViViEfs has in commands (the function level) and the engine (the actor level): the queue is the deferreds and the outbox, failure is typed errors and journaled exits. A model call is an activity ([D111 Faster and enriching implementations][D111]). A handler written as instructions for a model is a skill, vivief's Markdown/LLM strategy in [D132 Four states at every level][D132]'s lens, not a part of the runtime. `vivief:effect-handler-runtime-needs`: keep ours. | A model's output already enters through an activity, journaled, with its origin. A second door would go around both. |
| <a id="d141"></a>D141 | The actor is the accountable identity | The envelope's `actor` is the authenticated identity accountable for a changeset, the one authority checked ([D124 One checkpoint][D124]'s first question). Today a person or the server (the server rejects an actor that is not the signed-in caller, `ActorMismatch`). An agent writing in a person's session has that person as actor; inside a server workflow, the server; in both the model is the origin ([D58' Envelope names the origin][D58'], [D115 Origin trust][D115]). Whether an agent may have its own identity is [I54 Trust, encryption and who may sign in][I54]'s. The kind of identity is a fact about that identity, read when access is decided, not an envelope field. vivief's actor category (`vivief:provenance`, "actor-type defaults") is not adopted: trust stays on the origin. | "A person or the server" was the list of identities that can sign in today, not the meaning. With trust on the origin, nothing needs the actor's kind on every changeset. |
