01 · Working conclusion

Share the domain foundation. Make authority explicit.

The strongest candidate is a common replica core with explicit enterprise and independent authority profiles, using different connection implementations where they earn their place. Retain Effect RPC over HTTP for enterprise communication. Evaluate Iroh for native peer connectivity and blob transfer. Keep WebRTC/libp2p as the serious alternative when direct browser-to-browser communication is a requirement.

This is an architectural recommendation, not a measured winner. Effect RPC describes typed interactions; Iroh establishes authenticated connections. They occupy different layers and can coexist. Replacing one with the other does not resolve who may publish, which history is accepted, or who may execute an irreversible activity.

Enterprise profile

The organization appoints an authority for acceptance, membership and coordinated work. Devices can connect directly and exchange verifiable material, while final enterprise acceptance remains authoritative.

Success means better connectivity without weakening existing business guarantees.

Independent profile

Authorized devices create, retain and exchange useful state without an application server or mandatory online identity provider. Shared rules govern mergeable work; exclusive work has an explicit owner or coordination requirement.

Success means the product remains useful when its operator disappears.

First-class P2P is a supported behavior, not a hidden transport option. It needs independent creation and identity, durable local writes, restart and catch-up, recovery, and a documented answer for conflicts. An enterprise outage must never silently switch an organization into independent authority.

Server independence does not imply infrastructure independence. Relays, address lookup, static web hosting, push notifications and optional backup replicas may still help. A relay forwards traffic; a storage replica retains data; an authority decides acceptance. These roles can be deployed together but should remain conceptually separate. This direction follows local-first ownership principles while preserving enterprise coordination where needed. [Local-first]

Iroh: materially more mature, with specific platform limits

The July 9, 2026 release essay states that Iroh 1.0 shipped. Its current release policy describes wire compatibility across adjacent major series and maintenance windows. This is stronger evidence than the predecessor’s “1.0 roadmap” rationale, but core transport maturity does not establish the maturity of every protocol, language binding or Expo integration. No benchmark or security-audit conclusion is claimed here. [Release]

Official Swift and Kotlin bindings document iOS and Android paths; the JavaScript binding is Node-oriented. None of those facts proves that it works directly in Hermes. The plausible native composition is a small Expo native module around the supported native interface, exposing connection capabilities to Effect. Qualification must cover lifecycle, cancellation, binary copies, memory and background suspension. [Native bindings]

The documented browser build uses WebAssembly and all browser connections traverse a relay, while remaining encrypted end to end. There is no bundled browser npm package in the inspected documentation. This can satisfy independent application authority with replaceable infrastructure, but cannot meet “two browser tabs communicate directly with no relay.” [Browser]

Enterprise networking deserves a separate decision: Iroh’s relay path requires WebSocket-compatible egress; permitting ordinary HTTPS alone is insufficient. Self-hosted infrastructure is supported. Inspecting proxy configuration, address lookup, default port mapping and network policy is part of adoption, not a reason to assume any port-443 connection will work. Keep HTTP as a complete enterprise path. [Enterprise networks]

Iroh protocols should earn separate adoption

iroh-blobs is especially relevant to evidence files: BLAKE3-addressed content, verified ranges and resumable transfer. ViViEfs currently uses blob: plus SHA-256. A change needs either a versioned content identifier or a verified mapping from the existing hash to the transfer hash; quietly replacing the hash changes persisted meaning. Hash integrity also does not grant access or promise that someone retains a copy. [Blobs] [R1]

iroh-gossip can announce that new material exists. Durable catch-up should reconcile stored history after reconnect, rather than depend on receiving every announcement. iroh-docs already combines reconciliation, blobs and gossip, but brings its own entry and storage model. Reuse a proven mechanism when its contract fits; avoid maintaining two independent sources of truth. [Gossip] [iroh-docs]

Licence snapshot: Iroh and js-libp2p declare MIT/Apache-2.0 alternatives; Automerge declares MIT; Holochain declares CAL-1.0. This is an inventory, not an adoption clearance. Exact packages, native artefacts and transitive dependencies need the repository’s licence checks before addition. No dependencies were added. [Licences]

04 · Proposed reference architecture

A small shared core with honest differences.

Keep commands, datoms, changeset manifests and read models as the common domain language where their invariants hold. Separate identity evidence, acceptance rules, reconciliation and byte movement. Do not force every profile through a server-shaped append -> server cursor interface.

ResponsibilityWhat callers should be able to rely on
Replica corePersist local work, import verified material, project complete changesets and report meaningful state. Stable IDs and replay safety survive reconnect and process death.
Identity and permissionsVerify who produced an action and the permission evidence relevant to it. Keep Person, device signing key, transport endpoint key and OIDC account mapping distinct.
Authority profileSpecify which operations are independently valid, which need final acceptance, and which must wait for ownership or coordination. Refusal and uncertainty are explicit outcomes.
ReplicationFind missing history, request it within resource limits, verify it, acknowledge durable receipt and recover after interruption. Server cursors and peer causal summaries are distinct progress mechanisms.
ConnectionsAuthenticated endpoint channels, bounded data transfer, backpressure, cancellation and reconnect. The chosen path does not grant business authority.
Blob availabilityVerify content and access, resume large transfers, and distinguish “I have these bytes” from an accepted retention promise. A manifest alone cannot supply missing bytes.

Reuse one acceptance vocabulary, not one false success state. “Saved on this device,” “received by another replica,” “accepted by enterprise authority,” and “conflict requiring resolution” communicate different promises. These are proposed user-visible distinctions, not pinned enum or attribute names.

Three concrete deployments

  1. Enterprise hub. Native and web devices use Effect RPC/HTTP. The authority validates, sequences and stores accepted history. Production databases, durable blobs and availability are operational choices. This preserves the current model.
  2. Enterprise with peer exchange. Devices can transfer permitted blobs and already accepted, independently verifiable changesets. They may relay proposals, but cannot turn them into accepted enterprise history. Keep the authoritative catch-up path for omissions and fresh membership. Forwarding somebody else’s proposal requires signed authorship/delegation; the present bearer-caller/actor check is insufficient.
  3. Independent group. Devices establish a group trust root, grant devices permissions, persist signed changesets and reconcile over direct or encrypted relayed connections. An optional always-on replica helps asynchronous delivery, backup and discovery, but has no special validation authority. No mandatory OIDC lookup or server acknowledgement is needed for the agreed mergeable operations.

Recommended initial independent scope: append evidence, edit agreed mergeable attributes and exchange files among an invited group. Treat shared exclusive activities separately. This makes independent mode real without claiming every ERP operation can remain available under partition.

How far should protocol reuse go?

Effect already separates RPC contracts from its connection protocol; the inspected SyncRpc is a useful starting seam. Carrying Effect RPC over an Iroh stream may preserve TypeScript behavior, but is not automatically supported. It needs framing, errors, streaming, cancellation and resource-limit tests. Prefer keeping Rust focused on connections if that avoids duplicating domain validation. Only define a language-neutral, versioned wire format when a non-Effect participant needs it; canonical signing bytes still require an explicit specification. [R7]

05 · Guarantees that drive the design

Convergence and authority solve different problems.

1. One server cursor cannot describe independent history

If A and B each create changes offline, they have different histories and different local sequence numbers. Taking the larger number loses information. An independent profile needs a way to summarize missing history: for example per-writer counters with gap detection, a causal graph, or content-set reconciliation. Choose one after establishing membership and conflict semantics. A hash of one observed head does not prove a malicious writer never showed another head elsewhere.

Preserve the fast server-cursor path for enterprise catch-up. For P2P, distinguish receipt progress from causal dependencies and authority acceptance. The existing numeric basis and projector logic are part of the redesign, not merely transport configuration. Incremental projection must equal rebuilding from the same valid history regardless of arrival order.

2. A convergent log does not make every operation coordination-free

Two offline devices can append distinct observations and later retain both. Two devices cannot each promise that they exclusively spent the same remaining unit without an additional rule. CRDT merge policies can make data converge; they do not automatically preserve every business invariant. Invariant-confluence research gives a useful criterion: coordinate where merging independently valid states could violate the application’s invariant. [Coordination]

For ViViEfs, re-prove LWW, human-conflict, defining-attribute deletion, changeset manifests and write-once behavior in the new model. HLC gives ordering information, not honest physical time or proof that a remote author had seen another change. A malicious future clock must not be allowed to win indefinitely. Keep useful conflict alternatives rather than silently resolving a business dispute through a tie-breaker.

3. Exclusive workflows require a real owner or coordination

Keep server-fenced leases for enterprise mode. For independent mode, compare three policies: a workflow remains owned by one device until an explicit handoff; a stable quorum authorizes transfers; or duplicate execution is allowed only where the external target reliably deduplicates a shared idempotency key. The first is the simplest starting candidate. Device loss then becomes recovery work, not permission to invent a newer epoch offline.

Consensus such as Raft requires a majority to make progress and assumes non-Byzantine participants; it is not automatically a good fit for intermittently online, mutually distrustful phones. A peer group needing malicious-member tolerance needs a stronger model. Rejecting a stale journal entry also cannot undo an external payment already made. That target must enforce idempotency or fencing where the guarantee depends on it. [Raft] [R2]

4. Authenticate connections, sign durable meaning

Iroh authenticates endpoint keys and encrypts the connection, including through a relay. That does not bind the endpoint to a Person, grant organization membership, or make a stored changeset portable evidence of authorship. Its own security guidance leaves application authorization to applications. Relays can still observe network metadata; encrypted payloads do not make endpoints anonymous. [Security]

A candidate durable proof binds organization, signer/key epoch, schema/protocol version, changeset members and manifest, relevant causal context and permission evidence. Server acceptance should be a separate signed receipt over that immutable authored content. Otherwise adding acceptedAt mutates what the author signed. Exact encoding and key lifecycle remain open; the current envelope is not silently extended by this research.

Independent membership needs a bootstrapped trust root, invitations, delegation bounds, device removal and recovery. Do not replicate the enterprise server-only OIDC account mapping to peers. Also do not forward a bearer access token to an arbitrary peer: authenticate the peer interaction with evidence intended for that recipient and purpose.

5. Offline revocation is necessarily delayed knowledge

An isolated device cannot know that another device was revoked five minutes ago. Define what “authorized when created” means, how concurrent revocation and edits resolve, how keys rotate, and when a receiver must demand fresh authority information. A self-asserted clock cannot settle whether a write predates revocation. Enterprise mode can require online checks for sensitive operations; independent mode must state its offline policy. Previously disclosed plaintext cannot be revoked retroactively.

Connection encryption and SQLCipher do not provide encrypted group replication by themselves. An untrusted storage replica needs application-level ciphertext and explicit key distribution. This must align with P13 crypto-shredding, retained signatures, ciphertext hashing and subject keys. An enterprise server validating plaintext and a blind storage replica have different trust roles. [R5]

6. Permission to connect is not permission to replicate everything

Current full-organization replication is a deliberate scope choice with known over-broad local-read and growth risks. P2P increases the consequences of distribution. Determine sharing scopes before deploying it for selective collaboration: an entire organization, a project, or a changeset’s dependency closure. The UI cannot securely hide data already replicated to an unauthorized device. Partial sync also needs a rule for atomic changesets crossing scopes.

7. Availability, retention and mobile lifecycle remain application work

An offline recipient needs some other participant to retain its updates until it returns. A forwarding relay is not a durable mailbox. Independent operation therefore needs overlapping device availability, optional storage replicas, or an explicit export/import mechanism. The web application’s own code must also remain obtainable if its original host disappears.

Design sync around interruption: checkpoint transfers, bound reconciliation and pending work, resume after suspension, and expose whether bytes are locally durable or redundantly retained. Compaction cannot wait forever for every peer ever seen. Define retirement, retention windows, trusted snapshots and re-bootstrap. In the current plan the server log remains uncompacted pending tamper-evidence work; do not relax that by implementing a P2P shortcut. [R5]

06 · Discussion frontier

The decisions that would change the recommendation.

The scope decision is settled: support both enterprise authority and independent operation. The following are deliberately unresolved. Recommendations are research positions, not user approvals or new repository decisions.

IDQuestion and recommended starting pointWhat changes with another answer
Q1Must independent mode work without any reachable relay? Start with no required application authority, plus native LAN operation and replaceable relays.Direct, relay-free browser peers make WebRTC/libp2p much more attractive than current Iroh browser support.
Q2Which operations must be final offline? Start with evidence and mergeable collaboration; list exclusive business operations explicitly.Offline finality for scarce resources requires preallocated rights, stronger coordination or weaker semantics.
Q3Who may join and govern an independent group? Start with invited groups and an explicit owner/admin trust root.Open membership, malicious administrators or federation substantially change authorization and abuse resistance.
Q4Is web a full offline owner, or a participating client? Prefer durable local ownership, with a documented relayed connection limitation if Iroh wins.Gateway-only web weakens product independence. Native-only independence would be a deliberate scope restriction.
Q5May the same data move between profiles? Start with explicit import/promotion while preserving provenance and revalidation.Seamless live switching needs an authority-transition protocol, fork handling and migration of acceptance semantics.
Q6What must survive device loss? Define data recovery and identity recovery separately, with optional encrypted backup replicas.No external storage and no second surviving device cannot promise recovery.
Q7Is media central to the reference architecture? Keep it a separate optional concern until a consumer requires it.A media-first product could justify MoQ across several delivery paths, while durable reconciliation still remains separate.

Suggested discussion order: resolve Q1-Q4 using a field-team scenario, then Q5-Q6 using revocation and lost-device scenarios. Defer package names and wire codecs until these answers constrain them. Q7 can remain deferred if there is no media requirement.

Competing architecture directions

  • Retain the server model, add P2P transport: smallest semantic change and useful for enterprise connectivity, but fails the confirmed independent-mode goal on its own.
  • Common core, explicit authority profiles: recommended hypothesis. Reuses domain meaning and projection while exposing differences in acceptance and coordination. Risk: the common contract becomes too weak or too configurable; a paired exemplar must demonstrate useful reuse.
  • P2P-native core, enterprise server as one policy participant: strongest uniform peer story. Attractive if independent collaboration dominates; risk of rebuilding server guarantees as a complex distributed protocol. Automerge and Holochain provide different reference points, not interchangeable implementations.
07 · How to earn confidence

Test the shared guarantees before choosing the universal stack.

No new gate numbers or changes to frozen decisions are proposed as settled. Amend the relevant ADRs only after the architectural discussion. Retain existing P09/P11 expectations for enterprise mode; qualify independent behavior with a named scope and paired positive controls.

  1. Paired exemplar: two devices create an evidence item and file, disconnect, edit, restart and converge. Run once through enterprise acceptance and once with no application authority. The independent run must not contact an OIDC provider or hidden sync server.
  2. Connection comparison: Iroh versus WebRTC/libp2p on physical iOS and Android, desktop browsers and mobile browsers. Exercise LAN without internet, restrictive NAT, UDP blocked, WebSockets blocked, Wi-Fi/cellular changes, suspension and relay loss. Record direct/relayed paths, latency, CPU, memory, battery and binary/bundle size. Do not infer these from QUIC marketing.
  3. History and projection: reordered and duplicated changesets, missing dependencies, partially received manifests, poisoned clocks, schema skew and a replica offline beyond retention. Require incremental projection to equal a full rebuild; incomplete manifests must remain invisible.
  4. Authority and adversaries: wrong Person, unauthorized organization, forged acceptance receipt, equivocation, replay across organizations, revoked device and duplicate identifier with altered content. Include corrupt-blob and oversized-message controls. A rejected request must not leak another organization’s existence.
  5. Exclusive activity: partition during handoff and crash after an external side effect but before journaling. Observe the external target, not only the log. The result must match the selected ownership and idempotency policy.
  6. Independence and recovery: remove the original operator, restore data onto a fresh authorized device, rotate/recover keys, replace the relay and catch up from another replica. Separately test a browser build’s dependency on static hosting.

Decision rule: prefer Iroh when native peer connections and large verified transfers are central and relayed browsers meet the requirement. Prefer WebRTC/libp2p when direct browser peers or its interoperability ecosystem are decisive. Preserve the enterprise HTTP path either way. If the same domain operations cannot be expressed honestly in both profiles, share lower-level mechanisms and keep their acceptance contracts separate.

Adoption is reversible at the connection seam only if durable identities and signed data do not depend unnecessarily on one library’s endpoint format. Protocol versions, hash algorithms, key rotation and persisted acceptance semantics deserve more conservatism than replacing a connection implementation.
